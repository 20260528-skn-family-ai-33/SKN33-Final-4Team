카드 후보 조회·선택 저장·청구서 조회 3개 API의 요청·응답과 예시를 정리한다. 팀원과 논의할 내용은 이 문서 마지막의 **확인 필요 사항 모음**에서 확인한다.

기존 검토 내용과 참조를 유지하기 위해 API 번호 1~10과 소비 분석 A-1~A-7 번호를 그대로 사용한다. 다른 기능의 번호는 위 관련 문서에서 확인한다.

문서 작성 완료와 팀 합의·구현 완료는 다르다. 본문의 **초안 제안·미정·확정 보류** 표시는 유지했다. 기존 모델에 칸이 있다는 사실만으로 CODEF 제공 여부나 사용자 수정 권한이 확정되는 것은 아니다. 예시의 개인정보·금액·UUID는 모두 가상 값이다.

비밀번호 재설정·ML 입력 정보·추천 예산·쿠션 배분 규칙·후속 차수 기능은 이번에 정하지 않는다. 로그인·내 계정 응답의 `onboardingCompleted`는 첫 예산 승인 시 true이며, false면 저장된 값을 채운 온보딩 첫 단계로 이동한다(결정기록 3-3 R). 1차에는 단계 번호를 반환하지 않는다. 금융 동의·계좌·연결 해제·재조회·챗봇 전체 계약은 혜리 담당이며, `chat.md` 최종 편집도 혜리가 한다.

- 홈 ‘꼭 나갈 돈 → 카드 청구서 → 청구서 상세 보기’에서 상세 팝업을 연다. 홈의 `sourceId`를 `billId`로 사용해 기존 상세 GET API를 호출한다.

- 로딩·동의 필요·세션 만료·404·통신 오류와 재조회 동작을 제공한다. 기존 시안의 별칭/연결 해제 기능은 청구서 팝업에서 제거하고 기존 연결 관리 화면에서 관리한다.
- 연결 관리의 카드사에서 청구서 목록/월 선택으로 들어가는 경로는 이번 범위에 포함하지 않는다.

### 요청·오류·재시도 공통 적용

- 보내는 값 표에 없는 필드와 서버가 정하는 필드(예: `status`)를 보내면 400 `invalid`, 해당 필드에 “이 칸은 보낼 수 없어요.”를 반환한다. 조용히 무시하지 않는다. 아직 확정 보류인 요청 필드는 허용 목록으로 취급하지 않는다.
- 오류에는 `code`·`message`가 항상 있다. `fields`는 입력 칸 오류가 있을 때만 넣고, 로그인 불일치·미인증·404처럼 칸과 무관한 오류에서는 키 자체를 생략한다. 빈 `{}`를 보내지 않는다. 여러 입력 칸의 조합 오류는 `fields.nonFieldErrors`를 사용한다.
- 주소 ID가 잘못된 UUID이거나, 없거나, 남의 항목이거나, 해당 동작을 할 수 없는 상태이면 JSON 404 `not_found`다. 본문 ID의 형식 오류·없는 항목·남의 항목·선택 불가 항목은 400이며, 여러 개 중 하나라도 잘못되면 전체 저장하지 않는다. 존재·소유·선택 가능 여부를 구분해 노출하지 않는다.
- 이미 요청한 상태라면 같은 작업을 다시 반영하지 않고 성공으로 응답한다. 다만 없는 ID·남의 데이터에는 적용하지 않는다. 대출 보완은 `repaying`만 가능하고 `repaid`는 404다(P). 카드의 원천 상태별 선택 가능 범위는 마지막 확인 목록에 남기며 고정지출 상태 코드를 그대로 가져오지 않는다.
- 새로 만들기·승인 요청에 쓰는 `Idempotency-Key`는 입력 폼·팝업을 열 때, 버튼 하나로 끝나는 동작은 누를 때 만든다. 처리 중 버튼을 잠그고 응답 전 재전송에는 같은 키를 쓰며, 완료 후 버린다.
- 요청 번호 적용 대상에서는 같은 회원·키·내용에 처음 응답을 재사용하고, 기록된 키로 다른 내용을 보내면 409 `idempotency_conflict`다. 실패한 4xx·5xx는 기록하지 않아 수정 후 같은 키로 재시도할 수 있다. 회원가입은 이메일 중복 검사·DB 유일성 제약으로 중복 가입을 막으며 별도 요청 번호를 쓰지 않는다(결정기록 3-3 X). 이 규칙만으로 모든 PUT·PATCH에 필수 헤더를 추가하지 않는다.

회원가입·로그인의 세션·CSRF 계약과 이메일 중복 방지는 [인증·회원 명세](./auth.md)를 참조한다.

아래 공통 규칙의 “6개 API”는 카드 3개와 대출 3개(직접 등록 포함)를 합한 범위다.

## 카드·대출 공통 규칙

- 6개 API 모두 로그인 필요. 조회는 세션 쿠키, 저장은 세션 쿠키와 `X-CSRFToken`을 사용한다.
- 금액은 원 단위 정수, 날짜는 `YYYY-MM-DD`, 시각은 한국 시간 ISO 8601, ID는 UUID 문자열이다.
- 목록은 `{ "items": [...] }`, 조회가 정상 완료되어 항목이 없으면 `{ "items": [] }`이다. 미조회·조회 실패를 보유 상품 없음으로 바꾸지 않는다.
- 모르는 값은 null, 확인된 0원은 0이다. 값이 없다고 계산해서 채우거나 다른 항목을 대신 쓰지 않는다.
- 계좌·카드 응답은 공통 규칙의 `displayName`·`status`를 포함한다. `connected`는 정상 연결, `relogin`은 다시 연결 필요(선택·기존 연결 유지), `disconnected`는 연결 해제(새로 선택 불가)다. **결정 기록 H-07에 따라 API 값은 DB 값과 같으며, 계좌·카드의 연결 상태는 연결된 `connection.status`에서 그대로 가져온다.** 별도 상태 저장·API용 매핑은 만들지 않는다. 기관이 제공하는 `cardStatus`와는 다른 값이다. 모델의 choices·CHECK 미반영은 구현 대기이며 정책 미정이 아니다. 연결 FK가 없는 카드의 응답·노출 방식은 별도 확인 대상으로 남긴다.
- 응답에는 비밀번호·CODEF 키·`connectedId`·원문 번호·기관 원천 식별값·암호화 원문을 넣지 않는다. 예시 데이터는 모두 가상이다.
- 본인 소유만 조회·수정한다. 관련 계좌·카드·연결의 소유권도 서버에서 검증한다.
- 고정비는 생활비를 나누기 전에 한 번만 뺀다. 확정 고정지출·대출 월 상환 예정액·첫 카드 청구서·이번 회차 할부금 사이에 같은 비용을 중복 차감하지 않는다. 승인된 예산은 사용자 승인 없이 변경하지 않는다.
- `PaymentDue`는 출금일이 있을 때만 만든다. 출금일을 모르면 날짜를 추측하지 않고 “출금일 확인 필요”로 안내한다. 카드 청구서는 출금 예정일, 없으면 결제 예정일을 출금일로 본다(11/5 나은: 카드는 결제일에 출금됨). 카드로 내는 고정지출은 카드 청구서에 포함되므로 고정지출용 납부 예정을 따로 만들지 않는다.
- 고정지출과 연결된 카드 거래는 `spending_allocation.funding_bucket = fixed`로 분류하여 생활비 카테고리 사용액에서 제외한다. 연결은 이름만으로 판단하지 않고 실제 근거 거래를 사용한다. 소비 분석의 총액·카테고리 금액에는 포함하고, 그중 고정지출 합계를 `fixedAmount`로 따로 표시한다(결정기록 3-3 S).
- “이번 주기”는 설정한 월급날부터 다음 월급날 전날까지다(H-01). 실제 입금이 늦어도 주기는 바뀌고 그 사이 소비는 새 주기에 속한다. 다음 월급이 미리 들어와도 지난 주기 예산에 더하지 않는다. 매월 해당 날짜가 없는 달은 말일을 사용한다.

### 카드·대출 공통 실패 처리

각 API의 실패 표와 함께 적용한다.

| 상황 | HTTP 상태 | `error.code` | 화면 안내 |
|---|---|---|---|
| 비로그인·세션 만료 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| 저장 요청의 CSRF 실패 | 403 | `permission_denied` | 다시 시도 안내 |
| 입력 형식·값 오류 | 400 | `invalid` | 해당 `fields`를 입력 칸 아래 표시 |
| 주소의 ID 형식 오류·없는 항목·남의 항목·해당 동작 불가 상태 | 404 | `not_found` | 같은 JSON 오류로 찾을 수 없어요 |
| 요청 본문 ID가 없거나 다른 사람 소유·선택 불가 | 400 | `invalid` | 모두 같은 선택 불가 문구. 한 개라도 잘못되면 전체 저장 취소 |
| JSON 형식 오류 | 400 | `parse_error` | 개발 단계에서 요청 확인 |
| 지원하지 않는 방식 | 405 | `method_not_allowed` | 개발 단계에서 요청 방식 확인 |
| 금융 GET에 필요한 조회 동의 없음 | 403 | `consent_required` | 동의 안내, `fields` 생략 |
| 서버 내부 오류 | 500 | `server_error` | 잠시 후 다시 시도 안내 |

**결정기록 3-3 O:** 카드 후보·청구서·대출 GET은 저장된 자료만 읽고 CODEF를 호출하지 않는다. 해당 금융 조회 동의가 없으면 403 `consent_required`이며 `fields`는 생략한다. `provider_unavailable`(502)·`relogin_required`(409)는 추후 연결·재조회 API의 오류이며 이 GET의 외부 호출 오류로 넣지 않는다. `relogin` 상태에서도 저장된 마지막 자료를 조회한다. 조회 시각은 원래의 `fetchedAt`을 유지한다.

## 6. 카드 후보 보기

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 카드 선택 화면에서 조회된 카드와 현재 선택 상태를 보여줄 때 |
| 어디로 | `GET /api/finance/connect/cards/` |
| 로그인 필요 | O |
| 명세 상태 | 기본만: 모델·공통 표시 규칙에 근거한 응답 초안 |

**보내는 값**

요청 본문 없음. 본인 식별은 세션으로 한다. 저장된 카드 후보만 읽고 CODEF를 호출하지 않는다(O). 기관·연결별 쿼리 필터는 미정이다.

**받는 값 (200, 기본 응답 초안)**

| 이름 | 타입 | 뜻·범위 |
|---|---|---|
| `items` | 배열 | 본인의 카드 후보 목록. 연결 해제(`disconnected`)된 연결의 카드는 제외(M) |
| `items[].cardId` | UUID 문자열 | 선택 저장에 사용할 내부 카드 ID |
| `items[].displayName` | 문자열 | 공통 카드명·마스킹 번호. 카드명 없으면 “카드사 카드”, 카드사도 없으면 “카드”. 끝 4자리 없으면 ` · ****1234` 같은 번호 부분 전체를 생략(N⑨) |
| `items[].status` | 문자열 | 후보의 연결 상태: `connected`, `relogin`만 반환(M). 원천은 `connection.status` |
| `items[].cardType` | 문자열 또는 null | 저장된 카드 종류. 기관 값 정규화 기준은 미정 |
| `items[].cardStatus` | 문자열 또는 null | 기관이 제공한 카드 상태. 연결 상태와 구분 |
| `items[].isSelected` | 불리언 | 현재 관리 대상으로 저장된 선택 여부 |
| `items[].fetchedAt` | 시각 문자열 또는 null | 마지막 정상 조회 시각. 응답 생성 시각으로 대체하지 않음 |

```json
{
  "items": [
    {
      "cardId": "13cb7fb6-cff8-4c17-a76a-ea90f57ce330",
      "displayName": "신한 Deep Dream · ****4321",
      "status": "connected",
      "cardType": "체크",
      "cardStatus": "정상",
      "isSelected": true,
      "fetchedAt": "2026-10-21T09:30:00+09:00"
    }
  ]
}
```

정상 조회 결과 카드가 없는 경우의 예시:

```json
{ "items": [] }
```

화면은 선택 가능한 카드가 없다는 안내와 다음 단계로 진행할 선택지를 보여준다. 이 빈 목록은 해당 조회 범위에서 노출할 후보가 정상적으로 0건인 경우에 사용한다. 연결 해제된 카드만 남은 경우에도 후보에서 제외하므로 빈 목록이다(M). 카드사 인증·조회 실패나 일부 카드사의 미조회 결과를 빈 목록으로 바꾸지 않는다. 카드사를 선택했지만 보유 카드가 없는 경우의 진행 방식은 7번에 정리했다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 비로그인 | 403 | `not_authenticated` | 로그인 필요 |
| 서버 오류 | 500 | `server_error` | 조회 실패·재시도 |
| 조회 동의 없음 | 403 | `consent_required` | 동의 안내. `fields` 생략(O) |

## 7. 카드 선택 저장

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 카드 선택 화면에서 사용할 카드를 고르고 다음 단계로 갈 때 |
| 어디로 | `PUT /api/finance/connect/cards/` |
| 로그인 필요 | O, CSRF 검증 필요 |
| 명세 상태 | 기본만: 전체 선택 교체·빈 배열 허용은 결정기록 3-3 K로 확정. 나머지 세부 정책은 확인 목록 참조 |

**보내는 값**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `selectedCardIds` | UUID 문자열 배열 | O | 본인이 관리 대상으로 선택할 카드의 전체 ID 목록. 빈 배열 허용. 번호 원문·카드명을 보내지 않음 | 아래 예시 |

```json
{ "selectedCardIds": ["13cb7fb6-cff8-4c17-a76a-ea90f57ce330"] }
```

결정기록 3-3 K: **보낸 목록이 본인의 전체 카드 선택을 대체한다.** 목록에 있는 카드는 선택하고, 빠진 기존 선택 카드는 선택 해제한다. 특정 카드사·연결만 바꾸는 요청이 아니다. `selectedCardIds` 필드는 필수이며 생략은 전체 해제와 다르다. 중복 ID·최대 개수·동시 저장 세부 정책은 미정이다.

“카드는 나중에 연결”을 선택하면 아래처럼 빈 배열을 보내 카드 선택을 모두 해제한다. 카드 선택 해제는 금융기관 연결 해제나 과거 거래 삭제가 아니다. 해제한 카드를 사용하는 기존 고정지출과 그 결제 수단은 그대로 유지한다(N⑩).

```json
{ "selectedCardIds": [] }
```

**카드사를 선택했지만 해당 카드사의 보유 카드가 없는 경우 — 화면 처리 초안**

카드사 선택은 조회할 기관을 고르는 단계이고, 이 API는 조회된 실제 카드 ID를 저장하는 단계이다. 보유하지 않은 카드사를 앞 단계에서 골랐다고 가짜 카드 ID를 만들거나 카드사 이름을 `selectedCardIds`에 넣지 않는다.

| 조회 결과·사용자 행동 | 화면·저장 처리 |
|---|---|
| 정상 조회 결과 해당 카드사에 보유 카드가 없음 | “선택한 카드사에서 조회된 카드가 없어요.” 안내. 카드사 다시 선택 또는 카드 연결 건너뛰기 제공 |
| 모든 조회가 완료됐고 선택할 카드가 하나도 없으며 사용자가 “카드는 나중에 연결”을 선택 | `selectedCardIds: []`로 PUT을 보내 전체 선택을 해제하고, 저장 성공 후 다음 단계로 진행(K) |
| 다른 카드사에는 선택 가능한 카드가 있음 | 해당 카드들을 계속 선택할 수 있게 함. 보유 카드가 없는 카드사 때문에 다른 카드의 선택을 초기화하지 않음 |
| 인증 실패·조회 실패·일부 기관 미조회 | 보유 카드 없음과 구분해 실패·재시도 안내. 실패 결과로 기존 선택을 덮어쓰지 않음 |
| 클라이언트가 없는 카드 ID를 넣어 저장 요청 | 서버가 400 `invalid`와 동일한 선택 불가 문구로 거절하고 전체 미저장 |

이 처리안은 카드 선택 단계의 동작이다. 기관 연결 해제를 자동 실행하지 않으며, 카드사별 조회 결과를 구분할 응답 구조와 최종 화면 연결은 마지막 확인 목록에서 혜리와 맞춘다.

**받는 값 (200, 확정 구조)**

선택 저장 결과는 6번 후보 목록과 같은 `items` 구조로 반환한다(취합 명세의 확정 응답). 후보에는 변경된 `isSelected`를 반영하고 연결 해제 카드는 제외한다. 빈 배열로 저장해도 후보가 있으면 그 목록의 `isSelected`가 모두 false이며, 후보가 0건일 때만 `items: []`다.

```json
{
  "items": [
    {
      "cardId": "13cb7fb6-cff8-4c17-a76a-ea90f57ce330",
      "displayName": "신한 Deep Dream · ****4321",
      "status": "connected",
      "cardType": "체크",
      "cardStatus": "정상",
      "isSelected": true,
      "fetchedAt": "2026-10-21T09:30:00+09:00"
    }
  ]
}
```

같은 선택을 다시 저장해도 중복 기록이나 중복 차감을 만들지 않고 성공으로 처리한다. 선택 저장 시각을 금융정보의 `fetchedAt`으로 기록하지 않는다. 카드 선택만으로 예산·고정비·기존 거래를 다시 계산하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| `selectedCardIds` 누락·ID 배열이 아닌 값·UUID 형식 오류 | 400 | `invalid` | `fields.selectedCardIds` 표시. 빈 배열 자체는 허용 |
| 없는 카드·남의 카드·선택 불가 카드 포함 | 400 | `invalid` | 모두 같은 선택 불가 안내, 전체 미저장 |
| 비로그인·CSRF 오류 | 403 | 공통 규칙 | 로그인 또는 재시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "입력값을 확인해 주세요.",
    "fields": { "selectedCardIds": ["선택할 수 없는 카드예요."] }
  }
}
```

### 청구 상세와 상태 — 결정기록 3-3 Z 채택

`confirmationStatus`·`scopeType`·`items`·`itemsState`와 기존 제안의 상태 코드는 Z로 채택됐다. CODEF가 제공하지 않아 저장 근거가 없는 값은 null이다. `unknown`·`unavailable`은 해당 상태가 저장된 경우의 코드이며, 값 자체가 없을 때 임의로 채우지 않는다. `items: []`는 항목 없음이 정상 확인된 경우에만 사용한다.

원천에서 제공되는 실제 값과 상세 항목 매핑은 검증이 필요하다. `cards`와 청구서 전체 `fetchedAt`은 AA로 채택됐다. DB는 `card_bill.fetched_at`(10/24 `finance/0008`에서 추가)에 저장하고, 범위 · 확정 상태 · 상세 항목 상태는 `scope_type` · `confirmation_state` · `items_state`(모두 비울 수 있음)에 저장한다. 상세 항목의 가장 최근 시각을 청구 총액 조회 시각으로 대신 쓰지 않는다.

| 이름 (`items[]` 안, 응답 필드 제안) | 타입 | 뜻·근거 |
|---|---|---|
| `billItemId` | UUID 문자열 | 내부 청구 항목 ID |
| `itemType` | 문자열 | 기존 `CardBillItem.ItemType`의 `one_time`, `installment`, `fee`, `interest`, `adjustment`, `unknown` 사용. CODEF 원천값 대응은 검증 대기 |
| `merchantName` | 문자열 또는 null | 가맹점·항목명 |
| `card` | 객체 또는 null | 해당 항목의 카드 공통 표시 객체. 알 수 없으면 null |
| `purchasedOn` | 날짜 문자열 또는 null | 원 구매일. 청구일로 대신 채우지 않음 |
| `originalPurchaseAmount` | 정수 또는 null | 전체 구매 금액, 원 |
| `billedAmount` | 정수 또는 null | 이번 회차 청구액, 원. 미제공 null과 확인된 0원 구분 |
| `installmentMonths`, `installmentRound` | 정수 또는 null | 할부 총회차·이번 회차. 확인된 할부는 1 이상, 이번 회차는 총회차 이하. 일시불·회차 미확인은 null 제안 |
| `fetchedAt` | 시각 문자열 또는 null | 해당 항목의 마지막 정상 조회 시각. 모델 `CardBillItem.fetched_at` 대응 후보 |

`issuerCode`는 형식 설명용 예시이며 특정 카드사와의 실제 매핑을 보증하지 않는다. 결제 계좌를 알 수 없으면 객체 전체가 null이다. 청구서 자체가 없으면 404이며, 금액 0원인 가짜 청구서를 만들지 않는다.

예시 검산: 일시불 360,000원 + 이번 회차 할부 60,000원 = 총청구액 420,000원. 할부 원 구매액 180,000원을 다시 더하지 않는다. `scopeType: issuer`이면 카드가 한 장이어도 카드사 통합 청구서다. 단일 카드 청구(`card`)에서는 `card`와 `cards`의 한 항목이 같은 카드를 가리키도록 하는 제안이다. 카드사 통합 청구에서는 `card: null`을 사용하고 실제 포함 카드는 `cards`로 표시한다. 카드 예시는 6번의 체크카드 예시와 별개의 가상 상황이다.

**총액만 확보되고 범위·확정 상태·상세는 미제공인 경우 — 응답 필드 발췌(Z)**

이 경우 “조회 금액 420,000원 · 확정 여부 및 상세 항목 확인 필요”로 안내하는 제안이다. 일부 항목만 있으면 `itemsState: partial`과 확보한 항목만 보내며, 항목 합계를 총청구액으로 대체하지 않는다. 전체 항목과 모든 `billedAmount`가 확인된 경우에만 총액과 대조한다. 차이가 있으면 임의의 조정 항목을 만들어 맞추지 않고 자료 불일치를 안내할 계약을 합의한다. `estimated`·`unknown`을 확정 납부액으로 표시하지 않는다. GET은 마지막 저장 자료를 읽는 API이며 실시간 외부 조회 성공을 뜻하지 않는다(O). 기존 조회 시각을 유지하고, 조회 동의가 없으면 403 `consent_required`다.

시각 저장 원천·상세 누락과 불일치 안내 등 남은 확인 사항은 마지막 목록에 정리했다. 위 제외 항목은 서비스 범위에서 삭제한다는 뜻이 아니며, 화면에서는 자료 확인 전 숨길지 “확인 필요”로 표시할지 합의한다.

**첫 청구서·고정지출 연동 — 확정된 원칙**

- 첫 카드 청구서만 예산에서 먼저 차감한다. 이후 청구서 납부는 카드 사용 때 이미 반영한 지출과 연결하며 다시 차감하지 않는다(TXN-009).
- 카드 고정지출은 청구서에 포함되므로 별도 고정지출 납부 예정을 만들지 않는다. 첫 청구서와 이번 회차 할부금에도 같은 비용을 두 번 넣지 않는다.
- 카드 청구서의 납부 예정도 출금일을 확인할 수 있어야 생성한다(출금 예정일, 없으면 결제 예정일 — 11/5). 둘 다 없으면 “출금일 확인 필요”로 안내한다.
- **C-17 확정(Q): 미리 뗄 돈 = `max(0, 첫 청구서 총액 − 이번 급여주기 시작 뒤 그 카드로 쓴 돈)`**. 예: 첫 청구서 420,000원, 이번 주기 카드 사용 120,000원이면 선차감은 300,000원. 차이가 음수이면 0원이다. 이전의 “구매일이 주기 시작 전인 항목만 합산” 제안을 대체한다. **10/29부터 카드사 단위로 계산한다(아래 '미리 뗄 돈').**
- **C-17 고정지출 보정 (11/4)**: `PaymentMatch` 없이 `evidence`로 연결된 카드 고정지출도 같은 판정으로 선차감에 반영한다. 연결 금액은 이번 주기 카드 사용액에서 되돌리고 고정지출은 실제 결제 카드에서 한 번만 뺀다. 첫 청구서 300,000원·일반 소비 50,000원·고정지출 12,000원이면 정기결제 연결 전후 모두 238,000원이다. 전액 취소 거래는 실제 납부 카드 판단에서 제외하고, 부분 취소는 잔액이 있으면 유지한다.
- **첫 청구서 기준 변경 (11/06, 아래 10/29 기준을 대체)**: 선차감 대상은 '카드 연결일 이후 첫 청구서'가 아니라 **최초 예산 적용 주기에 결제일(출금 예정일, 없으면 결제 예정일)이 `[starts_on, ends_before)` 안인 카드사 통합 사용 명세서 전부**다. 결제일이 연결일보다 앞서도 포함하고(예: 주기 10/10~11/10, 결제 11/5, 연결 11/6 → 11/5 청구서), 주기 밖 과거 · 미래 청구서는 가져오지 않는다. 정정으로 대체된 예전 청구서는 뺀다. 날짜별 카드론 제외 · 명세서 종류 · 범위 · 금액 검증은 그대로.
  - **최초 적용 주기**(`budgets.protect.first_budget_cycle`): 그 카드사 카드 중 가장 먼저 연결된 시각 이후 **승인된 예산(approved_at)** 이 이번 주기보다 앞선 주기에 없으면 이번 주기가 최초다. 있으면 그 주기에 이미 반영했으므로 0원(`cardNotes: first_budget_applied`) — 저장된 승인 기록으로만 판단해 조회할 때마다 바뀌지 않는다. 초안 · 연결 전에 승인한 예산은 세지 않는다. 같은 주기의 재승인(수정)은 계속 최초 주기다. 나중에 새 카드사를 연결하면 그 연결 뒤 첫 승인 예산 주기가 그 카드사의 최초 주기다.
  - 예: 10/10~11/10 주기에 11/6 연결 · 11/5 청구 511,515원 → 이 주기에 예산을 승인하면 11/5 청구서로 선차감, 다음 주기(11/10~)는 0원. 이 주기에 승인하지 않고 11/12(다음 주기)에 처음 예산을 만들면 그 주기에 결제일인 12/5 청구서가 대상.
  - 청구서 조회 기록은 주기 시작일부터 이어져야 한다(`bill_history_incomplete`). 이번 주기 청구서가 없을 때: 주기 마지막 날까지 조회됐으면 정상 빈 조회 = 0원(`cardNotes: no_bill_in_cycle`), 아직 오지 않은 기간이 남았으면 `first_bill_unavailable`로 보류(조회 실패가 아니라 '아직 못 찾음'으로 안내).
  - **금액 (11/06 보완, 위 식을 대체)**: `max(0, 대상 청구액 합 − 이번 주기 전에 낸 금액 − 확인된 중복) + 할부 회차` (`finance/card_deduction.cycle_overlap` · `prepaid_before`).
    - **예산 반영액 ≠ 납부 잔액**: 반영액은 이번 월급에서 이 카드 청구 의무에 배정할 돈이라 '앞으로 낼 금액'으로 줄이지 않는다(이번 월급으로 이미 낸 카드값도 이번 예산에서 쓴 돈). 홈 '꼭 나갈 돈' · 납부 확인 화면은 지금처럼 남은 금액을 쓴다. 그래서 납부 확인 여부로 예산 계산을 보류하지 않는다. 연결된 출금 근거상 **이번 주기 시작 전에** 낸 금액(이전 월급)만 뺀다 — 사용자 확인은 낸 날짜가 없어 빼지 않는다.
    - **확인된 중복만 뺀다**: 청구서 상세 중 구매일이 이번 주기 시작 ~ 거래를 불러온 날인 일시불 · 할부 항목을, 같은 카드사 카드 승인 거래와 구매일 · 원 구매 금액으로 맞춘다. 같은 날 · 같은 금액 묶음의 항목 수와 거래 수가 같을 때만 짝으로 보고(가맹점명은 표기가 달라 쓰지 않음), 그 거래가 이번 주기 예산에 잡혀 있으면(관리 카드 소비, 또는 고정지출 근거로 연결된 결제 — 결제 카드와 상관없이 고정비에 있음) 그 항목의 이번 회차 청구액(취소가 있으면 거래 순액까지)만 뺀다. 이번 주기 카드 소비 전체 · 카드 고정비 합계를 일괄로 빼지 않는다. 주기 전 구매 · 수수료 · 이자 · 조정 항목은 빼지 않는다. 할부는 그 회차만.
    - **확인 못 한 중복**(짝 후보가 여럿 · 짝 없음 · 구매일이나 종류 모름)은 빼지 않고(넉넉하게) `cardNotes: card_overlap_uncertain`(건수 · 금액)으로 알린다. 상세가 일부만 왔으면 빠진 항목은 알 수 없어 `bill_items_incomplete`(건수 · 금액 null)만 알린다. 둘 다 보류하지 않고 재조회 · 카드 인증을 요구하지 않는다. 자료가 보완되면 다음 계산에서 중복을 뺀다.
    - **청구 총액 불일치**: 상세의 이번 회차 금액이 모두 있는데 합계가 총액보다 크면(예: 결제일 당일 조회 총액 0원 · 상세 합계 511,515원) 원래 청구액을 알 수 없어 `bill_total_mismatch`로 보류한다. 0원 · 상세 합계로 정하지 않고 총액을 덮어쓰지 않는다. 화면 '낼 금액 없음'으로도 보지 않는다(`CardBillCheckStatus.status: total_mismatch`). 원래 청구액 확인 방식은 별도 결정.
    - 최초 주기엔 대상 청구서 안 할부가 총액에 있으므로 회차를 더하지 않고, 뒤 주기는 기존 할부 회차 규칙만 적용한다.
  - 초안 일관성 (11/06 보완): 선차감이 이제 카드를 쓴다고 바뀌지 않으므로, 승인 때 다시 계산해 초안에 저장한 값과 다르거나 지금 보류면 초안을 만료한다(청구 정정 · 상세 보완 · 계산 규칙 변경). 납부 확인은 반영액을 바꾸지 않아 초안을 만료하지 않는다. 승인된 예산은 다시 계산하지 않는다.
  - 지킬 돈 화면: 보류 이유별로 결제 카드 선택(`card_assignment_required`) · 재조회(`bill_history_incomplete` · `spending_history_incomplete` · `installment_amount_unknown`) · 아직 못 찾음(`first_bill_unavailable`) · 자료 이상(그 밖)을 나눠 보여 준다. 카드번호 · 비밀번호 재입력은 재조회가 필요할 때만.
- **(대체됨) 첫 청구서 기준(10/29 나은 결정, 카드사 단위)**: CODEF 청구서가 명세서 단위 카드사 통합(`issuer`)이라 **카드사마다 한 번**, 그 카드사 카드 중 **가장 먼저 연결된 날**(`first_connected_at`의 최솟값) 이후 처음 납부할 청구서다. 과거 조회 자료 중 가장 오래된 청구서나 매 급여 주기의 첫 청구서가 아니다. 재연결·관리 대상 재선택으로 다시 시작하지 않고, **나중에 관리 대상으로 추가로 고른 카드도 첫 청구서를 새로 만들지 않는다**(첫 청구서는 카드사에 한 번뿐).
- **미리 뗄 돈 (10/29 카드사 단위)** = `max(0, 카드사 첫 청구서 총액 − 그 카드사 관리 대상 카드로 이번 주기에 쓴 돈 − 그 카드사 카드 고정지출)`. 관리 대상이 아닌 카드 몫은 따로 골라내지 않고 첫 청구서에서 같이 뗀다(그 카드로 쓴 돈을 빼지 않음). 카드 고정지출은 관리 대상이 아닌 카드로 내는 것도 뺀다(첫 청구서에 들어 있고 고정비 P-04에도 이미 있어서).
- **이번 회차 할부금 (11/04 [임시])** = 이번 급여 주기에 내는 청구서(첫 청구서 · 카드론 명세서 제외)의 할부 항목 `billedAmount` 중 **예산에 아직 안 잡힌 구매**의 합. 미리 뗄 돈에 더한다. 할부는 긁을 때 전액이 소비로 잡히므로, 이번 주기나 최초 연결 뒤 승인 예산이 있던 주기에 산 것은 뺀다. 최초 연결 전 구매, 연결 뒤 첫 예산 주기 전 구매, 구매일을 모르는 할부는 포함한다. 대상 청구서의 `itemsState`가 `complete`가 아니거나 회차 금액을 모르면 보류(`installment_amount_unknown`)하고 0원으로 치지 않는다. 아직 안 온 청구서는 0원이다.
- **같은 날 내는 청구서 구분(10/29 리뷰 반영)**: 이름에 `카드론`·`장기카드대출`이 있는 명세서는 장수와 관계없이 빼고, 그날 카드론 명세서뿐이면 건너뛰고 다음 날짜를 본다(카드론을 대출로 등록하면 고정지출과 이중 반영되므로). 해당 납부일의 명세서가 **한 장이고 카드론이 아니면 `resBillType` 값과 무관하게** 사용 명세서로 처리한다. 빈 값·숫자 코드(`0`, `1` 등)도 포함한다. **두 장 이상이면** 이름에 `카드론`·`장기카드대출`이 있는 명세서는 빼고, `이용`·`사용`이 있는 명세서는 합친다. 숫자 코드의 의미는 추정하지 않으며 해석 불가 값은 보류(`bill_type_unknown`), 빈 값이 섞이면 보류(`first_bill_ambiguous`)한다. 여러 장이 모두 카드론이면 그날을 건너뛰고 다음 날짜를 본다.

- **청구서 → 납부 예정 (R04, 11/5, `finance/card_payments.py` `sync_bill_dues`)** — 출금 전에도 홈 '꼭 나갈 돈'에 보이게 한다.
    - 언제: 카드 다시 불러오기에서 청구서를 저장한 뒤(같은 저장 트랜잭션 · 회원 잠금 안, 새 승인 거래가 없어도)와 홈을 열 때. 저장된 청구서만 읽고 외부 조회는 하지 않는다. 이어서 이미 받은 카드값 출금을 다시 맞춘다.
    - 채택: 출금 매칭 · 선차감과 같다. 카드사 통합(`issuer`) 청구서를 납부일별로 묶어 카드론 명세서는 빼고, 한 장이면 구분값과 무관하게, 여러 장이면 사용 명세서만 쓴다. 판단 못 하면(`bill_type_unknown` · `first_bill_ambiguous`) 만들지 않는다. **청구서 한 장 = 납부 예정 하나**(카드별로 나누지 않음, `occurrence_key = card_bill:<billId>`). 0원 · 음수 청구서는 만들지 않는다.
    - 범위: 새로 만드는 건 납부일이 홈의 조회 범위 시작일(지난 급여 주기 시작일) 이후인 청구서만. 급여일이 없으면 만들지 않고, 급여일을 정한 뒤 홈을 열면 만든다.
    - 고치기: 이미 있는 예정은 ID · 납부 연결(`PaymentMatch`)을 두고 금액 · 날짜 · 확인 상태를 저장된 청구서로 맞춘다. 납부 연결이 있으면 기존 계산(90% 이상 `paid` · 일부 `partial`), 없으면 홈과 같게 출금일 +3일까지 `unpaid`, 그 뒤 `needs_review`. 더 늦게 시작한 조회의 값은 청구서 저장에서 덮지 않으므로 오래된 응답이 예정을 되돌리지 않는다.
    - 취소: 정정으로 **0원 이하**가 된 청구서의 예정은 납부 기록이 있어도 취소(`obligation_state: canceled`)한다 — 이미 낸 기록(`PaymentMatch`)은 남기고, 예전 청구액을 낼 돈으로 보이지 않는다. 더는 채택되지 않는(판단 보류) 청구서는 납부 기록이 없을 때만 취소한다. 다시 청구되면 같은 예정을 되살린다. 납부 기록은 지우지 않는다. 이번 응답에 없다는 이유만으로는 취소하지 않는다.
    - **날짜 미제공 정정 (PR #93)**: 정정 청구서에 결제·출금 예정일이 모두 없으면 금액이 0원인지 양수인지와 관계없이 기존 예정을 취소한다. 이전 날짜·금액은 취소된 예정의 이력으로만 보존하고 홈 `mustPay`에는 표시하지 않는다. 청구서의 최신 금액과 기존 납부 연결·납부액은 보존하며 납부 완료로 간주하지 않는다. 날짜가 다시 제공되면 같은 예정 ID·납부 연결로 최신 금액·날짜를 반영한다. 처음부터 날짜가 없는 청구서는 예정을 새로 만들지 않는다.
    - **결제일 정정 (R04 보완)**: CODEF 청구서엔 고유 번호가 없어 결제일이 명세서 키에 들어가므로, 날짜가 바뀌면 새 청구서 행이 생긴다. 날짜가 가깝다고 합치지 않고, 같은 카드사 · 청구 월 · 명세서 구분에서 **그 달 마지막 조회 응답에 예정이 있던 예전 청구서는 없고 새 청구서 하나만 있으며 새 청구서에 아직 예정이 없을 때만** 정정으로 보고 **같은 납부 예정(ID · 납부 기록 그대로)을 새 청구서로 옮긴다**. 중복 방지 키(`occurrence_key = card_bill:<billId>`)도 옮긴 청구서 기준으로 바꿔서, 예전 청구서가 나중에 다시 와도 키가 겹치지 않는다. 응답에 있었는지는 청구서를 저장한 조회의 시작 시각으로 판단한다. 대체된 예전 청구서에는 예정을 다시 만들지 않고 출금도 붙이지 않는다(청구서 행은 지우지 않음). 두 청구서가 한 응답에 같이 온 적이 있거나(그때 각자 예정이 생김) 새 후보가 여럿이면 정정 여부가 불확실해서 옮기지 않고 둘 다 남긴다. 정정이 되돌려지면 같은 규칙으로 다시 옮겨 온다.
    - 결제 계좌: 청구서 계좌, 없으면 그 카드사 카드의 결제 계좌가 하나로 정해질 때만. 모르면 비우고, 실제 출금을 찾으면 그 출금 계좌를 채운다.
    - 분할 · 선결제: 출금은 청구 총액과 **정확히 같을 때만** 잇는다(분할 납부 탐지 없음). 결제일 전에 일부만 내면 카드사가 다음 조회에서 총액을 낮춰 줄 때만 줄어든 금액이 보이고, 총액이 그대로면 전액이 계속 보인다.
    - 예전에 저장한 청구서: 홈을 열거나 카드를 다시 불러오면 위 범위 안의 것은 채워진다. 범위 밖(지난 주기 전) 청구서는 만들지 않는다.

## 11/05 추가: 결제 카드 확인이 필요한 거래

금액·취소 정보는 정상이나 보유 카드가 0개 또는 여러 개 매칭된 승인만 별도 보관한다. 카드명 일치는 후보 안내에만 쓰고 자동 연결하지 않는다. 원문 카드번호는 저장·응답하지 않는다.

### GET /api/finance/card-reviews/

로그인·카드 조회 동의 필요. 외부 조회 없이 연결 중(connected/relogin) 카드사의 본인 미확인 거래를 `{items: [...]}`로 반환한다. 각 항목:

- `reviewId`, `issuerCode`, `issuerName`, `occurredOn`, `occurredTime`, `merchantName`, `amount`, `isCanceled`, `canceledAmount`, `fetchedAt`
- `canResolve`: 최신 조회에서도 금액·취소 정보가 정상인지. false면 이전 정상 금액이 표시되더라도 재조회 안내만 제공한다.
- `candidates`: 같은 회원·카드사·연결 중인 provider 카드의 `cardId`, `displayName`, `status`, `isSelected`, `nameMatches`. 미선택 카드도 실제 결제 카드로 지정할 수 있으며 예산 관리 대상으로 자동 선택하지 않는다.

### PUT /api/finance/card-reviews/<id>/

본문은 `{"cardId": "UUID"}`만 허용한다. 회원 잠금 안에서 동의·소유권·같은 카드사·연결 상태·최신 금액 상태를 재검증한다.

성공: `{reviewId, cardId, transactionId, status: "resolved"}`. 같은 카드로 재전송하면 같은 거래 ID를 반환한다(별도 Idempotency-Key 불필요). 다른 카드로 이미 확정한 거래, 같은 승인의 기존 거래가 여러 개인 경우, 다른 확인 요청에 이미 연결된 거래는 409 `card_review_conflict`이며 저장을 롤백한다. 잘못된 본문 카드 ID는 400 `invalid`, 남의 review·없는 review는 404, 동의 없음은 403이다.

해당 승인 한 건만 확인한다. 같은 회원·카드사의 과거 카드를 포함해 승인 식별 키가 같은 기존 거래를 찾고, 하나로 특정되면 기존 거래 ID·카드·소비 분류를 보존하며 취소 상태만 갱신한다. 사용자가 선택한 카드는 확인 요청의 `resolved_card`에 기록한다. 기존 거래가 없을 때만 선택한 카드로 새 거래를 만들고 기존 분류 파이프라인을 실행한다. 카드 확인과 소비 카테고리 확인은 별개다. 동일한 미매칭 카드번호의 다른 거래에는 확인 결과를 전파하지 않는다.

원천 카드번호와 승인 식별 정보의 해시로 요청을 찾는다. 번호 표기가 바뀌면 승인번호·일시·가맹점·원천 금액·할부·통화 속성을 함께 비교한다. 승인번호가 있고 이번 응답과 기존 확인 요청에서 각각 하나로 특정되는 경우에만 기존 요청 ID와 조회 범위 연결을 유지한 채 조회 키·정상 여부·거래의 취소 상태를 갱신한다. 정상 금액으로 다시 조회되면 이전 `data_valid=false`도 해소한다. 같은 속성의 전표가 여러 개이거나 승인번호가 없으면 표기가 다른 요청을 자동으로 합치지 않는다.

조회별 실제 coveredFrom/coveredTo, 카드 목록, 미확인 거래 목록, 기타 금액 오류 여부를 보존한다. 모든 관련 거래가 실제 금융 거래로 반영되고 기타 오류가 없는 조회만 `card_approval_list/success`를 생성한다. 요청 기간으로 실제 조회 기간을 늘리지 않는다. 최신 조회에 금액 오류 또는 미확인 거래가 있으면 과거 성공 기록이 있어도 예산 계산을 보류한다. 승인된 예산을 자동 변경하지 않는다.

화면: 연결 관리의 `결제 카드를 확인할 거래 N건` → `/finance/card-reviews`. 지킬 돈의 `cardPending[].reason = card_assignment_required`는 화면 안에서 같은 확인 목록을 펼친다. 확인 후 지킬 돈 API를 다시 조회해 청구서·조회 기간 등 남은 조건을 검증한다.

기존에 건너뛴 거래는 마이그레이션만으로 복원하지 않는다. 업데이트 후 카드 내역을 한 번 다시 불러와야 확인 목록이 만들어진다. 금액·취소액 불명확 거래는 이번 수동 확인 범위에서 제외한다.

## 11/06 추가: 카드 청구서 납부 확인 (첫 예산: 앞으로 얼마를 더 내야 하나)

CODEF 현대카드 개인 청구내역에는 이번 청구서의 납부 완료 상태가 없고 기출금액(`resPreWithdrawal`)도 주지 않는다. `resAmountOutstanding`은 **전월 미결제금액**이라 이번 청구서의 미납액으로 쓰지 않는다. 그래서 첫 예산에 필요한 "이 청구액 중 앞으로 얼마를 더 내야 하나요?"는 계좌 출금으로 자동 확인하고, 못 찾으면 사용자에게 간단히 묻는다. 출금 거래를 골라 연결하는 것은 기본 흐름이 아니다(아래 '거래로 확인하기').

| 주소 | 하는 일 |
|------|---------|
| `PUT /api/finance/card-bills/<id>/payment-check/` | `{ answer: unpaid\|paid\|partial\|later, remainingAmount? }` 저장 → 확인 상태 |
| `DELETE` 같은 주소 | 사용자 확인 취소 (출금 근거는 그대로) |

- 확인 상태(`CardBillCheckStatus`, `finance/card_payments.bill_status`)는 고정지출 목록 `cardBills[].bills[]` · 청구서 상세 `paymentCheck`에 같은 모양으로 나온다.
  - `paid_by_transactions`: 연결된 계좌 출금이 청구액 이상 → 앞으로 0원. 다시 묻지 않는다(화면은 결과와 [수정]만).
  - `user_confirmed`: 사용자 확인. 아직 안 냈어요 = 청구액, 전부 냈어요 = 0원, 일부 냈어요 = 입력 금액(1원 ~ 청구액 −1원). 화면에 '사용자 확인'으로 표시한다.
  - `recheck`: 확인 뒤 청구액이 바뀜(`bill_changed`), 확인한 남은 금액이 출금 기록으로 본 남은 금액보다 큼(`transactions_conflict`), 연결 출금 취소 → 조용히 덮지 않고 다시 묻는다. 확인 기록은 지우지 않는다.
  - `unchecked`: 확인 없음 · 나중에 확인. `remainingAmount: null` — 0원도 확정 미납액도 아니다. `no_charge`: 청구액 0원 이하.
  - `needsCheck`: 결제일이 지났는데 앞으로 낼 금액을 모름(또는 재확인). 결제일 전이면 묻지 않고 청구액을 낼 예정으로 본다.
- 저장: 청구서 `field_states.userPaymentCheck = { answer, remaining_amount, bill_total, confirmed_at }`. 가짜 출금 · PaymentMatch를 만들지 않고 청구 총액을 바꾸지 않는다. 재조회(`_save_bills`)는 이 키를 지우지 않는다(같은 행 잠금). 결제일 정정으로 새 청구서 행이 생기면 그 청구서는 확인 전으로 다시 묻는다.
- 사용자 확인값과 출금 연결액은 더하지 않는다: 출금이 청구액 이상이면 출금 근거, 아니면 사용자 확인값만 쓴다.
- **(11/06 보완으로 대체 — 위 '금액' 참고)** 예전 첫 예산 연동: `budgets/protect.issuer_deduction`의 첫 청구서 선차감 = `min(기존 계산, 앞으로 낼 금액) + 할부 회차`. 기존 계산(`청구 총액 − (이번 주기 카드 사용 − 고정지출에 연결된 사용) − 카드 고정비`)은 그대로이고, 앞으로 낼 금액에서 고정비 · 사용액을 다시 빼지 않는다. 결제일이 지났는데 모르면 `card_payment_unconfirmed`, 재확인이면 `card_payment_recheck`로 보류(지킬 돈 화면에서 같은 질문). 승인된 예산은 다시 계산하지 않는다(초안 · 승인은 기존 `input_snapshot` 규칙). 첫 청구서 판정(카드사별 첫 연결 뒤 첫 사용 명세서)은 기존 그대로라 나중에 새 카드사를 연결해도 같은 규칙이 적용된다.
- 홈 '꼭 나갈 돈': 카드 청구서를 '전부 냈어요'로 확인하면 빠지고, '일부'면 그 금액(`userChecked: true`). 카드 청구서는 출금을 못 찾아도 '미납'이 아니라 '납부 확인 필요'로 표시한다. 매달 온보딩 질문을 반복하지 않고, 못 찾을 때만 홈 청구서 상세에서 선택적으로 답한다.

## 11/06 추가: 거래로 확인하기 (카드 청구서 납부 거래 연결 · 분할 납부, 보조 경로)

`finance/api_card_payments.py` · 자동 연결은 `finance/card_payments.py`. 저장된 거래만 보고 CODEF를 부르지 않는다.

| 주소 | 하는 일 |
|------|---------|
| `GET /api/finance/card-bills/<id>/payments/?from=&to=` | 청구서 납부 현황 + 연결한 출금(`linked`) + 고를 수 있는 내 계좌 출금(`items`, 기본 결제일 35일 전 ~ 7일 뒤, 최대 92일) |
| `POST /api/finance/card-bills/<id>/payments/` | `{ transactionIds: [...], confirmReclassify? }` 여러 건을 한 번에 연결 (`Idempotency-Key` 선택) |
| `DELETE /api/finance/card-bills/<id>/payments/<transactionId>/` | 연결 취소. 본문 없음 |

- `<id>` = 본인의 카드사 통합 청구서(`scopeType: issuer`). 없음 · 남의 것 · 카드별 명세서는 404. 카드 동의가 없으면 403 `consent_required`.
- **청구와 납부는 따로 둔다**: 청구 총액(`totalAmount`)은 줄이지 않는다. `paidAmount` = 연결한 출금의 유효한 합(취소된 출금 제외), `remainingAmount = max(0, totalAmount − paidAmount)`. 청구액보다 많이 내도 납부 기록(`matchedAmount`)을 자르지 않는다.
- **상태는 금액으로만** (대출의 '다 냈어요' · 공통 90% 규칙을 쓰지 않음): 청구액 이상 `paid`, 일부 `partial`, 연결 없음 + 결제일 +3일 전 `unpaid`, 그 뒤 또는 연결한 출금이 취소되면 `needs_review`.
- 후보에서 빼는 거래 · 다른 납부에 붙은 거래(409 `not_ready`, 옮기지 않음) · 분류 변경 확인(`confirmReclassify`, 소비나 사용자 확정 분류를 카드값으로 바꿀 때)은 대출 납부 확인(loans.md 12)과 같다. 하나라도 고를 수 없으면 아무것도 저장하지 않는다.
- 연결하면 거래는 `card_payment`(사용자 확인)가 된다. 연결 기록(`field_states.card_bill_payment`)에 바꾸기 전 분류를 남겨, 취소할 때 그 뒤 바뀌지 않았으면 되돌린다(`restored`, 아니면 `kept`). 취소한 출금은 그 청구서에 자동으로 다시 붙지 않는다(`skip_auto_match`에 `card_due:<납부 예정 ID>` — 결제일 정정으로 예정이 새 청구서로 옮겨 가도 남는다). 사용자가 다시 연결하면 풀린다.
- 청구서에 출금 · 결제 예정일이 둘 다 없으면 조회는 200으로 `paymentState: needs_review`, `reviewReason: due_date_unknown`('결제일 확인 필요')을 주고 후보(`items`)는 주지 않는다. 새 연결은 409, 이미 있는 연결의 확인 · 취소는 된다. 그 밖의 `reviewReason`: `payment_not_found` · `payment_canceled`, 확인 필요가 아니면 `null`.
- 한 출금이 같은 날 명세서 여러 장에 나뉘어 연결된 경우(자동 연결), 분류 기록은 거래에 하나다. 한 청구서 연결만 풀면 남은 연결이 있으므로 분류는 카드값 그대로(`kept`)이고, 마지막 연결을 풀 때 원래 분류로 되돌린다(`restored`). 취소 순서와 상관없이 결과가 같다.
- 새 출금을 붙일 수 없는 청구서(`bill.canLink: false` — 0원 · 정정으로 대체됨 · 같은 날 명세서 판단 보류 · 취소된 예정)에 POST하면 409 `not_ready`. 연결 취소는 된다.
- 잠금 순서: 회원 → 납부 예정 → 거래. 같은 출금을 두 청구서에 동시에 연결하면 한쪽만 성공한다.

### 자동 연결 조건 (`card_payments.match`)

출금 **한 건씩** 본다. 여러 출금을 조합해 합계를 맞춰 보지 않는다. 모두 맞을 때만 자동 연결:

1. 은행 출금 · 취소 아님 · 아직 어떤 납부에도 안 붙음. 유형이 `card_payment`이거나 적요에 카드사 이름이 있어 **카드값 후보**(`field_states.card_payment_candidate`)로 표시된 `transfer`. 두 유형 모두 `confirmation_state`가 `needs_review` 또는 `suggested`여야 하며 사용자 확정 거래는 제외한다
2. 적요의 카드사 = 청구서 카드사, 출금일이 청구서 출금일(없으면 결제일) ±3일
3. 결제 계좌를 알면(청구서 → 그 카드사 카드) 그 계좌에서 나간 출금
4. 출금액 = 같은 날 명세서 묶음의 **남은 금액**과 정확히 같다 (처음엔 청구액, 일부 납부 뒤엔 나머지)
5. 맞는 청구서 묶음이 하나뿐이고, 그 묶음에 맞는 출금도 하나뿐 (같은 금액 출금이 둘이면 먼저 온 것을 고르지 않는다)
6. 사용자가 그 청구서에서 연결을 푼 출금이 아님

홈 조회·새 거래 처리 모두 실제 연결 전에 **후보 거래 행을 잠근 뒤** 유형·확정 상태·기존 납부 연결을 다시 조회하고 금액·계좌·적요·연결 해제 표시도 최신 값으로 검증한다. 후보를 읽은 뒤 사용자 분류 PATCH가 먼저 확정되면 자동 연결에서 제외한다.

그래서 30만 + 20만 분할 납부는 자동으로 붙지 않는다(어느 쪽도 남은 50만 원과 같지 않음). 사용자가 30만을 연결하면 남은 20만과 같은 출금은 다음 처리에서 자동으로 붙는다. 선결제처럼 ±3일 밖이거나 금액이 다른 출금은 사용자가 고른다.

### R11 (11/06): 카드사 이름만으로 카드값으로 바꾸지 않는다

예전에는 적요에 카드사 이름이 있으면 바로 `card_payment`가 되어 거래 목록에서 숨었다('신한카드 홍길동' 같은 송금 포함). 이제 `transfer` 그대로 두고 카드값 후보 표시만 한다 → 목록에 보이고 사용자가 분류할 수 있다. 위 조건으로 청구서에 자동 연결되거나 사용자가 연결할 때만 `card_payment`가 되고, 연결을 풀면 `transfer`로 돌아온다. 사용자가 확정한 거래는 자동으로 가져가지 않는다. 이미 예전 규칙으로 `card_payment`가 된 거래는 그대로 두며(보정 안 함) 위 조건으로 계속 매칭된다.
