# 카드 API 명세 — 후보·선택·청구서

> 담당: 권세진 · 작성일: 2026-10-21 · 수정일: 2026-10-22 · 명세 상태: 검토용 초안
> 개발 상태: 카드 API 3개 미구현, 관련 화면은 임시 동작·예시 데이터 사용
> 기준: [공통 규칙](../API_RULES.md), [결정 기록](../결정기록_2026-10-21.md), [API 목록](../머니쿠션_API_명세_목록_2026-10-21.md), [작성 틀](./_TEMPLATE.md)
> 관련 문서: [인증·회원](./auth.md) · [카드](./cards.md) · [대출](./loans.md) · [소비 분석](./spending-analysis.md)

카드 후보 조회·선택 저장·청구서 조회 3개 API의 요청·응답과 예시를 정리한다. 팀원과 논의할 내용은 이 문서 마지막의 **확인 필요 사항 모음**에서 확인한다.

기존 검토 내용과 참조를 유지하기 위해 API 번호 1~10과 소비 분석 A-1~A-7 번호를 그대로 사용한다. 다른 기능의 번호는 위 관련 문서에서 확인한다.

문서 작성 완료와 팀 합의·구현 완료는 다르다. 본문의 **초안 제안·미정·확정 보류** 표시는 유지했다. 기존 모델에 칸이 있다는 사실만으로 CODEF 제공 여부나 사용자 수정 권한이 확정되는 것은 아니다. 예시의 개인정보·금액·UUID는 모두 가상 값이다.

| 번호 | 기능 | 방식·주소 | 목록의 작성 상태 |
|---|---|---|---|
| 6 | 카드 후보 보기 | `GET /api/finance/connect/cards/` | 기본만 |
| 7 | 카드 선택 저장 | `PUT /api/finance/connect/cards/` | 기본만 |
| 10 | 카드 청구서 보기 | `GET /api/finance/card-bills/<id>/` | 기본만 |

비밀번호 재설정·ML 입력 정보·추천 예산·쿠션 배분 규칙·후속 차수 기능은 이번에 정하지 않는다. 온보딩 미완료자는 홈 대신 온보딩으로 이동한다는 원칙은 확정됐지만(H-06), 진행 단계를 어느 API의 어떤 필드로 전달할지는 미정이다(H-08). 금융 동의·계좌·연결 해제·재조회·챗봇 전체 계약은 혜리 담당이며, `chat.md` 최종 편집도 혜리가 한다.

### 요청·오류·재시도 공통 적용

- 보내는 값 표에 없는 필드와 서버가 정하는 필드(예: `status`)를 보내면 400 `invalid`, 해당 필드에 “이 칸은 보낼 수 없어요.”를 반환한다. 조용히 무시하지 않는다. 아직 확정 보류인 요청 필드는 허용 목록으로 취급하지 않는다.
- 오류에는 `code`·`message`가 항상 있다. `fields`는 입력 칸 오류가 있을 때만 넣고, 로그인 불일치·미인증·404처럼 칸과 무관한 오류에서는 키 자체를 생략한다. 빈 `{}`를 보내지 않는다. 여러 입력 칸의 조합 오류는 `fields.nonFieldErrors`를 사용한다.
- 주소 ID가 잘못된 UUID이거나, 없거나, 남의 항목이거나, 해당 동작을 할 수 없는 상태이면 JSON 404 `not_found`다. 본문 ID의 형식 오류·없는 항목·남의 항목·선택 불가 항목은 400이며, 여러 개 중 하나라도 잘못되면 전체 저장하지 않는다. 존재·소유·선택 가능 여부를 구분해 노출하지 않는다.
- 이미 요청한 상태라면 같은 작업을 다시 반영하지 않고 성공으로 응답한다. 다만 없는 ID·남의 데이터에는 적용하지 않는다. 카드·대출의 구체적인 동작 가능 상태표는 별도 확정이 필요하며, 고정지출의 상태 코드를 그대로 가져오지 않는다.
- 새로 만들기·승인 요청에 쓰는 `Idempotency-Key`는 입력 폼·팝업을 열 때, 버튼 하나로 끝나는 동작은 누를 때 만든다. 처리 중 버튼을 잠그고 응답 전 재전송에는 같은 키를 쓰며, 완료 후 버린다.
- 요청 번호 적용 대상에서는 같은 회원·키·내용에 처음 응답을 재사용하고, 기록된 키로 다른 내용을 보내면 409 `idempotency_conflict`다. 실패한 4xx·5xx는 기록하지 않아 수정 후 같은 키로 재시도할 수 있다. 현재 공통 구현은 비로그인 요청에 적용되지 않으므로 회원가입의 중복 방지 계약은 마지막 확인 목록에 남긴다. 이 규칙만으로 모든 PUT·PATCH에 필수 헤더를 추가하지 않는다.

공통 규칙에서 언급한 회원가입·로그인의 세션·CSRF 계약과 익명 가입의 요청 번호 확인 사항은 [인증·회원 명세](./auth.md#확인-필요-사항-모음)를 함께 참조한다.

아래 공통 규칙의 “5개 API”는 카드 3개와 대출 2개를 합한 범위다.

## 카드·대출 공통 규칙

- 5개 API 모두 로그인 필요. 조회는 세션 쿠키, 저장은 세션 쿠키와 `X-CSRFToken`을 사용한다.
- 금액은 원 단위 정수, 날짜는 `YYYY-MM-DD`, 시각은 한국 시간 ISO 8601, ID는 UUID 문자열이다.
- 목록은 `{ "items": [...] }`, 조회가 정상 완료되어 항목이 없으면 `{ "items": [] }`이다. 미조회·조회 실패를 보유 상품 없음으로 바꾸지 않는다.
- 모르는 값은 null, 확인된 0원은 0이다. 값이 없다고 계산해서 채우거나 다른 항목을 대신 쓰지 않는다.
- 계좌·카드 응답은 공통 규칙의 `displayName`·`status`를 포함한다. `connected`는 정상 연결, `relogin`은 다시 연결 필요(선택·기존 연결 유지), `disconnected`는 연결 해제(새로 선택 불가)다. **결정 기록 H-07에 따라 API 값은 DB 값과 같으며, 계좌·카드의 연결 상태는 연결된 `connection.status`에서 그대로 가져온다.** 별도 상태 저장·API용 매핑은 만들지 않는다. 기관이 제공하는 `cardStatus`와는 다른 값이다. 모델의 choices·CHECK 미반영은 구현 대기이며 정책 미정이 아니다. 연결 FK가 없는 카드의 응답·노출 방식은 별도 확인 대상으로 남긴다.
- 응답에는 비밀번호·CODEF 키·`connectedId`·원문 번호·기관 원천 식별값·암호화 원문을 넣지 않는다. 예시 데이터는 모두 가상이다.
- 본인 소유만 조회·수정한다. 관련 계좌·카드·연결의 소유권도 서버에서 검증한다.
- 고정비는 생활비를 나누기 전에 한 번만 뺀다. 확정 고정지출·대출 월 상환 예정액·첫 카드 청구서·이번 회차 할부금 사이에 같은 비용을 중복 차감하지 않는다. 승인된 예산은 사용자 승인 없이 변경하지 않는다.
- `PaymentDue`는 출금일이 있을 때만 만든다. 출금일을 모르면 날짜를 추측하지 않고 “출금일 확인 필요”로 안내한다. 카드로 내는 고정지출은 카드 청구서에 포함되므로 고정지출용 납부 예정을 따로 만들지 않는다.
- 고정지출과 연결된 카드 거래는 `spending_allocation.funding_bucket = fixed`로 분류하여 생활비 카테고리 사용액에서 제외한다. 연결은 이름만으로 판단하지 않고 실제 근거 거래를 사용한다. 소비 분석 총액에도 제외할지는 별개의 미정 사항이다.
- “이번 주기”는 설정한 월급날부터 다음 월급날 전날까지다(H-01). 실제 입금이 늦어도 주기는 바뀌고 그 사이 소비는 새 주기에 속한다. 다음 월급이 미리 들어와도 지난 주기 예산에 더하지 않는다. 매월 해당 날짜가 없는 달은 말일을 사용한다.

### 카드·대출 공통 실패 처리

각 API의 실패 표와 함께 적용한다.

| 상황 | HTTP 상태 | `error.code` | 화면 안내 |
|---|---|---|---|
| 비로그인·세션 만료 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| 저장 요청의 CSRF 실패 | 403 | `permission_denied` | 다시 시도 안내 |
| 입력 형식·값 오류 | 400 | `invalid` | 해당 `fields`를 입력 칸 아래 표시 |
| 주소의 ID 형식 오류·없는 항목·남의 항목·해당 동작 불가 상태 | 404 | `not_found` | 같은 JSON 오류로 찾을 수 없어요 |
| 요청 본문 ID가 없거나 다른 사람 소유·선택 불가 | 400 | `invalid` | 모두 같은 선택 불가 문구. 한 개라도 잘못되면 전체 저장 취소 |
| JSON 형식 오류 | 400 | `parse_error` | 개발 단계에서 요청 확인 |
| 지원하지 않는 방식 | 405 | `method_not_allowed` | 개발 단계에서 요청 방식 확인 |
| 서버 내부 오류 | 500 | `server_error` | 잠시 후 다시 시도 안내 |

외부 조회 실패·동의 미완료·재인증 필요의 HTTP 상태와 오류 코드는 미정이다.

## 6. 카드 후보 보기

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 카드 선택 화면에서 조회된 카드와 현재 선택 상태를 보여줄 때 |
| 어디로 | `GET /api/finance/connect/cards/` |
| 로그인 필요 | O |
| 명세 상태 | 기본만: 모델·공통 표시 규칙에 근거한 응답 초안 |

**보내는 값**

요청 본문 없음. 본인 식별은 세션으로 한다. 기관·연결별 쿼리 필터는 미정이다.

**받는 값 (200, 기본 응답 초안)**

| 이름 | 타입 | 뜻·범위 |
|---|---|---|
| `items` | 배열 | 카드 후보 목록 |
| `items[].cardId` | UUID 문자열 | 선택 저장에 사용할 내부 카드 ID |
| `items[].displayName` | 문자열 | 공통 규칙대로 서버가 조합한 카드명·마스킹 번호 |
| `items[].status` | 문자열 | 연결 상태: `connected`, `relogin`, `disconnected` |
| `items[].cardType` | 문자열 또는 null | 저장된 카드 종류. 기관 값 정규화 기준은 미정 |
| `items[].cardStatus` | 문자열 또는 null | 기관이 제공한 카드 상태. 연결 상태와 구분 |
| `items[].isSelected` | 불리언 | 현재 관리 대상으로 저장된 선택 여부 |
| `items[].fetchedAt` | 시각 문자열 또는 null | 마지막 정상 조회 시각. 응답 생성 시각으로 대체하지 않음 |

```json
{
  "items": [
    {
      "cardId": "13cb7fb6-cff8-4c17-a76a-ea90f57ce330",
      "displayName": "신한 Deep Dream · ****4321",
      "status": "connected",
      "cardType": "체크",
      "cardStatus": "정상",
      "isSelected": true,
      "fetchedAt": "2026-10-21T09:30:00+09:00"
    }
  ]
}
```

정상 조회 결과 카드가 없는 경우의 예시:

```json
{ "items": [] }
```

화면은 카드가 없다는 안내와 다음 단계로 진행할 선택지를 보여준다. 이 빈 목록은 해당 조회 범위에서 보유 카드가 없다고 정상 확인된 경우에만 사용한다. 카드사 인증·조회 실패나 일부 카드사의 미조회 결과를 빈 목록으로 바꾸지 않는다. 카드사를 선택했지만 보유 카드가 없는 경우의 진행 방식은 7번에 정리했다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 비로그인 | 403 | `not_authenticated` | 로그인 필요 |
| 서버 오류 | 500 | `server_error` | 조회 실패·재시도 |
| 외부 조회 실패·미조회·조회 동의 미완료 | 미정 | 미정 | 카드가 없는 것으로 표시하지 않고 원인 안내 |

## 7. 카드 선택 저장

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 카드 선택 화면에서 사용할 카드를 고르고 다음 단계로 갈 때 |
| 어디로 | `PUT /api/finance/connect/cards/` |
| 로그인 필요 | O, CSRF 검증 필요 |
| 명세 상태 | 기본만: ID 목록 구조 초안. 저장 범위는 미정 |

**보내는 값**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `cardIds` | UUID 문자열 배열 | 초안: O | 본인이 조회한 후보 ID 목록. 번호 원문·카드명을 보내지 않음 | 아래 예시 |

```json
{ "cardIds": ["13cb7fb6-cff8-4c17-a76a-ea90f57ce330"] }
```

본문의 이름 `cardIds`는 ID만 보내라는 공통 원칙을 적용한 초안이다. **PUT으로 덮어쓸 범위가 전체 카드인지 특정 연결인지 확정 전에는, 요청에서 빠진 다른 카드들을 자동 해제하지 않는다.** 빈 배열·중복 ID·최대 개수의 정책은 미정이다. “카드는 나중에 연결” 버튼과 “기존 선택 전체 해제”는 같은 동작으로 가정하지 않는다.

**카드사를 선택했지만 해당 카드사의 보유 카드가 없는 경우 — 화면 처리 초안**

카드사 선택은 조회할 기관을 고르는 단계이고, 이 API는 조회된 실제 카드 ID를 저장하는 단계이다. 보유하지 않은 카드사를 앞 단계에서 골랐다고 가짜 카드 ID를 만들거나 카드사 이름을 `cardIds`에 넣지 않는다.

| 조회 결과·사용자 행동 | 화면·저장 처리 |
|---|---|
| 정상 조회 결과 해당 카드사에 보유 카드가 없음 | “선택한 카드사에서 조회된 카드가 없어요.” 안내. 카드사 다시 선택 또는 카드 연결 건너뛰기 제공 |
| 모든 조회가 완료됐고 선택할 카드가 하나도 없음 | 카드 선택 저장 PUT을 호출하지 않고 다음 단계로 진행하는 초안. 빈 배열을 보내 기존 카드 선택을 지우지 않음 |
| 다른 카드사에는 선택 가능한 카드가 있음 | 해당 카드들을 계속 선택할 수 있게 함. 보유 카드가 없는 카드사 때문에 다른 카드의 선택을 초기화하지 않음 |
| 인증 실패·조회 실패·일부 기관 미조회 | 보유 카드 없음과 구분해 실패·재시도 안내. 실패 결과로 기존 선택을 덮어쓰지 않음 |
| 클라이언트가 없는 카드 ID를 넣어 저장 요청 | 서버가 400 `invalid`와 동일한 선택 불가 문구로 거절하고 전체 미저장 |

이 처리안은 카드 선택 단계의 동작이다. 기관 연결 해제를 자동 실행하지 않으며, 카드사별 조회 결과를 구분할 응답 구조와 최종 화면 연결은 마지막 확인 목록에서 혜리와 맞춘다.

**받는 값 (200, 기본 응답 초안)**

저장 대상으로 합의된 범위의 카드 상태를 6번과 같은 `items` 구조로 반환하는 초안이다.

```json
{
  "items": [
    {
      "cardId": "13cb7fb6-cff8-4c17-a76a-ea90f57ce330",
      "displayName": "신한 Deep Dream · ****4321",
      "status": "connected",
      "cardType": "체크",
      "cardStatus": "정상",
      "isSelected": true,
      "fetchedAt": "2026-10-21T09:30:00+09:00"
    }
  ]
}
```

같은 선택을 다시 저장해도 중복 기록이나 중복 차감을 만들지 않고 성공으로 처리한다. 선택 저장 시각을 금융정보의 `fetchedAt`으로 기록하지 않는다. 카드 선택만으로 예산·고정비·기존 거래를 다시 계산하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| ID 배열이 아닌 값·UUID 형식 오류 | 400 | `invalid` | `fields.cardIds` 표시 |
| 없는 카드·남의 카드·선택 불가 카드 포함 | 400 | `invalid` | 모두 같은 선택 불가 안내, 전체 미저장 |
| 비로그인·CSRF 오류 | 403 | 공통 규칙 | 로그인 또는 재시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "입력값을 확인해 주세요.",
    "fields": { "cardIds": ["선택할 수 없는 카드예요."] }
  }
}
```

### 청구 상세와 상태 전달 제안 — 팀 합의 전 미정

작성 순서의 “청구 항목 목록”과 CARD-002의 “예상/확정 상태·기준 시각”을 표현하기 위한 제안이다. **새 필드·상태 코드·목록 의미는 미정이며 CODEF 제공을 보증하지 않는다.** `scopeType`·`confirmationStatus`는 기존 DB 칸에 대응할 후보이고, `CardBill`에는 전용 `fetched_at`이 없어 조회 기록 등 시각의 원천을 나은·혜리와 정해야 한다. 상세 항목의 가장 최근 시각을 청구 총액 조회 시각으로 대신 쓰지 않는다.

| 이름 (`items[]` 안, 응답 필드 제안) | 타입 | 뜻·근거 |
|---|---|---|
| `billItemId` | UUID 문자열 | 내부 청구 항목 ID |
| `itemType` | 문자열 | 기존 `CardBillItem.ItemType`의 `one_time`, `installment`, `fee`, `interest`, `adjustment`, `unknown` 사용. CODEF 원천값 대응은 검증 대기 |
| `merchantName` | 문자열 또는 null | 가맹점·항목명 |
| `card` | 객체 또는 null | 해당 항목의 카드 공통 표시 객체. 알 수 없으면 null |
| `purchasedOn` | 날짜 문자열 또는 null | 원 구매일. 청구일로 대신 채우지 않음 |
| `originalPurchaseAmount` | 정수 또는 null | 전체 구매 금액, 원 |
| `billedAmount` | 정수 또는 null | 이번 회차 청구액, 원. 미제공 null과 확인된 0원 구분 |
| `installmentMonths`, `installmentRound` | 정수 또는 null | 할부 총회차·이번 회차. 확인된 할부는 1 이상, 이번 회차는 총회차 이하. 일시불·회차 미확인은 null 제안 |
| `fetchedAt` | 시각 문자열 또는 null | 해당 항목의 마지막 정상 조회 시각. 모델 `CardBillItem.fetched_at` 대응 후보 |

**총액·상세 모두 확인된 가상 응답 예시 — 신규 계약은 제안 상태**

예시 검산: 일시불 360,000원 + 이번 회차 할부 60,000원 = 총청구액 420,000원. 할부 원 구매액 180,000원을 다시 더하지 않는다. `scopeType: issuer`이면 카드가 한 장이어도 카드사 통합 청구서다. 단일 카드 청구(`card`)에서는 `card`와 `cards`의 한 항목이 같은 카드를 가리키도록 하는 제안이다. 카드사 통합 청구에서는 `card: null`을 사용하고 실제 포함 카드는 `cards`로 표시한다. 카드 예시는 6번의 체크카드 예시와 별개의 가상 상황이다.

**총액만 확보되고 상세는 미제공인 경우 — 응답 변경 필드 발췌, 제안**

```json
{
  "billId": "7521ba60-6358-4810-94e4-e62eed25b3c6",
  "scopeType": "unknown",
  "totalAmount": 420000,
  "confirmationStatus": "unknown",
  "fetchedAt": "2026-10-21T09:30:00+09:00",
  "card": null,
  "cards": null,
  "itemsState": "unavailable",
  "items": null
}
```

이 경우 “조회 금액 420,000원 · 확정 여부 및 상세 항목 확인 필요”로 안내하는 제안이다. 일부 항목만 있으면 `itemsState: partial`과 확보한 항목만 보내며, 항목 합계를 총청구액으로 대체하지 않는다. 전체 항목과 모든 `billedAmount`가 확인된 경우에만 총액과 대조한다. 차이가 있으면 임의의 조정 항목을 만들어 맞추지 않고 자료 불일치를 안내할 계약을 합의한다. `estimated`·`unknown`을 확정 납부액으로 표시하지 않는다. 조회 실패 시 기존 자료를 반환할지 오류를 반환할지는 금융 공통 실패 계약에서 정하며, 위 성공 예시로 실패를 숨기지 않는다.

| 구분 | 이번 제안의 처리 |
|---|---|
| 기본 응답에 추가할 후보 | 청구 범위·관련 카드·항목 목록·청구 확정 상태·정상 조회 시각 |
| 실제 제공 검증 대기 | 상세 원천값, 할부 총회차·현재 회차, 청구 확정 근거, 카드사 통합 범위 |
| 이번 응답 제안에서 제외 | 리볼빙·현금서비스·카드론·연체료의 별도 위험 요약, 급여주기 승인·취소 기준 소비액. 미제공을 0원으로 표시하거나 위험 없음으로 해석하지 않음 |

**확인 필요:** 필드명·상태 코드·시각 저장 원천·상세 누락과 불일치 안내 / 김나은·김혜리·권세진. 위 제외 항목은 서비스 범위에서 삭제한다는 뜻이 아니며, 화면에서는 자료 확인 전 숨길지 “확인 필요”로 표시할지 합의한다.

**첫 청구서·고정지출 연동 — 확정된 원칙**

- 첫 카드 청구서만 예산에서 먼저 차감한다. 이후 청구서 납부는 카드 사용 때 이미 반영한 지출과 연결하며 다시 차감하지 않는다(TXN-009).
- 카드 고정지출은 청구서에 포함되므로 별도 고정지출 납부 예정을 만들지 않는다. 첫 청구서와 이번 회차 할부금에도 같은 비용을 두 번 넣지 않는다.
- 카드 청구서의 납부 예정도 출금일을 확인할 수 있어야 생성한다. 출금일이 없으면 “출금일 확인 필요”로 안내한다.
- **첫 청구서에서 정확히 어떤 항목을 얼마만큼 차감할지는 C-17 미정 사항이다.** `totalAmount` 전체를 선차감액으로 간주하지 않는다. H-04 홈 표시 방식과 함께 마지막 확인 목록에서 합의한다.

상세 청구 항목·할부는 위 응답 후보로 제안했으며 실제 제공 범위와 계약은 미정이다. 위험 요약·급여주기 소비액은 별도 확인 대상으로 남긴다. 출금 예정일이 지났거나 `confirmationStatus: confirmed`라는 이유로 납부 완료로 바꾸지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 주소 UUID 형식 오류·청구서 없음·남의 청구서 | 404 | `not_found` | 청구서를 찾을 수 없어요 |
| 비로그인 | 403 | `not_authenticated` | 로그인 필요 |
| 서버 오류 | 500 | `server_error` | 조회 실패·재시도 |
| 외부 조회 실패·미조회 | 미정 | 미정 | 청구액을 0원으로 표시하지 않음 |

## 구현 전 검토·검증 목록

향후 구현 시 검증할 항목이며 현재 테스트 통과 기록이 아니다.

- [ ] 본인 상품만 조회되고 다른 사람의 주소 ID는 404가 된다.
- [ ] 본문 ID에 남의 카드·없는 카드·선택 불가 카드가 섞이면 동일한 400 안내로 전체 저장이 취소된다.
- [ ] 빈 목록·null·0원·조회 실패를 구분한다.
- [ ] 계좌·카드의 표시 객체와 마스킹, 대문자 카테고리 코드를 지킨다.
- [ ] H-07에 따라 계좌·카드 `status`가 연결된 `connection.status`와 일치하고 별도 매핑·독립 상태 저장을 하지 않는다. 연결 FK 없음 처리는 합의 후 검증한다.
- [ ] 청구 응답 제안 채택 후 카드사 통합·단일 카드·범위 미확인, 예상·확정·확정 여부 미확인, 상세 전체·일부·미제공을 각각 구분한다. 원 구매액을 이번 회차 청구액에 중복 합산하지 않는다.
- [ ] 카드 청구·대출 상환·고정지출·거래를 중복 차감하지 않는다.
- [ ] 주소 UUID 형식 오류·동작 불가 상태는 JSON 404, PATCH 생략·nullable null·필수 null·빈 문자열은 공통 규칙을 따른다. ID 경로에는 `<uuid:이름>`을 사용하고, 새 경로는 `api_urls.py`의 마지막 `not_found` 처리 위에 등록한다.
- [ ] 같은 요청은 중복 반영하지 않는다. 요청 번호 적용 대상은 같은 키 재시도·다른 내용 충돌·실패 후 재시도를 확인한다.
- [ ] 출금일 없는 납부 예정을 만들지 않고, 카드 고정지출용 납부 예정을 별도로 만들지 않는다.
- [ ] 고정지출과 연결된 카드 거래는 생활비 사용액에서 제외하고, 대출 상환 출금은 고정지출 후보로 중복 생성하지 않는다.
- [ ] 월급의 조기·지연 입금에도 설정한 월급날 기준 주기를 유지한다.
- [ ] 첫 청구서의 선차감 상세는 C-17 확정 후 검증하며, 이후 카드 납부를 다시 차감하지 않는다.
