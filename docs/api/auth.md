# 인증·회원 API 명세

> 담당: 권세진 · 작성일: 2026-10-21 · 수정일: 2026-10-22 · 명세 상태: 검토용 초안

> 기준: [공통 규칙](../API_RULES.md), [결정 기록](../결정기록_2026-10-21.md), [API 목록](../머니쿠션_API_명세_목록_2026-10-21.md), [작성 틀](./_TEMPLATE.md)
> 관련 문서: [인증·회원](./auth.md) · [카드](./cards.md) · [대출](./loans.md) · [소비 분석](./spending-analysis.md)

인증·회원 5개 API의 요청·응답과 예시를 정리한다. 팀원과 논의할 내용은 이 문서 마지막의 **확인 필요 사항 모음**에서 확인한다.

기존 검토 내용과 참조를 유지하기 위해 API 번호 1~10과 소비 분석 A-1~A-7 번호를 그대로 사용한다. 다른 기능의 번호는 위 관련 문서에서 확인한다.

문서 작성 완료와 팀 합의·구현 완료는 다르다. 본문의 **초안 제안·미정·확정 보류** 표시는 유지했다. 기존 모델에 칸이 있다는 사실만으로 CODEF 제공 여부나 사용자 수정 권한이 확정되는 것은 아니다. 예시의 개인정보·금액·UUID는 모두 가상 값이다.

| 번호 | 기능 | 방식·주소 | 목록의 작성 상태 |
|---|---|---|---|
| 1 | 저장 전 보안값 준비 | `GET /api/csrf/` | 지금 |
| 2 | 회원가입 | `POST /api/auth/signup/` | 지금 |
| 3 | 로그인 | `POST /api/auth/login/` | 지금 |
| 4 | 로그아웃 | `POST /api/auth/logout/` | 지금 |
| 5 | 내 계정 확인 | `GET /api/auth/me/` | 기본만 |

비밀번호 재설정·ML 입력 정보·추천 예산·쿠션 배분 규칙·후속 차수 기능은 이번에 정하지 않는다. 로그인·내 계정 응답의 `onboardingCompleted`는 첫 예산 승인 시 true이며, false면 저장된 값을 채운 온보딩 첫 단계로 이동한다(결정기록 3-3 R). 1차에는 단계 번호를 반환하지 않는다. 금융 동의·계좌·연결 해제·재조회·챗봇 전체 계약은 혜리 담당이며, `chat.md` 최종 편집도 혜리가 한다.

## 결정기록에서 반영한 확정 기준

아래는 `결정기록_2026-10-21.md` 전체를 확인해 이 담당 범위에 적용한 팀 확정 사항이다. **팀 규칙이 확정됐다는 뜻이며, 아래 API의 초안 필드나 구현까지 완료됐다는 뜻은 아니다.** 닉네임 필수는 세진 요청으로 반영한 별도 기준이다.

| 근거 | 이 명세에 반영한 내용 |
|---|---|
| ★ 1·2·3 / 체크리스트 | 연결 상태 3가지, 허용하지 않은 요청 항목 400, 주소 ID 형식·소유권·동작 불가 상태 404, 본문 ID 오류 400·전체 미저장 |
| ★ 4 / C-09·C-10·C-11 / 공통 규칙 | 오류 `fields`의 조건부 포함, PATCH의 생략·null 처리, 중복 처리 방지와 요청 번호 생성 시점 |
| H-06 / 3-3 R | 로그인·내 계정에 `onboardingCompleted`. 첫 예산 승인 시 true, false면 온보딩 첫 단계로 이동 |
| 3-3 R·V⑩·X | 온보딩 완료 여부, 로그인 실패 횟수 제한의 1차 제외, 회원가입·로그인·로그아웃 확정 정책 |

### 요청·오류·재시도 공통 적용

- 보내는 값 표에 없는 필드와 서버가 정하는 필드(예: `status`)를 보내면 400 `invalid`, 해당 필드에 “이 칸은 보낼 수 없어요.”를 반환한다. 조용히 무시하지 않는다. 아직 확정 보류인 요청 필드는 허용 목록으로 취급하지 않는다.
- 오류에는 `code`·`message`가 항상 있다. `fields`는 입력 칸 오류가 있을 때만 넣고, 로그인 불일치·미인증·404처럼 칸과 무관한 오류에서는 키 자체를 생략한다. 빈 `{}`를 보내지 않는다. 여러 입력 칸의 조합 오류는 `fields.nonFieldErrors`를 사용한다.
- 주소 ID가 잘못된 UUID이거나, 없거나, 남의 항목이거나, 해당 동작을 할 수 없는 상태이면 JSON 404 `not_found`다. 본문 ID의 형식 오류·없는 항목·남의 항목·선택 불가 항목은 400이며, 여러 개 중 하나라도 잘못되면 전체 저장하지 않는다. 존재·소유·선택 가능 여부를 구분해 노출하지 않는다.
- 이미 요청한 상태라면 같은 작업을 다시 반영하지 않고 성공으로 응답한다. 다만 없는 ID·남의 데이터에는 적용하지 않는다. 대출 보완은 `repaying`만 가능하고 `repaid`는 404다(P). 카드의 원천 상태별 선택 가능 범위는 마지막 확인 목록에 남기며 고정지출 상태 코드를 그대로 가져오지 않는다.
- 새로 만들기·승인 요청에 쓰는 `Idempotency-Key`는 입력 폼·팝업을 열 때, 버튼 하나로 끝나는 동작은 누를 때 만든다. 처리 중 버튼을 잠그고 응답 전 재전송에는 같은 키를 쓰며, 완료 후 버린다.
- 요청 번호 적용 대상에서는 같은 회원·키·내용에 처음 응답을 재사용하고, 기록된 키로 다른 내용을 보내면 409 `idempotency_conflict`다. 실패한 4xx·5xx는 기록하지 않아 수정 후 같은 키로 재시도할 수 있다. 회원가입은 이메일 중복 검사·DB 유일성 제약으로 중복 가입을 막으며 별도 요청 번호를 쓰지 않는다(결정기록 3-3 X). 이 규칙만으로 모든 PUT·PATCH에 필수 헤더를 추가하지 않는다.

## 인증·회원 공통 약속

- JSON 요청은 `Content-Type: application/json`을 사용한다. 키는 camelCase이다.
- 로그인은 Django 세션 쿠키를 사용한다. JWT·accessToken·refreshToken을 만들거나 응답에 넣지 않는다.
- `POST` 요청에는 CSRF 쿠키와 이에 대응하는 `X-CSRFToken` 헤더가 필요하다. 로그인 전의 회원가입·로그인 요청도 검증 대상으로 설계한다.
- React의 `apiSend`는 CSRF 쿠키가 없으면 `/api/csrf/`를 먼저 호출하고 요청 헤더를 붙인다. 로그인으로 토큰이 바뀌면 이후 요청은 새 쿠키를 사용한다.
- 회원 기본 정보는 `userId`, `email`, `nickname`이다. 로그인과 `/me/`에는 `onboardingCompleted`를 추가한다(결정기록 3-3 R). 비밀번호·비밀번호 해시·CODEF 연결 식별값은 반환하지 않는다.
- 모든 예시의 이메일·비밀번호·UUID는 설명용 가상 값이다.

### 공통 회원 응답

| 이름 | 타입 | null 가능 | 뜻·근거 |
|---|---|---|---|
| `userId` | UUID 문자열 | X | `users.User.user_id`, 서버가 만든 회원 ID |
| `email` | 문자열 | X | 저장된 이메일. 기존 모델은 앞뒤 공백 제거 후 전체 소문자로 저장 |
| `nickname` | 문자열 | X | 이름(닉네임), 필수. 앞뒤 공백 제거 후 1~100자이며 null·빈 문자열·공백만 있는 값은 허용하지 않음 |

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

### 인증·회원 공통 실패 처리

각 API의 실패 표에 더해 다음 규칙을 적용한다.

| 상황 | HTTP 상태 | `error.code` | 화면 처리 |
|---|---|---|---|
| JSON 형식이 깨짐 | 400 | `parse_error` | 요청 오류 안내, 개발 단계에서 요청 확인 |
| CSRF 검증 실패 | 403 | `permission_denied` | 오류 안내 후 다시 시도하도록 함 |
| 지원하지 않는 방식으로 요청 | 405 | `method_not_allowed` | 개발 단계에서 요청 방식 확인 |
| 서버 내부 오류 | 500 | `server_error` | 잠시 후 다시 시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "입력값을 확인해 주세요.",
    "fields": {
      "email": ["이메일 형식을 확인해 주세요."]
    }
  }
}
```

**받는 값 (200)**

| 이름 | 타입 | 뜻 |
|---|---|---|


| GET 외 방식 | 405 | `method_not_allowed` | 요청 방식 확인 |

## 2. 회원가입

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 회원가입 화면에서 필수 동의를 확인하고 [가입하고 시작하기]를 누를 때 |
| 어디로 | `POST /api/auth/signup/` |
| 로그인 필요 | X, CSRF 검증 필요 |
| 명세 상태 | 결정기록 3-3 L·X 반영. 구현 전 명세 |
| 개발 상태 | 미구현. 현재 화면은 저장 없이 온보딩으로 이동 |

**보내는 값**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `email` | 문자열 | O | 이메일 형식, 최대 255자(기존 모델). 앞뒤 공백 제거·소문자 정규화 후 중복 검사 | `"sejin@example.com"` |
| `password` | 문자열 | O | 8~25자. 영문·숫자·특수문자 중 2가지 이상 포함(X). 서버도 같은 조건 검사 | `"Example123!"` |
| `nickname` | 문자열 | O | 이름(닉네임), 앞뒤 공백 제거 후 1~100자. 누락·null·빈 문자열·공백만 있는 값은 거절 | `"세진"` |
| `consents` | 객체 배열 | O | 동의한 항목만 보냄. 서비스 약관 `terms`와 개인정보 `privacy`가 모두 있어야 가입 가능(L). 전송 버전은 `v1`(L), 최종 약관 문구는 확인 필요 | 아래 예시 |
| `consents[].purpose` | 문자열 | O | 동의 구분: `terms`, `privacy` | `"terms"` |
| `consents[].documentVersion` | 문자열 | O | 사용자가 실제 읽은 문서 버전. 결정기록 3-3 L의 `v1` | `"v1"` |

```json
{
  "email": "sejin@example.com",
  "password": "Example123!",
  "nickname": "세진",
  "consents": [
    { "purpose": "terms", "documentVersion": "v1" },
    { "purpose": "privacy", "documentVersion": "v1" }
  ]
}
```

비밀번호 확인은 화면에서만 원문과 비교한다. 서버에는 `password`를 한 번만 보내며 확인용 필드는 없다(X). 나이·성별·급여·금융기관 조회 동의는 포함하지 않는다. 금융 조회 동의는 혜리 담당의 별도 API이다.

결정기록 3-3 L: 동의하지 않은 항목은 목록에 넣지 않는다. `agreed` 필드는 보내지 않으며, 보내면 공통 규칙의 허용하지 않은 필드 오류(400 `invalid`)다. `terms` 또는 `privacy` 중 하나라도 없으면 가입을 거절한다.

**받는 값 (201 Created)**

생성된 회원 정보를 공통 회원 응답 형태로 반환하고 자동 로그인 세션 쿠키를 설정한다(X). 화면은 바로 온보딩으로 이동한다. 쿠키·CSRF 갱신은 로그인과 같은 세션 규칙을 따른다.

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

회원과 필수 동의 기록은 하나의 트랜잭션으로 저장하는 설계다. 동의 시각·원문 해시는 서버가 관리하며 클라이언트가 보낸 값을 신뢰하지 않는다. 비로그인 회원가입에는 요청 번호를 쓰지 않는다. 두 번 누른 가입은 정규화한 이메일의 중복 검사·DB 고유 제약으로 막아 회원을 하나만 만든다(X). 로그인 중 회원가입 요청은 400 `invalid`다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 이메일 누락·잘못된 형식·길이 초과 | 400 | `invalid` | `fields.email` 표시 |
| 정규화한 이메일이 이미 사용 중 | 400 | `invalid` | `fields.email`: "이미 가입된 이메일이에요" |
| 로그인한 상태로 회원가입 요청 | 400 | `invalid` | 회원가입 불가 안내. 칸 오류가 아니므로 `fields` 생략 |
| 비밀번호 조건 미충족 | 400 | `invalid` | `fields.password`에 충족하지 못한 조건 표시 |
| 닉네임 누락·null·빈 문자열·공백만 입력·길이 초과 | 400 | `invalid` | `fields.nickname`에 이름(닉네임) 입력 조건 안내 |
| `terms` 또는 `privacy` 누락·지원하지 않는 버전 | 400 | `invalid` | `fields.consents` 표시, 두 필수 동의·최신 약관 확인 안내 |
| CSRF 실패 | 403 | `permission_denied` | 오류 안내. 회원을 생성하지 않음 |

|---|---|---|---|---|
| `email` | 문자열 | O | 이메일 형식, 최대 255자. 기존 모델의 정규화 방식으로 회원 조회 | `"sejin@example.com"` |
| `password` | 문자열 | O | 로그인에서는 길이·조합을 검사하지 않고 저장된 비밀번호와 인증한다(X). 앞뒤 공백을 임의로 제거하지 않음 | `"Example123!"` |

```json
{ "email": "sejin@example.com", "password": "Example123!" }
```

1차에는 [자동 로그인] 체크박스와 해당 요청 필드가 없다. 로그인하면 세션을 14일 유지한다(X). [아이디 저장]은 화면이 이메일만 기억하는 기능으로 서버 요청과 무관하다. 로그인 실패 횟수 제한은 1차에 적용하지 않는다(V⑩). 사용자 ID나 로그인 성공 여부를 클라이언트가 보내 인증을 대신하지 않는다.

**받는 값 (200)**

공통 회원 응답에 `onboardingCompleted`를 추가하고 로그인 세션 쿠키를 받는다. 본문에는 토큰이 없다.

| 추가 이름 | 타입 | 뜻 |
|---|---|---|
| `onboardingCompleted` | 불리언, null 불가 | 첫 예산을 승인했으면 true, 아직 승인 전이면 false(R). 로그인과 `/me/`에서 같은 이름·의미 사용 |

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진",
  "onboardingCompleted": false
}
```

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 필수 입력 누락·이메일 형식 오류 | 400 | `invalid` | 해당 `fields`를 입력 칸 아래 표시 |
| 이메일·비밀번호 불일치 또는 정지·탈퇴 계정 | 400 | `invalid` | 이메일 또는 비밀번호를 확인해 주세요. 계정 상태를 구분해 노출하지 않음 |
| CSRF 실패 | 403 | `permission_denied` | 다시 시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "이메일 또는 비밀번호를 확인해 주세요."
  }
}
```

이메일 존재 여부·비밀번호 오류·정지 또는 탈퇴 계정은 모두 "이메일 또는 비밀번호를 확인해 주세요"라는 같은 문구로 답한다(X). 칸 오류가 아니므로 `fields`는 생략한다. 실패하면 세션을 만들거나 성공 화면으로 이동하지 않는다.

## 4. 로그아웃

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 마이 화면에서 [로그아웃]을 누를 때 |
| 어디로 | `POST /api/auth/logout/` |
| 로그인 필요 | X. 이미 로그아웃 상태여도 성공 처리(공통 재요청 원칙), CSRF는 검증 |
| 명세 상태 | 초안 |
| 개발 상태 | 미구현. 현재 화면은 세션 종료 없이 로그인 화면으로 이동 |

**보내는 값**

요청 본문 없음. 회원 ID·세션 ID는 보내지 않는다. 쿠키에 연결된 현재 세션만 종료한다.

**받는 값 (200 OK)**

| 이름 | 타입 | 뜻 |
|---|---|---|
| `ok` | 불리언 | 현재 요청의 로그인 세션 종료 처리 완료 |

```json
{ "ok": true }
```

유효한 CSRF 요청이라면 이미 로그아웃된 상태에도 200과 `{ "ok": true }`를 반환한다(X). 화면은 성공 후 회원 정보를 비우고 로그인 화면으로 이동한다. 다른 기기의 세션을 모두 종료하는 기능은 포함하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| CSRF 실패 | 403 | `permission_denied` | 로그아웃에 실패했으니 다시 시도 안내 |
| 서버 오류 | 500 | `server_error` | 로그아웃 성공으로 표시하지 않고 재시도 안내 |

## 5. 내 계정 확인

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 화면 진입·새로고침 시 현재 세션의 로그인 여부와 기본 회원 정보를 확인할 때 |
| 어디로 | `GET /api/auth/me/` |
| 로그인 필요 | O |
| 명세 상태 | 기본만: 계정 정보만 작성 |
| 개발 상태 | 미구현 |

**보내는 값**

요청 본문·경로 변수·쿼리 없음. 회원은 세션으로 식별하며 `userId`를 입력받지 않는다.

**받는 값 (200, 기본 응답 초안)**

공통 회원 응답의 세 필드와 `onboardingCompleted`를 반환한다(R). 이름(닉네임)은 필수 문자열이며 정상 응답에서 null이나 빈 문자열을 반환하지 않는다. 현재 DB 모델은 null을 허용하므로, 기존 데이터에 닉네임이 없는 경우의 보완·전환 절차는 마지막 확인 목록에서 별도로 다룬다. 이 문서 수정으로 DB나 기존 회원 데이터가 변경되지는 않는다.

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진",
  "onboardingCompleted": false
}
```

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 비로그인·세션 만료 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| 서버 오류 | 500 | `server_error` | 회원 정보를 불러오지 못했다는 안내와 재시도 |

```json
{
  "error": {
    "code": "not_authenticated",
    "message": "로그인이 필요해요."
  }
}
```

문구는 화면 안내 예시이며 현재 서버에서 확인된 응답은 아니다. 데이터 없음으로 200과 가짜 회원을 반환하지 않는다.

**로그인 후 화면 이동 — 결정기록 3-3 R**

- H-06: 온보딩 미완료자는 홈 대신 온보딩으로 보낸다. 온보딩을 마쳤지만 예산이 없으면 홈에서 안내 카드를 보여준다. 단순히 예산이 없다고 온보딩 미완료로 판단하지 않는다.
- 로그인과 `/me/` 모두 `onboardingCompleted`를 반환한다. **첫 예산 승인 시 true**이며, false면 온보딩 첫 단계로 보내고 이미 저장한 입력값은 채워서 보여 준다.
- 첫 설정 흐름은 월급 → 고정지출 → 저축 확인 → 방향 → 지킬 돈 → 추천 예산이다. `onboardingStep`이나 몇 번째 단계인지는 1차 응답에 넣지 않는다. 예산이 나중에 없어져도 첫 승인 이력을 단순한 현재 예산 유무로 대체하지 않는다.

## 구현 전 검토·검증 목록

향후 구현 시 검증할 항목이며 현재 테스트 통과 기록이 아니다.

- [ ] 비로그인 상태에서 CSRF 쿠키를 준비할 수 있고, 쿠키만 받았다고 로그인되지는 않는다.
- [ ] 회원가입·로그인·로그아웃에서 CSRF 누락·불일치를 거절한다.
- [ ] 정상 가입, 잘못된 입력, 정규화 후 중복 이메일을 검증한다. 동의한 항목만 보내고 `terms`·`privacy` 중 하나라도 없으면 거절하며, `agreed`를 보내면 400이다(L).
- [ ] 동의 저장 실패 시 회원만 남지 않으며 비밀번호는 해시로 저장된다.
- [ ] 정상 로그인 후 `/me/`가 본인 정보를 반환하고, 잘못된 자격증명은 세션을 생성하지 않는다.
- [ ] 비로그인·만료 세션의 `/me/`는 403 `not_authenticated`를 반환한다.
- [ ] 로그아웃 후 기존 세션으로 `/me/`를 호출할 수 없다.
- [ ] 비밀번호·해시·CODEF 식별값이 응답과 오류에 포함되지 않는다.
- [ ] 칸과 무관한 오류에 `fields`가 없고, 허용하지 않은 요청 필드는 400으로 거절한다.
- [ ] 로그인·`/me/`의 `onboardingCompleted`가 첫 예산 승인 이력과 일치하고, false면 기존 입력을 채운 온보딩 첫 단계로 이동한다(R).
- [ ] 가입 비밀번호 8~25자·세 종류 중 두 종류 조건을 검사하되 로그인에서는 길이·조합을 다시 검사하지 않는다(X).
- [ ] 가입 201·자동 로그인, 로그인 중 가입 400, 이메일 중복 400, 로그인 14일 유지, 정지·탈퇴의 일반 실패 문구, 로그아웃 200을 검증한다(X). 실패 횟수 제한은 1차에 없음(V⑩).
- [ ] 공통 담당자와 비로그인 API 예외·기본 인증 권한 전환을 함께 확인한다.
