> 기준: [공통 규칙](../API_RULES.md), [결정 기록](../결정기록_2026-10-21.md), [API 목록](../머니쿠션_API_명세_목록_2026-10-21.md), [작성 틀](./_TEMPLATE.md)

인증·회원 5개 API의 요청·응답과 예시를 정리한다. 팀원과 논의할 내용은 이 문서 마지막의 **확인 필요 사항 모음**에서 확인한다.

기존 검토 내용과 참조를 유지하기 위해 API 번호 1~10과 소비 분석 A-1~A-7 번호를 그대로 사용한다. 다른 기능의 번호는 위 관련 문서에서 확인한다.

문서 작성 완료와 팀 합의·구현 완료는 다르다. 본문의 **초안 제안·미정·확정 보류** 표시는 유지했다. 기존 모델에 칸이 있다는 사실만으로 CODEF 제공 여부나 사용자 수정 권한이 확정되는 것은 아니다. 예시의 개인정보·금액·UUID는 모두 가상 값이다.

| 번호 | 기능 | 방식·주소 | 목록의 작성 상태 |
|---|---|---|---|
| 1 | 저장 전 보안값 준비 | `GET /api/csrf/` | 지금 |
| 2 | 회원가입 | `POST /api/auth/signup/` | 지금 |
| 3 | 로그인 | `POST /api/auth/login/` | 지금 |
| 4 | 로그아웃 | `POST /api/auth/logout/` | 지금 |
| 5 | 내 계정 확인 | `GET /api/auth/me/` | 기본만 |

비밀번호 재설정·ML 입력 정보·추천 예산·쿠션 배분 규칙·후속 차수 기능은 이번에 정하지 않는다. 온보딩 미완료자는 홈 대신 온보딩으로 이동한다는 원칙은 확정됐지만(H-06), 진행 단계를 어느 API의 어떤 필드로 전달할지는 미정이다(H-08). 금융 동의·계좌·연결 해제·재조회·챗봇 전체 계약은 혜리 담당이며, `chat.md` 최종 편집도 혜리가 한다.

| 근거 | 이 명세에 반영한 내용 |
|---|---|
| ★ 1·2·3 / 체크리스트 | 연결 상태 3가지, 허용하지 않은 요청 항목 400, 주소 ID 형식·소유권·동작 불가 상태 404, 본문 ID 오류 400·전체 미저장 |
| ★ 4 / C-09·C-10·C-11 / 공통 규칙 | 오류 `fields`의 조건부 포함, PATCH의 생략·null 처리, 중복 처리 방지와 요청 번호 생성 시점 |
| H-06 / 화면·흐름 | 온보딩 미완료 시 온보딩으로 이동. 진행 단계 전달 계약(H-08)은 마지막 확인 목록에 보류 |

### 요청·오류·재시도 공통 적용

- 보내는 값 표에 없는 필드와 서버가 정하는 필드(예: `status`)를 보내면 400 `invalid`, 해당 필드에 “이 칸은 보낼 수 없어요.”를 반환한다. 조용히 무시하지 않는다. 아직 확정 보류인 요청 필드는 허용 목록으로 취급하지 않는다.
- 오류에는 `code`·`message`가 항상 있다. `fields`는 입력 칸 오류가 있을 때만 넣고, 로그인 불일치·미인증·404처럼 칸과 무관한 오류에서는 키 자체를 생략한다. 빈 `{}`를 보내지 않는다. 여러 입력 칸의 조합 오류는 `fields.nonFieldErrors`를 사용한다.
- 주소 ID가 잘못된 UUID이거나, 없거나, 남의 항목이거나, 해당 동작을 할 수 없는 상태이면 JSON 404 `not_found`다. 본문 ID의 형식 오류·없는 항목·남의 항목·선택 불가 항목은 400이며, 여러 개 중 하나라도 잘못되면 전체 저장하지 않는다. 존재·소유·선택 가능 여부를 구분해 노출하지 않는다.
- 이미 요청한 상태라면 같은 작업을 다시 반영하지 않고 성공으로 응답한다. 다만 없는 ID·남의 데이터에는 적용하지 않는다. 카드·대출의 구체적인 동작 가능 상태표는 별도 확정이 필요하며, 고정지출의 상태 코드를 그대로 가져오지 않는다.
- 새로 만들기·승인 요청에 쓰는 `Idempotency-Key`는 입력 폼·팝업을 열 때, 버튼 하나로 끝나는 동작은 누를 때 만든다. 처리 중 버튼을 잠그고 응답 전 재전송에는 같은 키를 쓰며, 완료 후 버린다.
- 요청 번호 적용 대상에서는 같은 회원·키·내용에 처음 응답을 재사용하고, 기록된 키로 다른 내용을 보내면 409 `idempotency_conflict`다. 실패한 4xx·5xx는 기록하지 않아 수정 후 같은 키로 재시도할 수 있다. 현재 공통 구현은 비로그인 요청에 적용되지 않으므로 회원가입의 중복 방지 계약은 마지막 확인 목록에 남긴다. 이 규칙만으로 모든 PUT·PATCH에 필수 헤더를 추가하지 않는다.

## 인증·회원 공통 약속

- JSON 요청은 `Content-Type: application/json`을 사용한다. 키는 camelCase이다.
- 로그인은 Django 세션 쿠키를 사용한다. JWT·accessToken·refreshToken을 만들거나 응답에 넣지 않는다.
- `POST` 요청에는 CSRF 쿠키와 이에 대응하는 `X-CSRFToken` 헤더가 필요하다. 로그인 전의 회원가입·로그인 요청도 검증 대상으로 설계한다.
- React의 `apiSend`는 CSRF 쿠키가 없으면 `/api/csrf/`를 먼저 호출하고 요청 헤더를 붙인다. 로그인으로 토큰이 바뀌면 이후 요청은 새 쿠키를 사용한다.
- 응답의 회원 정보는 `userId`, `email`, `nickname`만 공개한다. 비밀번호·비밀번호 해시·CODEF 연결 식별값은 반환하지 않는다.
- 모든 예시의 이메일·비밀번호·UUID는 설명용 가상 값이다.

### 공통 회원 응답

| 이름 | 타입 | null 가능 | 뜻·근거 |
|---|---|---|---|
| `userId` | UUID 문자열 | X | `users.User.user_id`, 서버가 만든 회원 ID |
| `email` | 문자열 | X | 저장된 이메일. 기존 모델은 앞뒤 공백 제거 후 전체 소문자로 저장 |
| `nickname` | 문자열 | X | 이름(닉네임), 필수. 앞뒤 공백 제거 후 1~100자이며 null·빈 문자열·공백만 있는 값은 허용하지 않음 |

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

### 인증·회원 공통 실패 처리

각 API의 실패 표에 더해 다음 규칙을 적용한다.

| 상황 | HTTP 상태 | `error.code` | 화면 처리 |
|---|---|---|---|
| JSON 형식이 깨짐 | 400 | `parse_error` | 요청 오류 안내, 개발 단계에서 요청 확인 |
| CSRF 검증 실패 | 403 | `permission_denied` | 오류 안내 후 다시 시도하도록 함 |
| 지원하지 않는 방식으로 요청 | 405 | `method_not_allowed` | 개발 단계에서 요청 방식 확인 |
| 서버 내부 오류 | 500 | `server_error` | 잠시 후 다시 시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "입력값을 확인해 주세요.",
    "fields": {
      "email": ["이메일 형식을 확인해 주세요."]
    }
  }
}
```

| 이름 | 타입 | 뜻 |
|---|---|---|

## 2. 회원가입

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 회원가입 화면에서 필수 동의를 확인하고 [가입하고 시작하기]를 누를 때 |
| 어디로 | `POST /api/auth/signup/` |
| 로그인 필요 | X, CSRF 검증 필요 |
| 명세 상태 | 초안: 계정 정보와 동의 요청 형식 제안 |
| 개발 상태 | 미구현. 현재 화면은 저장 없이 온보딩으로 이동 |

**보내는 값**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `email` | 문자열 | O | 이메일 형식, 최대 255자(기존 모델). 앞뒤 공백 제거·소문자 정규화 후 중복 검사 | `"sejin@example.com"` |
| `password` | 문자열 | O | 화면 기준 영문·숫자·특수문자를 포함한 8자 이상. 서버 정책·최대 길이는 미정 | `"Example123!"` |
| `nickname` | 문자열 | O | 이름(닉네임), 앞뒤 공백 제거 후 1~100자. 누락·null·빈 문자열·공백만 있는 값은 거절 | `"세진"` |
| `consents` | 객체 배열 | 초안: O | 서비스 약관·개인정보 동의. 아래는 저장 계약의 제안이며 최종 문구·버전은 미정 | 아래 예시 |
| `consents[].purpose` | 문자열 | 초안: O | 화면의 동의 구분 `terms`, `privacy`를 사용하는 제안 | `"terms"` |
| `consents[].documentVersion` | 문자열 | 초안: O | 사용자가 실제 읽은 문서 버전. 화면 시안은 `v1` | `"v1"` |
| `consents[].agreed` | 불리언 | 초안: O | 두 필수 항목 모두 true여야 가입하는 제안 | `true` |

```json
{
  "email": "sejin@example.com",
  "password": "Example123!",
  "nickname": "세진",
  "consents": [
    { "purpose": "terms", "documentVersion": "v1", "agreed": true },
    { "purpose": "privacy", "documentVersion": "v1", "agreed": true }
  ]
}
```

비밀번호 확인은 화면에서 원문과 비교하는 초안이며 별도 요청 필드는 두지 않았다. 나이·성별·급여·금융기관 조회 동의는 포함하지 않는다. 금융 조회 동의는 혜리 담당의 별도 API이다.

**받는 값 (초안: 201)**

생성된 회원 정보를 공통 회원 응답 형태로 반환한다.

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

초안 제안: 회원과 필수 동의 기록은 하나의 트랜잭션으로 저장한다. 동의 시각·원문 해시는 서버가 관리하며 클라이언트가 보낸 값을 신뢰하지 않는다. 자동 로그인 여부는 미정이므로 이 응답만으로 로그인 완료나 다음 화면을 판단하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 이메일 누락·잘못된 형식·길이 초과 | 400 | `invalid` | `fields.email` 표시 |
| 정규화한 이메일이 이미 사용 중 | 초안: 400 | `invalid` | `fields.email`: 사용할 수 없는 이메일 안내 |
| 비밀번호 조건 미충족 | 400 | `invalid` | `fields.password`에 충족하지 못한 조건 표시 |
| 닉네임 누락·null·빈 문자열·공백만 입력·길이 초과 | 400 | `invalid` | `fields.nickname`에 이름(닉네임) 입력 조건 안내 |
| 필수 동의 누락·거부·지원하지 않는 버전 | 초안: 400 | `invalid` | `fields.consents` 표시, 최신 약관 확인 안내 |
| CSRF 실패 | 403 | `permission_denied` | 오류 안내. 회원을 생성하지 않음 |

## 3. 로그인

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 로그인 화면에서 이메일·비밀번호를 입력하고 [로그인]을 누를 때 |
| 어디로 | `POST /api/auth/login/` |
| 로그인 필요 | X, CSRF 검증 필요 |
| 명세 상태 | 초안, 기본 요청·응답은 `_TEMPLATE.md` 기준 |
| 개발 상태 | 미구현. 현재 화면은 인증 없이 홈으로 이동 |

**보내는 값**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `email` | 문자열 | O | 이메일 형식, 최대 255자. 기존 모델의 정규화 방식으로 회원 조회 | `"sejin@example.com"` |
| `password` | 문자열 | O | 작성 틀 기준 8자 이상. 앞뒤 공백을 임의로 제거하지 않음 | `"Example123!"` |

```json
{ "email": "sejin@example.com", "password": "Example123!" }
```

자동 로그인·아이디 저장 체크박스의 API 필드는 아직 정하지 않았다. 사용자 ID나 로그인 성공 여부를 클라이언트가 보내 인증을 대신하지 않는다.

**받는 값 (200)**

공통 회원 응답과 로그인 세션 쿠키를 받는다. 본문에는 토큰이 없다.

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 필수 입력 누락·이메일 형식 오류 | 400 | `invalid` | 해당 `fields`를 입력 칸 아래 표시 |
| 이메일 또는 비밀번호 불일치 | 400 | `invalid` | 이메일 또는 비밀번호를 확인해 주세요 |
| CSRF 실패 | 403 | `permission_denied` | 다시 시도 안내 |

```json
{
  "error": {
    "code": "invalid",
    "message": "이메일 또는 비밀번호를 확인해 주세요."
  }
}
```

이메일 존재 여부와 비밀번호 오류를 각각 다른 메시지로 노출하지 않는다. 실패하면 세션을 만들거나 성공 화면으로 이동하지 않는다.

## 4. 로그아웃

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 마이 화면에서 [로그아웃]을 누를 때 |
| 어디로 | `POST /api/auth/logout/` |
| 로그인 필요 | X. 이미 로그아웃 상태여도 성공 처리(공통 재요청 원칙), CSRF는 검증 |
| 명세 상태 | 초안 |
| 개발 상태 | 미구현. 현재 화면은 세션 종료 없이 로그인 화면으로 이동 |

**보내는 값**

요청 본문 없음. 회원 ID·세션 ID는 보내지 않는다. 쿠키에 연결된 현재 세션만 종료한다.

**받는 값 (초안: 200)**

| 이름 | 타입 | 뜻 |
|---|---|---|
| `ok` | 불리언 | 현재 요청의 로그인 세션 종료 처리 완료 |

```json
{ "ok": true }
```

유효한 CSRF 요청이라면 이미 로그아웃된 상태에도 성공으로 처리한다. 구체적인 성공 상태 200과 `{ "ok": true }` 본문은 초안이다. 화면은 성공 후 회원 정보를 비우고 로그인 화면으로 이동한다. 다른 기기의 세션을 모두 종료하는 기능은 포함하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| CSRF 실패 | 403 | `permission_denied` | 로그아웃에 실패했으니 다시 시도 안내 |
| 서버 오류 | 500 | `server_error` | 로그아웃 성공으로 표시하지 않고 재시도 안내 |

## 5. 내 계정 확인

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 화면 진입·새로고침 시 현재 세션의 로그인 여부와 기본 회원 정보를 확인할 때 |
| 어디로 | `GET /api/auth/me/` |
| 로그인 필요 | O |
| 명세 상태 | 기본만: 계정 정보만 작성 |
| 개발 상태 | 미구현 |

**보내는 값**

요청 본문·경로 변수·쿼리 없음. 회원은 세션으로 식별하며 `userId`를 입력받지 않는다.

**받는 값 (200, 기본 응답 초안)**

공통 회원 응답의 세 필드만 반환한다. 이름(닉네임)은 필수 문자열이며 정상 응답에서 null이나 빈 문자열을 반환하지 않는다. 현재 DB 모델은 null을 허용하므로, 기존 데이터에 닉네임이 없는 경우의 보완·전환 절차는 마지막 확인 목록에서 별도로 다룬다. 이 문서 수정으로 DB나 기존 회원 데이터가 변경되지는 않는다.

```json
{
  "userId": "3f2c9a10-7b63-4ec5-9a12-10c5728baf90",
  "email": "sejin@example.com",
  "nickname": "세진"
}
```

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 비로그인·세션 만료 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| 서버 오류 | 500 | `server_error` | 회원 정보를 불러오지 못했다는 안내와 재시도 |

```json
{
  "error": {
    "code": "not_authenticated",
    "message": "로그인이 필요해요."
  }
}
```

문구는 화면 안내 예시이며 현재 서버에서 확인된 응답은 아니다. 데이터 없음으로 200과 가짜 회원을 반환하지 않는다.

**로그인 후 화면 이동 — 확정 원칙과 응답 보류 구분**

- H-06: 온보딩 미완료자는 홈 대신 온보딩으로 보낸다. 온보딩을 마쳤지만 예산이 없으면 홈에서 안내 카드를 보여준다. 단순히 예산이 없다고 온보딩 미완료로 판단하지 않는다.
- 첫 설정 흐름은 월급 → 고정지출 → 저축 확인 → 방향 → 지킬 돈 → 추천 예산이다. 이 순서를 근거로 단계 코드나 완료 판정 조건을 임의로 만들지 않는다.
- 로그인 응답과 `/me/` 중 어느 곳에서 진행 상태를 주는지, 필드 이름·타입·단계 코드·다음 화면 판정 계약은 H-08로 마지막 확인 목록에 남긴다. 현재 세 필드 응답만으로 화면이 온보딩 완료 여부를 알 수 있다는 뜻은 아니다.

## 구현 전 검토·검증 목록

향후 구현 시 검증할 항목이며 현재 테스트 통과 기록이 아니다.

- [ ] 비로그인 상태에서 CSRF 쿠키를 준비할 수 있고, 쿠키만 받았다고 로그인되지는 않는다.
- [ ] 회원가입·로그인·로그아웃에서 CSRF 누락·불일치를 거절한다.
- [ ] 정상 가입, 잘못된 입력, 정규화 후 중복 이메일, 필수 동의 누락을 검증한다.
- [ ] 동의 저장 실패 시 회원만 남지 않으며 비밀번호는 해시로 저장된다.
- [ ] 정상 로그인 후 `/me/`가 본인 정보를 반환하고, 잘못된 자격증명은 세션을 생성하지 않는다.
- [ ] 비로그인·만료 세션의 `/me/`는 403 `not_authenticated`를 반환한다.
- [ ] 로그아웃 후 기존 세션으로 `/me/`를 호출할 수 없다.
- [ ] 비밀번호·해시·CODEF 식별값이 응답과 오류에 포함되지 않는다.
- [ ] 칸과 무관한 오류에 `fields`가 없고, 허용하지 않은 요청 필드는 400으로 거절한다.
- [ ] 온보딩 미완료와 온보딩 완료·예산 없음을 구분한다(H-08 응답 계약 확정 후 검증).
- [ ] 공통 담당자와 비로그인 API 예외·기본 인증 권한 전환을 함께 확인한다.
