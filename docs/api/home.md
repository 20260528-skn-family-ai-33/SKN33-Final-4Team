### 10/21 결정

| 번호 | 질문 | 결정 |
|---|---|---|
| H-01 | 월급이 일찍 · 늦게 들어오면 주기는? | **주기는 항상 사용자가 설정한 월급날에 바뀐다.** 실제 입금은 주기를 바꾸지 않고 상태로만 알린다. 미리 들어온 월급은 지난 주기 예산에 넣지 않고 따로 빼 두며, 늦게 들어오는 동안은 "아직 안 들어왔어요"로 알린다 (아래 ①). 처음엔 '입금일에 새 주기'로 정했다가 같은 날 바꿈 — 늦게 오면 지난 주기가 길어지고, 그사이 쓴 이번 달 생활비가 지난달 초과로 잡혀서 |
| H-02 | 저축용으로 고른 입출금 계좌도 잔액 합계에 넣나 | **넣는다.** 화면 이름이 '입출금 계좌 잔액'이고, 쓸 수 있는 돈은 예산 영역이 따로 보여 준다 |
| H-03 | 확인할 거래 수는 어떻게 세나 (10/22 혜리) | **전체 기간**에서 카테고리가 '확인 필요'(`UNCLASSIFIED`)인 **소비 거래** 수. 거래 목록 `GET /api/finance/transactions/?category=UNCLASSIFIED`(기간 없이)의 `summary.needsReviewCount`와 같은 값이다. 목록은 최신순 |
| H-05 | 출금일 모르는 고정지출을 홈에서 알리나 | **알린다.** `needsPaydayCount` → "출금일을 확인할 고정지출 N건 ›" 알림 줄 |
| H-06 | 예산이 없을 때 · 온보딩 전 홈 | ① 예산이 없으면(`budget: null`) 파란 카드 자리에 **안내 카드**. ② 온보딩을 안 끝냈으면 **홈을 열지 않고 온보딩으로 보낸다**(화면이 판단, 아래 ⑤) |
| H-07 | DB 코드 (10/22 혜리 · 나은) | API 값 = DB 값, 소문자 영어. 이 명세가 쓰는 것: 입출금 계좌 `bank_account.account_type = demand`(CODEF 예금 구분 `11`), 연결 상태 `connection.status` = `connected` · `relogin` · `disconnected`, 입금 `financial_transaction.direction = in`. 전체 코드표는 [결정기록](../결정기록_2026-10-21.md) 3-1 |

## 홈 화면 보기

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 하단 탭 [홈]을 누르거나 앱을 열 때 홈 화면에 보일 값을 한 번에 받는다 |
| 어디로 | `GET /api/home/` |
| 로그인 필요 | O · 세션 쿠키 (읽기라 CSRF 없음) |
| 명세 상태 | 초안 (기본만) |
| 개발 상태 | DB 구현 (`backend/budgets/home.py`) |

**보내는 값**

없음. 쿼리 파라미터도 받지 않는다. 기준 날짜는 서버의 오늘(한국 시간)이다.

```http
GET /api/home/
```

**받는 값 (200 OK)**

| 이름 | 타입 | 뜻 |
|---|---|---|
| `period` | 객체 또는 `null` | 지금 급여 주기. 급여일을 아직 안 넣었으면 `null` |
| `period.startDate` | 날짜 | 주기 시작일 = 이번 월급날 (설정한 급여일, 없는 날이면 말일), `YYYY-MM-DD` |
| `period.endDate` | 날짜 | 주기 마지막 날 = 다음 월급날 전날 |
| `period.nextPayday` | 날짜 | 다음 월급날 |
| `period.dday` | 정수 | 다음 월급날까지 남은 날 (1 이상). 화면 "월급날 D−4" |
| `period.salaryState` | 문자 | 이번 주기 월급 상태 (R12). `received` 인정된 급여 있음(사용자 확인 · 자동 인정) · `needs_check` 판단 없는 후보만 있음 — 받음 · 아직으로 단정하지 않음 · `waiting` 후보도 없음 · `unknown` 월 실수령액을 안 넣어서 후보를 찾을 수 없음 |
| `period.salarySource` | 문자 또는 `null` | `user` 사용자 확인이 하나라도 있음 · `auto` 자동 인정만 · 인정된 급여가 없으면 `null` |
| `period.salaryAmount` | 정수 또는 `null` | 이번 회차 인정 급여 합계(분할 급여는 합계) = `budget_cycle.confirmed_income` |
| `period.salaryCheckCount` | 정수 | 인정된 급여가 없는 구간(이번 · 다음 조기)의 확인 필요 후보 수. 화면 알림 "월급으로 보이는 입금이 있어요" |
| `period.salaryReceivedOn` | 날짜 또는 `null` | 이번 회차에 인정된 급여 중 가장 이른 입금일. 월급날보다 일찍 들어왔으면 그 날짜(예: 명절 전 9/18) |
| `period.nextSalaryEarlyOn` | 날짜 또는 `null` | **다음 회차로 인정된 조기 급여의 입금일** (후보만 있으면 `null`). 화면 "월급이 12/18에 미리 들어왔어요. 12/25부터 예산에 넣을게요" |
| `period.salaryGap` | 객체 또는 `null` | 11/13. 이번 회차에 인정된 월급이 등록 실수령액과 1만원 이상 · 3% 이상 다르고 아직 그 금액으로 답하지 않았으면 `{diff, received, registered, basis}`. 화면 "월급이 300,000원 적게 들어왔어요. 예산을 조정할까요?" 칸 뜻 · 답하기는 [salary.md 월급 차이 안내](salary.md#월급-차이-안내-1113) |
| `balance` | 객체 | 입출금 계좌 잔액 요약 (항상 있음) |
| `balance.total` | 정수 또는 `null` | 잔액을 아는 계좌들의 잔액 합계(원). 셀 계좌가 없거나 전부 잔액을 모르면 `null` (0으로 채우지 않음) |
| `balance.accountCount` | 정수 | 합계 대상 계좌 수 (잔액을 모르는 계좌 포함). 화면 "입출금 계좌 2개" |
| `balance.unknownCount` | 정수 | 그중 잔액을 아직 못 받은 계좌 수. 1 이상이면 "잔액을 못 불러온 계좌가 있어요" |
| `balance.reloginCount` | 정수 | 그중 다시 연결이 필요한 계좌 수(`relogin`). 마지막으로 받은 잔액은 합계에 넣고 "다시 연결 필요"를 같이 보여 준다 |
| `balance.asOf` | 시각 또는 `null` | 기준 시각 = 합계에 들어간 계좌 중 **가장 오래된** 정상 조회 시각. 화면 "오늘 09:30 기준" |
| `pendingCount` | 정수 | 카테고리를 확인할 거래 수. 0이면 알림 줄을 숨김 |
| `needsPaydayCount` | 정수 | 출금일을 모르는 **확정** 고정지출 수. 0이면 알림 줄을 숨김. 누르면 고정지출 화면 |
| `mustPay` | 배열 | 이번 주기에 아직 안 나간 꼭 나갈 돈. 없으면 `[]` |
| `mustPay[].dueId` | UUID | 납부 예정 ID |
| `mustPay[].type` | 문자 | `recurring`(고정지출) · `card_bill`(카드 청구서) · `loan`(대출 상환) (10/22 결정 Q) |
| `mustPay[].sourceId` | UUID | 원래 항목 ID. `recurring` = 고정지출 `recurringId`(누르면 고정지출 화면) · `card_bill` = 청구서 `billId`(누르면 카드 청구서 팝업, `GET /api/finance/card-bills/<id>/`) · `loan` = `loanId`(누르면 대출 확인 화면. 팝업의 [납부 거래 확인]은 `dueId`로 `GET /api/finance/loan-dues/<dueId>/payments/`, loans.md 12 · 11/06) |
| `mustPay[].name` | 문자 | 표시 이름. 고정지출은 사용자가 붙인 이름 |
| `mustPay[].dueDate` | 날짜 | 나갈 날 (그 달에 없는 날이면 말일) |
| `mustPay[].amount` | 정수 | **아직 안 나간 금액** = 예정 금액 − 이미 낸 금액. 일부만 나갔으면 남은 금액 |
| `mustPay[].paymentState` | 문자 | `unpaid`(미납 — 출금일이 지났으면 "출금 확인 중") · `partial`(일부 납부 — 연결된 금액 합계가 예정 금액의 90%(올림) 미만. 90% 이상이면 `paid`로 빠짐, 11/4) · `needs_review`(**미납 확인 필요** — 출금일 +3일이 지나도 출금을 못 찾음. 카드 청구서는 다른 경로로 냈을 수 있어 화면에 **납부 확인 필요**로 표시, 11/06) |
| `mustPay[].userChecked` | 참/거짓 | 11/06: `card_bill`의 `amount`가 사용자가 알려 준 '앞으로 낼 금액'인지 (cards.md '카드 청구서 납부 확인'). '전부 냈어요'로 확인한 청구서는 목록에서 빠진다. 화면 '사용자 확인'. 그 밖은 `false` |
| `mustPay[].isEstimated` | 참/거짓 | 금액이 **예상**인지. `card_bill`이고 청구서가 아직 확정 전(`confirmationStatus` ≠ `confirmed`)이면 `true` → 화면 "예상" 표시. 고정지출 · 대출은 항상 `false` (10/22 결정 Z) |
| `mustPay[].paymentAccount` | 객체 또는 `null` | 출금 계좌 `{ accountId, displayName, status }` ([계좌 · 카드 표시](../API_RULES.md#계좌--카드-표시)). 결제 수단 모름이면 `null` |
| `budget` | 객체 / `null` | **이번 주기 승인(`approved`) 예산이 있으면 채움** (11/3, H-06). 승인 전 초안(`draft` · `validated`)은 넣지 않는다. 없으면 `null`. 값은 예산 화면(`GET /api/budgets/`)과 같은 계산 |

| `budget.livingBudget` | 정수 | 승인 생활비 (= 예산 화면 `living.budget`) |
| `budget.livingLeft` | 정수 | 남은 생활비 (= `living.remaining`, 0 아래로 안 내림). 생활비 사용액은 고정지출 · 예산 밖 카테고리(주거·통신, 여행·숙박) 지출을 뺀 값 (budgets.md R-13) |
| `budget.livingPct` | 정수 | 쓴 돈 ÷ 생활비 × 100, 반올림. **100을 넘어도 그대로**(화면 막대만 100에서 멈춤). 생활비 0원이면 쓴 돈이 있을 때 100, 없으면 0 |
| `budget.spare` | 정수 | 남은 여윳돈 (= `overspend.spareRemaining`) |
| `budget.daily` | 정수 / `null` | 하루에 쓸 수 있는 돈 = `livingLeft ÷ daysLeft` (원 미만 버림). `daysLeft`가 0(주기 마지막 날)이면 `null` → 화면 "—" |
| `budget.cardNotes` | 배열 | 승인 예산의 계산 당시 카드 안내. `first_bill_unavailable`이면 이전 주기 카드값이 미반영되어 생활비·하루 금액이 실제보다 클 수 있음을 표시한다. 청구서 조회만으로 지우지 않고, 같은 주기 재추천·승인 후 갱신한다. |
| `budget.cardBillsReady` | 배열 | 11/12. `cardNotes`의 `first_bill_unavailable` 카드 중 **지금은 청구서가 나온** 카드 ID. 있으면 화면 띠가 '새 카드 청구서가 나왔어요'로 바뀌고 바로 재추천으로 이동한다. 계산 기준은 [budgets.md](budgets.md) 11/09 절. 없으면 `[]` |
| `budget.daysLeft` | 정수 | 오늘까지 쓴 돈을 뺀 뒤 나누는 날 수 = 다음 월급날 − 오늘 − 1 (채팅 소비 분석의 남은 일수와 같음) |
| `budget.outOfBudgetAllocated` | 정수 | 이전 기준 예산의 주거·통신 · 여행·숙박 배정 (예산 화면 `budget.outOfBudgetAllocated`와 같음, N-F1). 0보다 크면 파란 카드 안에 재추천 안내. `livingBudget`은 이 금액을 포함한 저장값 그대로 |
| `budget.overCategories[]` | 배열 | 예산을 넘긴 카테고리 (11/11). 칸: `category` · `categoryName` · `allocated`(배정) · `spent`(쓴 돈) · `over`(= `spent − allocated`). **쓴 돈이 배정을 1원이라도 넘으면** 넣고, 배정이 0원인 카테고리는 넣지 않는다. 많이 넘긴 순. 없으면 `[]`. 값은 예산 화면 `categories[]`와 같은 계산 |
| `budget.nag` | 문자열 / null | 11/13. 예산을 자주 바꾸면 "이번 달 예산을 여러 번 바꿨어요" (예산 화면 `nag`와 같은 규칙 · 문구). 화면은 종 알림 한 줄, 누르면 예산 화면 |
| `budget.bigSpendings[]` | 배열 | 생활비 예산 대비 큰 지출 (11/11, 돌발 지출 감지 1단계). 이번 주기(시작일 ~ 오늘)에 **한 건이 `livingBudget`의 10% 이상**(원 미만 올림, 취소분을 뺀 금액)인 거래. 칸: `transactionId` · `occurredOn` · `merchantName`(없으면 `""`) · `amount` · `kind`(`spending` / `transfer`) · `category` · `categoryName`(이체는 둘 다 `null`). 최신순(같은 날은 큰 금액 먼저). 없으면 `[]` |

### 계산 규칙

**① 급여 주기 (`period`) — BUD-004 · H-01**

> **주기는 항상 사용자가 설정한 월급날에 바뀐다.** 실제 입금은 주기를 바꾸지 않고, 들어왔는지 · 미리 들어왔는지 · 아직인지를 **알려 주는 데만** 쓴다.

*월급날*

- 기준은 `FinancialProfile.payday`(매월 급여일 1~31). 비어 있으면 `period: null`, `mustPay: []`.
- 그 달에 급여일이 없으면 **그 달 말일**(31일 → 9/30, 2/28, 윤년 2/29). [공통 규칙 '매월 N일'](../API_RULES.md#한눈에-보기)과 같다. 주말 · 공휴일 이동은 계산하지 않는다.
- 오늘이 이번 달 월급날 **이후거나 같은 날**이면 이번 달 월급날이 시작일, 아니면 지난달 월급날이 시작일이다. 다음 월급날 전날이 마지막 날이다.

| 급여일 | 오늘 | startDate | endDate | nextPayday | dday |
|---|---|---|---|---|---|
| 25 | 10/21 | 09-25 | 10-24 | 10-25 | 4 |
| 25 | 10/25 (월급날, 입금 전이어도) | 10-25 | 11-24 | 11-25 | 31 |
| 31 | 2027/02/10 | 2027-01-31 | 2027-02-27 | 2027-02-28 | 18 |

*월급 입금 찾기* — **R12(11/06)부터 아래는 '후보'를 찾는 조건이다.** 후보는 자동으로 받음 처리하지 않는다. 확인 · 자동 인정 규칙은 [salary.md](salary.md#급여-확인--자동-인정-r12)

| 조건 | 값 |
|---|---|
| 어디로 | 내 관리 대상 입출금 계좌(`account_type = demand`, 연결 해제 제외)로 들어온 **입금**(`direction = in`) |
| 얼마 | **월 실수령액(`monthly_take_home_income`)의 80% 이상** — 중고거래 같은 작은 입금은 월급으로 보지 않는다 |
| 제외 | 취소 거래 · 저장된 내 계좌 이체 판정(`own_transfer` 유형 또는 R11 `OWN_TRANSFER` 연결) · 납부에 연결된 거래 · 저축 · 상환 · 카드값. **같은 날 같은 금액 출금이 있다는 이유만으로는 빼지 않는다** (R12) |
| 이번 주기 월급 | 이번 월급날 **7일 전**(명절에 당겨 주는 경우) ~ 다음 월급날 8일 전 사이 (판단 없는 후보가 여러 건이어도 하나를 고르지 않는다) |
| 다음 달 월급이 미리 옴 | 다음 월급날 7일 전 ~ 오늘 사이 → 인정되면 다음 회차에 붙고 `nextSalaryEarlyOn` |

*경우별 처리* (급여일 25일, 실수령액 250만 원)

| 경우 | 주기 | `salaryState` · 표시 | 예산(ML 후)에서 할 일 |
|---|---|---|---|
| 제때 (25일 입금) | 25일에 새 주기 | `received` | 평소대로 |
| **미리** (명절 전 12/18 입금) | 12/24까지 지난 주기, **12/25에 새 주기** | 지난 주기: `nextSalaryEarlyOn = 12/18` "미리 들어왔어요" / 새 주기: `received` · `salaryReceivedOn = 12/18` | 지난 주기의 쓸 수 있는 돈에 이 월급을 **넣지 않는다** (따로 빼 둠, BUD-004) |
| **늦게** (10/30 입금, 회사 사정 · 명절 후) | 10/25에 새 주기 | 10/25~29 `waiting` "월급이 아직 안 들어왔어요" → 10/30부터 `received` | 들어오기 전까지 오늘 쓸 수 있는 돈을 **실제 잔액을 넘지 않게** |
| 끝까지 안 들어옴 | 다음 월급날에 또 새 주기 | 계속 `waiting` | 위와 같음 |
| 실수령액을 안 넣음 | 날짜대로 | `unknown` | — |

- **월급날 ~ 실제 입금일 사이에 쓴 돈은 새 주기 생활비다.** 예산은 '어느 기간에 썼나'를 보지 '어느 돈으로 냈나'를 보지 않는다. 10/25~29에 쓴 밥값은 월급이 언제 들어오든 이번 달 생활비다.
- **저장**: 주기는 `budget_cycle`에 남긴다. `starts_on` = 월급날, `ends_before` = `expected_payday` = 다음 월급날, `status` = 지금 주기 `active` · 끝난 주기 `closed`(`budget_cycle.status` 코드 — 이 명세에서 정함), `confirmed_income` = 이번 회차에 **인정된** 급여 합계(사용자 확인 · 자동 인정, 없으면 비움). 홈을 열 때 이번 주기 값만 다시 쓴다 — R12 전에 자동 추정으로 채운 이번 주기 값은 확인 전이면 비워지고, 지난 주기 값은 그대로 둔다.
- **언제 확인하나**: 매일 도는 작업 없이 **홈 · 예산을 열 때** 확인한다(C-15와 같은 방식). 같은 주기는 `budget_cycle`(회원 · 시작일) UNIQUE로 한 번만 생긴다.
- 이번 명세의 '이번 주기'는 [fixed.md](fixed.md)의 '이번 주기(급여일 ~ 다음 급여일 전날)'와 같다.

**② 계좌 잔액 (`balance`) — H-02**

| 들어가는 계좌 | 빠지는 계좌 |
|---|---|
| 내 계좌 · 관리 대상으로 고른 것(`is_selected`) · 입출금 계좌(`account_type = demand`) — **저축 용도로 고른 입출금 계좌도 포함** | 관리 대상이 아닌 계좌 · 연결 해제(`disconnected`)된 계좌 · 예적금 · 대출 · 외화 계좌 |

- 잔액은 `BankAccount.balance`(잔액)를 쓴다. 출금 가능액(`withdrawable_amount`)은 쓰지 않는다.
- 잔액을 못 받은 계좌(`balance`가 비어 있음)는 **0으로 더하지 않고** `unknownCount`로 센다(UI-002: 미수집 잔액은 값 없음).
- 다시 연결이 필요한(`relogin`) 계좌는 마지막으로 받은 잔액을 합계에 넣고 `reloginCount`로 센다. 화면은 "다시 연결 필요"와 기준 시각을 같이 보여 준다.
- 고정지출 결제 계좌 선택에서는 저축 용도 계좌를 빼지만(fixed.md), 잔액 합계에는 넣는다. 잔액은 '내 입출금 계좌에 있는 돈'이고, '쓸 수 있는 돈'은 예산 영역이 따로 보여 주기 때문이다.
- **화면에서 금액을 따로 계산하지 않는다**(UI-002). 합계 · 개수는 서버가 준 값을 그대로 쓴다.

**③ 알림 줄 수 (`pendingCount` · `needsPaydayCount`)**

- `pendingCount` (H-03): **전체 기간**에서 카테고리가 '확인 필요'(`UNCLASSIFIED`)인 소비 거래 수. 거래 목록에 들어가는 거래와 같다(출금 중 소비 거래만, 카드값과 같은 구매로 중복된 계좌 출금은 제외). 서버는 거래 목록 `GET /api/finance/transactions/?category=UNCLASSIFIED`(기간 없이)의 `summary.needsReviewCount`와 **같은 조회**로 센다 — 홈 알림을 누르면 이 목록(최신순)으로 가므로 숫자와 목록이 항상 같다. 지난달에 처리하지 못한 거래도 사라지지 않는다. 거래 분류 ML 전에는 대부분의 소비 거래가 '확인 필요'라 숫자가 클 수 있다.
- `needsPaydayCount` (H-05): 내 고정지출 중 **확정(`confirmed`)이고 출금일(`payment_day`)이 비어 있는 것**의 수. 계좌 · 카드 · 모름 모두 센다(카드도 출금일이 있어야 '이 결제가 맞나요?'를 물을 수 있음, fixed.md C-14). 후보 · 중지 · 무시는 세지 않는다.
- 화면: 두 줄 모두 0이면 숨긴다. "카테고리를 확인할 거래 4건 ›" → 거래 목록, "출금일을 확인할 고정지출 1건 ›" → 고정지출 화면.

**④ 꼭 나갈 돈 (`mustPay`) — COM-004 · C-08 · C-15**

- 납부 예정(`PaymentDue`) 중 아래를 모두 만족하는 것만 보여 준다.

| 조건 | 값 |
|---|---|
| 내 것 | `user` = 로그인한 회원 |
| 유효 | `obligation_state = active` (취소된 것 제외) |
| 아직 다 안 냄 | `payment_state` 가 `unpaid` · `partial` · `needs_review` (`paid` 제외) |
| 언제 것까지 | **이번 주기 회차 + 지난 주기에 아직 다 안 낸 회차**. 지난 주기 미납은 **다음 월급날 전까지(이번 주기 내내)** 보여 주고, 새 주기가 시작되면(그다음 월급날) 홈에서 빠진다. 기록은 `needs_review`로 남는다 (10/22 PR #26 리뷰, 아래 '미납 안내') |
| 종류 | `recurring`(고정지출) · `card_bill`(카드 청구서) · `loan`(대출 상환) — 아래 '카드 청구서 · 대출' |

- **카드 청구서 · 대출 (10/22 결정 Q, H-04)** — 고정지출과 같은 모양, 같은 미납 안내 규칙.

  | | `card_bill` 카드 청구서 | `loan` 대출 상환 |
  |---|---|---|
  | `name` | "{카드사} 카드 청구서" (예: "신한카드 청구서") | "{기관} {상품명}" (예: "KB국민은행 신용대출") |
  | `dueDate` | 청구서의 **출금 예정일**, 없으면 **결제 예정일** (11/5 나은: 카드는 결제일에 출금됨, 매칭 · 선차감과 같은 기준) | 대출의 **매월 납부일**(이번 주기 날짜, 없는 날은 말일) |
  | `amount` | **청구 총액 − 이미 낸 금액** | **월 상환액 − 이미 낸 금액** |
  | `paymentAccount` | 청구서의 결제 계좌, 없으면 그 카드사 카드의 결제 계좌가 **하나로 정해질 때만**. 실제 출금을 찾으면 그 출금 계좌 | 납부 계좌(모르면 `null`) |
  | 보이는 조건 | 출금 · 결제 예정일 중 하나를 알고 청구액이 0원보다 클 때 | 월 상환액 + 납부일이 **둘 다** 있을 때만(결정 P) |
  | 예상 표시 | 청구서가 확정 전이면 `isEstimated: true` → "예상" (결정 Z) | 없음 |

  - **첫 청구서 미리 떼기(C-17)**는 예산 계산(ML 후)의 일이다. 홈은 위 금액을 그대로 보여 준다. 미리 뗄 돈 = 첫 청구서 총액 − 이번 주기 시작일 이후 그 카드로 쓴 돈(결정기록 Q).
  - 카드로 내는 고정지출은 카드 청구서 안에 있으므로 `recurring`으로 따로 나오지 않는다(위와 같음).
  - **카드 청구서 납부 예정은 출금 전에 만든다 (R04, 11/5)** — 카드 다시 불러오기에서 청구서를 저장할 때와 홈을 열 때 `finance/card_payments.py` `sync_bill_dues`가 저장된 청구서로 만들고 고친다(외부 조회 없음, 새 승인 거래가 없어도). 자세한 규칙은 [cards.md](cards.md) '청구서 → 납부 예정'.
- 회차(납부 예정 하나)는 주기와 같은 구간(월급날 ~ 다음 월급날 전날)으로 나눈다. 새 주기가 시작되면(월급이 아직이어도) 새 회차 것을 만든다.
- 정렬: 나갈 날(`dueDate`)이 빠른 순 → 금액이 큰 순.
- **완납 처리한 대출(`status=repaid`)의 회차는 여기 없다**(11/9, loans.md 13번). 회차 자체는 남아 대출 화면 [납부 거래 확인]에서 정리한다.
- **카드로 내는 고정지출은 여기 없다.** 카드 청구서 안에 들어 있어서 따로 세지 않는다(C-08). 출금일을 모르는 고정지출도 납부 예정이 없어서 여기 없고, 대신 `needsPaydayCount`로 알린다(H-05).
- **미납 안내 (10/22 PR #26 리뷰)** — 출금 **연결** 기간과 미납 **안내** 기간을 나눈다.

  | 시점 (출금일 25일 예) | 상태 | 홈 '꼭 나갈 돈' 표시 |
  |---|---|---|
  | 25일 전 | `unpaid` | "10.25 · 국민 급여통장" |
  | 25 ~ 28일 (출금일 +3일까지) | `unpaid` | **"출금 확인 중"** — 출금 연결(±3일)을 기다리는 중. 기억한 출금만 자동 연결, 처음 보는 출금은 고정지출 화면에서 확인(11/3) |
  | 29일부터 다음 월급날 전까지 | **`needs_review`** | **"미납 확인 필요 ›"** — 누르면 고정지출 화면의 [고르기] |
  | 다음 월급날부터 | `needs_review` 그대로 | 홈에서 빠짐 (기록은 남음) |

  - `unpaid` → `needs_review` 바꾸기는 매일 도는 작업 없이 **홈 · 고정지출을 열 때** 한다(C-15와 같은 방식).
  - 늦게 낸 출금(±3일 밖)은 자동으로 연결하지 않는다. 사용자가 고정지출 화면의 [고르기]로 고르면 `paid`가 되어 홈에서 빠진다([fixed.md](fixed.md) '미납 확인 필요 회차의 고르기').
  - 1차에는 "따로 냈어요"처럼 끄는 버튼이 없다. 그래서 다음 월급날까지만 보여 준다.
- 주기 중간에 홈을 처음 열면 이미 지난 날짜의 회차(예: 9/30 통신비)가 `unpaid`로 생길 수 있다. 실제 출금이 기억한 출금이면 출금 매칭이 연결해 `paid`로 바꾸고(처음 보는 출금은 사용자가 확인), 그 전까지는 "출금 확인 중"이다.
  - **'지난 주기'는 저장된 마지막 주기가 아니라 실제 지난 급여 주기**다(이번 주기 시작일의 한 달 전 월급날 ~). 한 달을 건너뛰고 접속하면 그 지난 주기 회차가 아직 없으므로 홈을 열 때 함께 만들고, 출금일 ±3일의 기억한 출금 1건이면 자동 연결한다(11/3, [fixed.md](fixed.md) '계좌'). 두 주기 전 회차는 홈 · 납부 후보에 나오지 않는다 (10/27 PR #46 리뷰).
  - 단, **고정지출을 등록(확정)하기 전 출금일**이면(등록한 첫 달) [fixed.md](fixed.md) 규칙대로 맞는 출금이 있을 때만 회차를 만들고, 없으면 다음 회차부터 보여 준다. 새 고정지출은 기억한 출금이 없으므로 "냄"으로 바로 연결하지 않고 '미납 확인 필요'로 물어본다(11/3). **11/9: 등록 전 출금일이 지난 주기면 맞는 출금이 있어도 회차를 만들지 않는다** — 이미 나간 돈이 '꼭 나갈 돈'에 '출금 확인 필요'로 하나 더 보여 같은 고정지출이 두 번 나가는 것처럼 보였다. 이번 주기의 등록 전 출금일은 위 규칙 그대로. 등록한 뒤의 출금일은 앱을 늦게 열어도 만들어 미납을 알린다 (10/27).
- **이 API를 부르면 이번 회차 납부 예정이 없는 확정 고정지출의 납부 예정을 먼저 만든다**(C-15: 다음 주기 것은 그 주기에 홈 · 예산을 처음 열 때 만든다). 같은 회차는 `occurrence_key`(회원 · 회차) UNIQUE로 한 번만 생기므로 여러 번 불러도 결과가 같다. 대상은 계좌 · 결제 수단 모름이고 출금일이 있는 확정 고정지출이다.

**⑤ 예산 영역 (`budget`) · 온보딩 — H-06**

- **11/3**: 이번 주기 **승인(`approved`) 예산이 있으면** `budget` 객체를 채운다(칸은 위 표). DB의 승인 예산만 읽고 에이전트 · 추천 엔진을 부르지 않는다. 초안(`draft` · `validated`)은 홈에 보이지 않는다. 더 써도 되는 돈 · 쿠션 상태는 아직 정하지 않는다.
- 계산은 예산 화면(`budgets/overview.py` `budget_data`)을 그대로 쓴다. 사용액 기간은 주기 시작일 ~ 오늘로 예산 화면 · 채팅과 같다.
- 화면: 파란 카드 제목은 **"하루에 쓸 수 있는 돈"**(오늘 쓴 돈까지 빼고 내일부터 나눈 금액이라). `daily`가 `null`(마지막 날)이면 "—". [계산 근거]는 `livingLeft ÷ daysLeft`를 그대로 보여 준다. `outOfBudget.total > 0`이면 계좌 잔액 카드 안 둘째 줄(구분선)에 "예산 밖 지출 N원 ›"을 두고, 누르면 카테고리별 금액(`outOfBudget.categories`)과 "생활비 예산에 넣지 않고 따로 보여 드려요" 안내를 팝업으로 보여 준다(11/3 — 파란 카드 안 문장에서 옮김).
- 화면 (11/11): `overCategories`의 카테고리마다 종 알림에 한 줄 — "식비 예산을 12,000원 넘었어요 ›". 누르면 예산 화면. 읽음 처리는 없고, 넘긴 상태인 동안 계속 보인다(예산을 조정하거나 새 주기가 되면 사라짐). 푸시 알림은 없다. 예산 화면은 같은 기준으로 넘긴 카테고리의 막대를 라임색으로 바꾸고 '남은 N원' 자리에 'N원 초과'를 보여 준다.
- **큰 지출 (`bigSpendings`, 11/11)**: 대상은 ① 생활비 쪽 소비 — 고정지출로 연결된 거래와 예산 밖 카테고리(주거·통신, 여행·숙박)는 뺀다. '확인 필요' 소비는 넣는다. ② 남에게 보낸 이체(`transfer`, 출금) — 납부(고정지출 · 대출 · 카드 청구서)로 연결된 이체는 뺀다. 내 계좌 간 이체 · 저축 · 카드값 · 대출 상환은 거래 유형이 달라 들어오지 않는다. **알리기만 하고 어떤 숫자도 바꾸지 않는다**(소비는 소비 그대로, 이체는 소비 아님 그대로). 답을 저장하지 않으므로 이번 주기 동안 계속 보인다. 기준 10%는 `budgets/home.py`의 `BIG_SPENDING_PCT`(팀 확정 전 시작값). 같은 카테고리 평소 금액과 비교하는 필터 · '어떤 돈인가요?' 질문 · 조정 연결은 다음 단계.
- 화면 (11/11, **11/13 잠시 뺌** — 기준 10%가 아직 어색해서 종 알림에 올리지 않는다. API 값은 그대로 준다): `bigSpendings`의 거래마다 종 알림에 한 줄 — "11.10 홍길동 300,000원 · 큰 이체가 있었어요 ›"(소비는 "큰 지출이 있었어요"). 아이콘은 소비 = 카테고리, 이체 = 보내기. 누르면 거래 내역.
- 화면: `budget`이 `null`이면 파란 카드 자리에 **안내 카드**를 보여 준다 — "예산을 만들면 여기에 하루에 쓸 수 있는 돈이 보여요 [예산 만들기]".
- **온보딩을 안 끝낸 회원은 홈을 열지 않는다.** 화면이 로그인 응답 · `GET /api/auth/me/`의 **`onboardingCompleted`**가 `false`면 온보딩으로 보낸다(10/22 결정 R — 첫 예산을 승인하면 `true`). 이 API는 막지 않는다(온보딩 중에 불러도 위 규칙대로 답함).

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 로그인 안 됨 · 세션 만료 | 403 | `not_authenticated` | 로그인 화면으로 ([API_RULES](../API_RULES.md#에러-응답--항상-이-모양): 세션 로그인은 401이 아니라 403) |

- 보내는 값이 없으므로 `400`은 없다.
- 계좌 조회가 일부 실패해도 **오류로 답하지 않는다.** 마지막으로 받은 잔액과 기준 시각, `unknownCount` · `reloginCount`로 상태를 알려 준다(UI-002: 일부 조회 실패는 마지막 값 + 갱신 실패 표시).
- 급여일 미입력 · 계좌 없음 · 납부 예정 없음 · 월급 못 찾음도 오류가 아니라 `null` · `0` · `[]` · `salaryState`로 준다.
