- C-01 해결(10/21): 카테고리는 10개 + `ETC` 중 필수(`UNCLASSIFIED` 제외), 항목 이름으로 미리 선택하되 서버는 코드를 검사한다. 요청은 `category`, 응답은 `category` + `categoryName`이며 저축·투자·대출 상환·카드값은 고정지출에서 제외한다.
- C-02 해결(10/21): 결제 수단은 계좌·카드·모름 중 선택이며 동시 지정은 불가하다. 선택 조건·서버 표시 이름·연결 상태 응답을 확정하고, 연결 해제 후에도 고정지출과 고정비를 유지한다. 카드 거래와 고정지출의 연결은 아래 공통 기준을 따른다.
- C-03 해결(10/21): 금액은 1,000원 이상 100,000,000원 이하 정수, 출금일은 1~31 또는 `null`(모름)이다. 해당 월에 없는 날은 말일로 보고 주말·공휴일 이동은 계산하지 않는다(`BUD-004`). 고정지출 합계가 월급보다 커도 저장하며, 예산을 만들 때 부족액으로 안내한다(`BUD-001`).
- C-04 해결(10/21): 고정지출은 매월만 받으며 주기 칸은 없다. 상태·출처·확정 시각은 서버가 정하고, 직접 추가는 즉시 `confirmed`·`manual`, 중지는 `stopped`로 처리한다. 예산 대상은 `confirmed`이다.
- C-05 해결(10/21): PATCH에서 안 보낸 칸은 유지하고 `null`은 비운다. 비울 수 있는 칸은 `paymentDay`·`paymentAccountId`·`paymentCardId`·`evidenceTransactionId`이며, `name`·`amount`·`category`의 `null`과 모든 칸의 빈 글자 `""`는 `400 invalid`이다. 결제 수단 변경 시 두 ID를 함께 보내며 서버가 다른 칸을 자동으로 지우지 않는다.
- C-06 해결(10/21): 금액 수정은 이번 주기·앞으로의 미납 회차에만 반영하고, 중지는 이번 주기 미납 납부 예정을 취소한다. 반복 중지도 `204`이며 다시 시작 API는 1차에 없다. 과거 금액은 지난 회차·승인 예산에 남기고, 승인 전 초안은 재계산하되 승인된 예산은 사용자 승인 후 반영한다.
- C-07 해결(10/21): 목록은 후보·확정을 함께 반환하며 후보는 최근 발견 순, 확정은 출금일순(모름은 마지막)으로 서버가 정렬한다. 1차는 페이지 나누기 없이 확정 월 합계·후보 수를 함께 주고, 후보 확정·무시는 별도 API로 여러 개를 한 번에 처리한다. 이미 해당 상태면 성공하며, 선택할 수 없는 ID가 하나라도 있으면 전부 처리하지 않는다.
- C-08 해결(10/21): 실제로 돈이 빠져나가는 길은 한 번만 센다. 계좌·결제 수단 모름은 출금일이 있을 때 고정지출 납부 예정을 만들고, 카드는 별도 납부 예정 없이 카드 청구서에 포함한다. 이름으로 같은 비용을 찾지 않으며 선택한 실제 결제를 근거 거래로 저장한다. 근거 없는 카드 결제는 목록의 제안을 기존 수정 API로 확인하고, 첫 카드 청구서의 예산 선차감은 예산 쪽에서 처리한다.
- C-09·C-10 해결(10/21): `fields`는 칸 오류가 있을 때만 넣고, 칸 하나에 묶이지 않는 입력 오류는 `fields.nonFieldErrors`로 보낸다. 직접 추가·후보 확정·무시는 선택 헤더 `Idempotency-Key`로 같은 번호·같은 내용의 첫 응답을 재사용하며, 다른 내용은 `409 idempotency_conflict`이다. 성공 기록이 없는 4xx 실패는 기록하지 않아 같은 번호로 수정 재시도할 수 있고, 이름으로 중복을 판단하지 않는다. 저장 중에는 버튼을 잠근다.
- C-11 해결(10/21): 주소의 없는·남의·형식 틀린 ID는 모두 `404 not_found`와 “찾을 수 없어요.”로 응답하며 `fields`는 없다. 본문 ID 오류는 `400 invalid`를 유지한다. 주소 끝 `/` 누락도 `404 not_found`이며 “주소를 확인해 주세요. 주소 끝에 /가 필요해요.”로 안내한다.
- C-12·C-14 해결(10/21): 거래 분류 직후 서버가 기억한 가맹점·같은 카드·금액 ±10%로 매칭하고, 근거가 없으면 같은 카드·금액 ±10%·날짜 ±3일로 찾아 목록의 `evidenceSuggestion`으로 묻는다(1건이면 “이 결제가 맞나요?”, 여러 건이면 “비슷한 결제가 N건 있어요 [고르기]” — 10/21 추가). 연결하면 `funding_bucket=fixed`로 생활비 사용액에서 제외하고 거래 ID를 `evidence`에 더한다. [맞아요]는 기존 PATCH의 `evidenceTransactionId`를 쓰며, [아니에요]는 요청·저장 없이 다음 달 새 결제 때 다시 묻는다. 새 API는 만들지 않는다.
- C-15 해결(10/21): 납부 예정(`PaymentDue`)은 **이번 주기 1건씩** 만든다(1년치를 미리 만들지 않음). 고정지출이 확정될 때 이번 주기 것을, 다음 주기 것은 **그 주기에 홈·예산을 처음 열 때** 만든다(매일 도는 자동 작업 없음, 같은 회차 중복은 `occurrence_key` UNIQUE가 막음). 확정할 때 이번 주기 출금일이 이미 지났으면 출금 거래가 있을 때만 “냄”으로 연결하고 없으면 만들지 않는다. 출금일이 없거나 카드로 내는 고정지출은 만들지 않는다. 수정·중지 규칙의 '이번 달'은 '이번 주기'(급여일 ~ 다음 급여일 전날)로 맞췄다.
- C-16 해결(10/21): 1차에는 **추가 팝업에서 실제 결제를 고르지 않는다**(팝업에 보여 줄 결제 목록을 받을 API가 없어서). 카드 고정지출을 저장하면 목록의 `evidenceSuggestion`으로 바로 묻고(1건 “이 결제가 맞나요?”, 여러 건 [고르기]), 고른 결제는 `2. 수정`의 `evidenceTransactionId`로 보낸다. 추가 API의 `evidenceTransactionId`는 그대로 두되 1차 화면은 보내지 않는다. 같이 정한 것: **다른 고정지출에 이미 연결된 결제는 후보에서 빼고, 보내면 `400`**(결제 하나가 고정지출 두 개에 연결되지 않게).
- 10/21 검수 반영: 계좌·카드 `status`에 `relogin` 추가 · 납부 예정은 출금일이 있을 때만 생성 · 후보 정렬 기준은 `created_at`(발견·등록 시각, DB 칸 추가) · 자동 발견 후보는 근거 거래의 계좌·카드를 결제 수단으로 채움 · `categoryDetail` 삭제(DB 칸도 삭제) · 추가의 `paymentDay`는 생략하면 `null` · 근거 거래 선택과 '이 결제가 맞나요?'는 1차에 카드만 · 중지·무시 항목 수정은 404 · 확정·무시의 요청 번호는 버튼을 누를 때 생성 · 고정지출이 바뀌면 이전 초안은 만료(승인 불가)로 확정. 납부 예정을 만드는 때는 C-15, 추가 팝업의 결제 고르기는 C-16으로 확정.

**명세 상태**

- 주소·작성 범위·공통 응답 규칙은 위 공통 문서를 따른다. 확인 필요 C-01 ~ C-16을 모두 해결해 이 문서의 요청·응답 필드와 성공 상태 코드(`201`·`200`·`204`)를 **10/21 팀 기준으로 확정**한다. 이후 바꿀 때는 결정기록에 남기고 `확인 필요`에 번호를 새로 붙인다. 구현 완료를 뜻하지는 않는다.
- 고정지출은 매월만 받으며 주기 칸은 요청으로 받지 않는다. 1년에 한 번 내는 돈은 비정기지출 준비금(`BUD-011`), 매주·매일 사는 것은 생활비 카테고리 예산에서 다룬다.
- 추천 예산 금액·쿠션 배분·카드 및 대출과의 중복 차감 계산은 여기서 새로 정하지 않는다. **고정비는 생활비를 나누기 전에 한 번만 뺀다.**
- 이미 결제된 거래는 보존한다. 변경 전 금액은 별도 이력 표에 저장하지 않고, 지난 회차의 `PaymentDue.confirmed_amount`와 승인된 예산의 `input_snapshot`에 남긴다(`TXN-008`, 10/21 확정). 이 API의 저장 성공이 예산 변경 승인이나 실제 출금 실행을 의미하지 않는다.
- 승인 전 예산 초안(온보딩 중)은 바뀐 값으로 다시 계산하고, 변경의 영향을 받은 기존 초안은 만료 처리해 승인할 수 없게 한다(10/21 확정, 요구사항 `COM-005`의 만료 상태). 오래된 숫자의 초안이 그대로 승인되지 않도록 하기 위해서다. 승인된 예산은 자동으로 바꾸지 않으며 사용자 승인 후 반영한다(`BUD-005`).

## 공통 요청·응답 기준

- 모든 API는 로그인한 사용자 본인의 고정지출만 다룬다. `userId`를 요청으로 받지 않고 세션에서 사용자를 확인한다. 현재 전역 권한은 `AllowAny`이므로 **로그인 필수는 구현할 목표 계약**이다.
- `POST`·`PATCH`는 JSON 본문을 보내며, `POST`·`PATCH`·`DELETE`는 `X-CSRFToken`이 필요하다. 프론트에서는 기존 `apiSend`를 사용한다.
- `1. 직접 추가`·`5. 후보 확정`·`6. 후보 무시`의 `Idempotency-Key` 헤더는 선택이다. 없으면 요청을 그대로 처리한다. 같은 회원의 요청 번호 처리 기준은 [API_RULES.md](../API_RULES.md#같은-요청을-두-번-보내면)와 [idempotency.py](../../backend/config/idempotency.py)를 따르며, 아래 `1. 직접 추가`의 “두 번 눌렀을 때”에 정리한다.
- 직접 추가는 팝업을 열 때, 후보 확정·무시는 버튼을 누를 때 요청 번호를 만든다. 응답이 오기 전에 다시 보내면 같은 번호를 사용한다. 저장하는 동안 버튼을 잠그고 “저장 중…”으로 표시한다.
- `<id>`는 `RecurringExpense.recurring_id`에 대응하는 UUID이며, 응답에서는 `recurringId`로 쓴다. 계좌·카드 ID도 UUID이다. `category`는 카테고리 모델의 문자열 기본키이며 UUID가 아니다.
- 주소의 `<id>`가 없는·남의·형식 틀린 ID이면 모두 `404 not_found`이며, `error.message`는 “찾을 수 없어요.”이다. 예: `/api/budgets/fixed/abc/`. `fields`는 넣지 않는다.
- 본문에 든 ID(`paymentAccountId` 등)의 형식이나 선택값이 틀리면 기존처럼 `400 invalid`이다. 주소 오류와 본문 입력 오류를 구분한다.
- 주소 끝 `/`를 빼먹으면 `404 not_found`이며, `error.message`는 “주소를 확인해 주세요. 주소 끝에 /가 필요해요.”이다. 이 경우도 `fields`는 넣지 않는다.
- `status`·`sourceType`·`confirmedAt`은 서버가 정하는 응답 필드이며 사용자가 쓰기 요청 본문으로 보내지 않는다. 보내는 값 표에 없는 칸(이 세 칸 포함)을 보내면 `400 invalid`이고 해당 칸의 `fields`에 “이 칸은 보낼 수 없어요.”를 넣는다.
- 예산에는 `status=confirmed`인 고정지출만 들어간다. 후보·중지·무시 항목은 예산에 포함하지 않는다.
- 이번 주기 반영은 예산 쪽에서 처리.
- 카테고리는 [API_RULES.md의 카테고리 코드](../API_RULES.md#카테고리-코드)를 따른다. 요청은 `category`에 코드만 보내고, 응답은 `category`와 `categoryName`을 함께 보낸다. 허용 값은 코드표의 10개 + `ETC`이며 `UNCLASSIFIED`는 선택할 수 없다.
- 저축·투자·대출 상환·카드값은 이 API로 등록하지 않는다(`TXN-008`). 화면에서도 선택지에 없다.
- 저축은 저축 확인 화면(`TXN-005`), 대출은 대출 정보의 월 상환 예정액(`BUD-001`), 카드값은 카드 청구서에서 따로 다룬다.
- 카드 청구액 자체를 등록하는 것과 구독료 등 개별 고정지출의 결제 수단을 카드로 선택하는 것은 구분한다. 카드로 내는 고정지출은 등록할 수 있다.
- 실제로 돈이 빠져나가는 길은 한 번만 센다(`COM-004`). 계좌로 내는 고정지출은 그 고정지출의 납부 예정(`PaymentDue`)을 만든다. 납부 예정에는 날짜가 필요하므로 **출금일(`paymentDay`)이 있을 때만** 만든다. 출금일을 모르면 납부 예정 없이 “출금일 확인 필요”로 표시하고, 출금일이 정해지면 그때 만든다. 카드로 내는 고정지출은 별도 납부 예정을 만들지 않고 카드 청구서에 포함된 것으로 본다.
- 결제 수단을 모르면 출금일이 있을 때 일단 고정지출 납부 예정을 만들고, 카드 내역에서 발견되면 카드로 바꿀지 사용자에게 묻는다.
- 자동 발견 후보는 근거 거래가 있으므로 그 거래의 계좌·카드를 결제 수단(`paymentAccount`·`paymentCard`)으로 채워서 만든다.
- 납부 예정을 만드는 때(C-15, 10/21 확정):
  - **한 번에 이번 주기 1건씩** 만든다. 1년치를 미리 만들지 않는다. 주기는 급여일부터 다음 급여일 전날까지다.
  - 고정지출이 **확정될 때**(직접 추가 · 후보 확정) 이번 주기 1건을 만든다. 출금일이 이번 주기에 이미 지났으면 그 출금 거래가 있을 때만 "냄"으로 만들어 연결하고, 없으면 이번 주기 건은 만들지 않는다(`TXN-008` 온보딩 후 반영 규칙).
  - **다음 주기 것은 그 주기에 홈·예산을 처음 열 때** 없으면 만든다. 매일 도는 자동 작업(배치)은 1차에 만들지 않는다. 같은 회차를 두 번 만드는 것은 `occurrence_key`(회원 · 회차) UNIQUE가 막는다.
  - 출금일이 없거나 카드로 내는 고정지출은 만들지 않는다.
- `name`은 사용자가 붙인 별명이다. 같은 비용을 찾을 때 이름으로 맞추지 않는다.
- 근거 거래 선택(`evidenceTransactionId`)과 목록의 '이 결제가 맞나요?'(`evidenceSuggestion`)는 **1차에 카드로 내는 고정지출에만** 있다. 계좌로 내는 고정지출은 납부 예정과 실제 출금을 날짜·금액으로 연결하므로 사용자에게 묻지 않는다. 계좌·모름 고정지출에 `evidenceTransactionId`를 보내면 `400 invalid`(“선택할 수 없는 거래예요.”)이다.
- 결제 하나는 고정지출 하나에만 연결한다. **다른 고정지출의 근거 거래로 이미 연결된 결제**는 `evidenceSuggestion` 후보에서 빼고, `evidenceTransactionId`로 보내면 `400 invalid`(“선택할 수 없는 거래예요.”)이다. 같은 고정지출에 이미 연결된 결제를 다시 보내면 그대로 성공한다.
- 1차 화면은 고정지출 **추가 팝업에서 결제를 고르지 않는다**(C-16). 저장 뒤 목록의 제안·[고르기]에서 고른다.
- 카드로 낼 때 그 카드의 실제 결제 하나를 `evidenceTransactionId`로 선택하면 근거 거래(`evidence`)로 저장하고 그 가맹점을 기억한다. 자동 발견 후보는 처음부터 근거 거래가 있다. `RecurringExpense.evidence`의 내부 JSON 저장 형태와 별개로 API는 아래 응답 객체로 정리해 반환한다.
- 카드 거래의 같은 비용 찾기는 `TXN-008`을 따른다. 기억한 가맹점이 있으면 가맹점 + 같은 카드 + 금액 ±10%로 맞춘다. 근거 거래가 없으면 같은 카드 + 금액 ±10% + 날짜 ±3일로 찾아 사용자에게 한 번 확인한다. 이름으로는 맞추지 않는다.
- 연결하면 그 거래의 충당 재원(`SpendingAllocation.funding_bucket`)을 `fixed`로 기록해 생활비 카테고리 사용액에서 제외하고, 거래 ID를 고정지출 `evidence`에 더해 가맹점을 기억한다. 카드로 내는 고정지출은 연결된 카드 거래를 고정비로 센다.
- 매칭은 거래 분류가 끝난 직후 서버가 수행하며, 이 문서의 API가 직접 계산하지 않는다. 근거 없는 카드 고정지출에서 찾은 결제가 1건 이상이면 목록의 `evidenceSuggestion`으로 제안하고(여러 건이면 사용자가 고름), 사용자는 기존 수정 API의 `evidenceTransactionId`로 연결을 확인한다. 이 거래 연결 확인은 `5. 후보 확정`·`6. 후보 무시`와 별개이며 새 API를 만들지 않는다.
- 카드값은 첫 청구서만 예산에서 먼저 뺀다(`TXN-009`·`BUD-001`). 이 문서의 API는 그 계산을 하지 않는다.
- 결제 수단은 선택이다. 요청의 `paymentAccountId`·`paymentCardId`는 UUID 또는 `null`이며, 둘 다 `null`이면 모름으로 저장할 수 있다. 둘 다 값이 있으면 `400 invalid`이다.
- 고를 수 있는 계좌는 본인 계좌 중 `is_selected=true`인 입출금 계좌이며, 연결이 해제되지 않았고(`Connection.disconnected_at`이 `null`) 용도가 저축(`budget_role=savings`)이 아니어야 한다. 고를 수 있는 카드는 본인 카드 중 `is_selected=true`인 카드이다.
- 연결을 해제해도 등록된 고정지출을 지우거나 고정비에서 제외하지 않는다. 결제 수단 객체를 유지하고 연결 상태를 `disconnected`로 반환한다. 계좌 기록 자체가 삭제되어 FK가 `SET_NULL` 처리되면 `paymentAccount`는 `null`이다.
- 카드 거래 내역의 같은 결제를 고정지출로 구분하고 생활비 카테고리에서는 제외한다. 카드 고정지출의 납부 예정을 따로 만들어 다시 차감하지 않는다.
- `amount`는 **반복 지출의 기준 금액**이다. 특정 기간의 실제 납부액·미납액·예산 차감액이 아니다. 회차별 납부 정보는 별도 `PaymentDue` 모델에서 다룬다.
- 각 항목의 금액이 허용 범위 안이면 고정지출 합계가 월급보다 커도 추가·수정 저장을 막지 않는다. 부족액은 예산을 만들 때 안내한다(`BUD-001`).
- 계좌·카드 번호 원문·기관 인증정보·CODEF 식별값은 반환하지 않는다. 번호는 끝 4자리만 `****5678`처럼 마스킹해 표시 이름에 넣는다.
- 이 문서의 UUID·금액·계좌 정보는 설명용 예시다. 카테고리 예시는 확정 코드를 사용한다. 월세·통신비는 `HOUSING_TELECOM` / 주거·통신, 구독은 `CULTURE_LEISURE` / 문화·여가이다.

**고정지출 한 건의 응답 형태**

추가·수정 성공 응답과 목록·후보 확정·후보 무시 응답의 `items[]`에서 아래 기본 형태를 사용한다. 목록 응답의 각 항목에는 `evidenceSuggestion`을 추가한다. 결제 수단 객체·표시 이름과 상태·출처·확정 시각·근거 거래 규칙은 10/21 확정 사항이다.

| 이름 | 타입 | 뜻 |
|---|---|---|
| `recurringId` | UUID | 고정지출 식별자. 수정·중지 요청의 `<id>`에 사용 |
| `status` | 문자 | 고정지출 상태: `suggested`(후보) · `confirmed`(확정) · `stopped`(중지) · `ignored`(무시). 계좌·카드 객체 안의 연결 상태와 별개 |

| `confirmedAt` | 시각 또는 `null` | 확정 시각, ISO 8601 한국 시간. 미확정 후보는 `null`, 직접 추가는 저장 시각 |
| `name` | 문자 | 사용자가 붙인 항목 별명. 모델 기준 최대 100자이며 같은 비용을 찾는 기준으로 사용하지 않음 |

**표시 이름 규칙 (서버 생성, 10/21 확정)**

- 계좌 `displayName`: `{은행 짧은 이름} {별칭, 없으면 계좌명, 둘 다 없으면 '입출금'} · ****{끝 4자리}`. 예: `국민 급여통장 · ****5678`, `국민 KB국민ONE통장 · ****5678`, `국민 입출금 · ****5678`.
- 카드 `displayName`: `{카드명} · ****{끝 4자리}`. 예: `신한 Deep Dream · ****1234`.
- 계좌·카드 번호는 표시 이름에 끝 4자리만 포함한다. 별도의 `maskedNumber` 필드는 반환하지 않는다.

결제 수단은 쓰기 요청에서도 `null`로 비울 수 있다. PATCH에서 필드를 생략하면 기존 값을 유지하며, 두 수단을 모두 `null`로 바꾸면 모름으로 저장한다. 출금일도 `null`을 보내 모름으로 저장할 수 있으며 “출금일 확인 필요”로 표시한다. PATCH에서 비울 수 있는 칸과 결제 수단을 함께 보내는 규칙은 아래 수정 API의 보내는 값 표를 따른다.

**공통 실패 응답**

`error.code`·`error.message`는 항상 보낸다. `error.fields`는 칸 오류가 있을 때만 넣으며, 로그인·404·409 등 칸과 상관없는 오류에는 생략한다. 빈 객체도 넣지 않는다. 칸 하나에 묶이지 않는 입력 오류는 `fields.nonFieldErrors`로 보낸다.

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 요청 JSON 형식이 깨짐 | 400 | `parse_error` | 요청을 처리하지 못했음을 안내 |
| 로그인하지 않음 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| CSRF 검증 실패·권한 없음 | 403 | `permission_denied` | `error.message` 표시 |
| 주소 끝 `/` 누락 | 404 | `not_found` | “주소를 확인해 주세요. 주소 끝에 /가 필요해요.” 표시. `fields` 없음 |
| 지원하지 않는 메서드 | 405 | `method_not_allowed` | 요청 방식을 확인하도록 처리 |
| 서버 오류(배포 환경) | 500 | `server_error` | 잠시 후 다시 시도하도록 안내 |

입력값 검증 실패 예시 — 아래 필드명도 camelCase를 사용한다.

```json
{
  "error": {
    "code": "invalid",
    "message": "입력값을 확인해 주세요.",
    "fields": {
      "amount": ["금액은 1,000원 ~ 1억 원으로 입력해 주세요."],
      "paymentDay": ["출금일은 1일부터 31일 사이로 입력해 주세요."]
    }
  }
}
```

계좌와 카드를 둘 다 지정하는 것처럼 여러 칸에 걸친 입력 오류는 `error.fields.nonFieldErrors`의 메시지를 표시한다. 프론트는 `fields`가 없을 수도 있다고 보고 읽는다.

칸과 상관없는 로그인 오류 예시 — `fields`를 넣지 않는다.

```json
{
  "error": {
    "code": "not_authenticated",
    "message": "로그인이 필요해요."
  }
}
```

본문의 결제 수단 선택 검증은 10/21 확정 규칙에 따라 없는 것·남의 것·선택 조건 밖인 것을 구분하지 않고 `400 invalid`로 응답한다. `error.fields.paymentAccountId`에는 `["선택할 수 없는 계좌예요."]`, `error.fields.paymentCardId`에는 `["선택할 수 없는 카드예요."]`를 넣는다.

추가·수정에서 고른 근거 거래가 내 거래가 아니거나, 선택한 카드의 거래가 아니거나, 다른 고정지출에 이미 연결된 거래면 `400 invalid`이다. `error.fields.evidenceTransactionId`에는 `["선택할 수 없는 거래예요."]`를 넣는다.

| 어떤 기능 | 고정지출 확인 화면의 [고정지출 직접 추가]에서 값을 입력하고 [추가하기]를 누를 때 |
| 어디로 | `POST /api/budgets/fixed/` |
| 로그인 필요 | O · 세션 쿠키, CSRF 필요 |
| 명세 상태 | 확정 (10/21) |
| 개발 상태 | 미구현 |

**요청 헤더**

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `Idempotency-Key` | 문자 | X (선택) | 8~64자, 영문·숫자·`-`·`_`. 팝업을 열 때 만든 요청 번호이며 같은 팝업에서 재전송하면 같은 번호 사용. 없으면 그대로 처리 | `fixed-create-20261021-01` |

**보내는 값 (JSON 본문)**

카테고리는 필수, 결제 수단·출금일은 선택이다. 금액은 1,000원 ~ 1억 원이다.

| 이름 | 타입 | 필수 | 범위·설명 | 예시 |
|---|---|---|---|---|
| `name` | 문자 | O | 앞뒤 공백을 제거한 뒤 1~100자. 빈 값·`null` 불가 | `"월세"` |
| `amount` | 정수 | O | 원 단위 1,000 이상 100,000,000 이하(양끝 포함). 소수·문자열·`null` 불가 | `700000` |
| `paymentDay` | 정수 또는 `null` | X | 매월 출금일 1~31 또는 `null`(모름). **생략하면 `null`(모름)으로 저장**. 해당 월에 없는 날은 말일로 계산하며 주말·공휴일 이동은 계산하지 않음 | `25` |
| `paymentAccountId` | UUID 또는 `null` | X | 본인 계좌 + `is_selected=true` + 입출금 + 연결 해제 안 됨. `budget_role=savings` 제외. 카드와 동시 지정 불가 | `"27d3dbb3-1ee8-43b7-9134-9e8ff01991d4"` |
| `paymentCardId` | UUID 또는 `null` | X | 본인 카드 + `is_selected=true`. 계좌와 동시 지정 불가 | `null` |
| `evidenceTransactionId` | UUID 또는 `null` | X | **카드로 낼 때만**. 1차 화면은 보내지 않음(C-16, 저장 뒤 목록에서 고름). 선택한 카드의 본인 실제 결제 하나. 근거 거래로 저장하고 가맹점을 기억함. `null`로 비울 수 있음 | `null` |
| `category` | 문자 | O | `API_RULES.md` 코드표의 10개 + `ETC`. `UNCLASSIFIED`·생략·`null` 불가 | `"HOUSING_TELECOM"` |

화면은 항목 이름으로 카테고리를 미리 고르며, 사용자가 직접 고르면 그 선택을 유지한다. 서버는 이름으로 대신 결정하지 않고 반드시 전달받은 `category` 코드를 검사한다.

```json
{
  "name": "월세",
  "amount": 700000,
  "paymentDay": 25,
  "paymentAccountId": "27d3dbb3-1ee8-43b7-9134-9e8ff01991d4",
  "paymentCardId": null,
  "category": "HOUSING_TELECOM",
  "evidenceTransactionId": null
}
```

결제 수단을 지정하지 않으면 모름으로 저장할 수 있다. `userId`·`recurringId`는 서버가 관리하고, 주기·`status`·`sourceType`·`confirmedAt`은 요청 본문으로 받지 않는다.

**받는 값 (201 Created)**

서버가 식별자를 만든 뒤 바로 `status=confirmed`, `sourceType=manual`, `confirmedAt=저장 시각`으로 저장하고 고정지출 한 건을 반환한다. `data` 같은 추가 객체로 감싸지 않는다.

```json
{
  "recurringId": "a7c1d0e2-3b4f-4c68-9a12-8f30d5e1b6c4",
  "name": "월세",
  "amount": 700000,
  "paymentDay": 25,
  "paymentAccount": {
    "accountId": "27d3dbb3-1ee8-43b7-9134-9e8ff01991d4",
    "displayName": "국민 급여통장 · ****5678",
    "status": "connected"
  },
  "paymentCard": null,
  "category": "HOUSING_TELECOM",
  "categoryName": "주거·통신",
  "status": "confirmed",
  "sourceType": "manual",
  "confirmedAt": "2026-10-21T17:30:00+09:00",
  "evidence": null
}
```

화면은 저장 성공 후 목록을 갱신한다. 실패하면 입력값을 유지하고 해당 칸의 오류를 보여 준다.

**두 번 눌렀을 때**

- 팝업을 열 때 요청 번호를 하나 만들고 `Idempotency-Key` 헤더로 보낸다. 같은 팝업에서 다시 보내면 같은 번호를 사용하며, 저장 중에는 버튼을 잠그고 “저장 중…”으로 표시한다.
- 같은 회원·같은 번호·같은 요청 내용이면 다시 처리하지 않고 처음 성공 응답의 상태 코드와 본문을 그대로 돌려준다. 고정지출을 두 건 만들지 않는다.
- 같은 번호로 다른 내용을 보내면 `409 idempotency_conflict`이며 `fields`는 없다.
- 성공 기록이 없는 요청의 처리 결과가 4xx이면 기록하지 않는다. 입력을 고쳐 같은 번호로 다시 보낼 수 있다. 이미 성공 기록이 있는 번호의 409 충돌은 그 성공 기록을 지우거나 다른 내용으로 바꾸지 않는다.
- 이름이 같다는 이유로 중복이라고 판단하지 않는다. 새 항목은 팝업을 다시 열어 새 번호로 보내며, 번호가 다르면 별개 항목이다.
- 헤더가 없으면 직접 추가를 그대로 처리한다. 후보 확정·무시에서도 헤더는 선택이며, 번호를 보낸 경우 위 재전송·충돌 규칙을 동일하게 적용한다.

예: 위 직접 추가 요청 본문을 같은 API에 그대로 두 번 보낸다.

| 전송 | 요청 번호 | 처리·응답 |
|---|---|---|
| 첫 번째 | `fixed-create-20261021-01` | 한 건을 저장하고 위 `201 Created` 응답 반환 |
| 두 번째 | `fixed-create-20261021-01` | 새로 저장하지 않고 첫 번째와 같은 `201 Created`·같은 응답 본문 반환. `recurringId`도 동일 |

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 필수값 누락, 이름·금액·출금일 형식 또는 범위 오류 | 400 | `invalid` | 해당 입력 칸 아래에 `fields` 메시지 |
| 금액이 1,000 미만 또는 100,000,000 초과 | 400 | `invalid` | `fields.amount`에 “금액은 1,000원 ~ 1억 원으로 입력해 주세요.” 표시 |
| 출금일이 1~31 범위 밖임(`null` 제외) | 400 | `invalid` | `fields.paymentDay`에 “출금일은 1일부터 31일 사이로 입력해 주세요.” 표시 |
| 결제 수단 ID가 UUID 형식이 아님 | 400 | `invalid` | 해당 결제 수단을 다시 선택하도록 안내 |
| 계좌·카드 둘 다 보냄(두 ID 모두 값이 있음) | 400 | `invalid` | `fields.nonFieldErrors`로 계좌·카드·모름 중 하나만 선택하도록 안내 |
| 선택할 수 없는 계좌/카드(없는 것·남의 것·선택 조건 밖 모두 포함) | 400 | `invalid` | 공통 규칙의 해당 `fields`에 “선택할 수 없는 계좌예요.” / “선택할 수 없는 카드예요.” 표시 |
| 선택할 수 없는 거래(내 거래가 아님 · 선택한 카드의 거래가 아님 · 다른 고정지출에 이미 연결됨) | 400 | `invalid` | `fields.evidenceTransactionId`에 “선택할 수 없는 거래예요.” 표시 |
| `category`가 코드표에 없거나 `UNCLASSIFIED`임 | 400 | `invalid` | 카테고리를 다시 고르도록 안내 |
| 같은 요청 번호로 다른 내용을 보냄 | 409 | `idempotency_conflict` | `error.message` 표시. `fields` 없음 |

요청 번호 충돌 예시 — `fields`를 넣지 않는다.

```json
{
  "error": {
    "code": "idempotency_conflict",
    "message": "같은 요청 번호로 다른 내용을 보낼 수 없어요."
  }
}
```

그 밖의 로그인·CSRF·서버 오류는 공통 실패 응답을 따른다. 미정인 입력 정책은 확정 후 검증 조건에 반영한다.

**확인 필요**

없음.

## 2. 고정지출 수정

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 고정지출 항목의 [수정]을 누르고 값을 바꾼 뒤 [수정 저장]을 누를 때 |
| 어디로 | `PATCH /api/budgets/fixed/<id>/` |
| 로그인 필요 | O · 세션 쿠키, CSRF 필요 |
| 명세 상태 | 확정 (10/21) |
| 개발 상태 | 미구현 |

**보내는 값**

경로의 `<id>`는 본인 고정지출의 UUID이다. 수정할 수 있는 것은 목록에 나오는 **후보(`suggested`)·확정(`confirmed`)** 항목뿐이다. 중지(`stopped`)·무시(`ignored`) 항목은 목록에 없으므로 `404 not_found`이며, 다시 쓰려면 `1. 고정지출 직접 추가`로 새로 만든다. 본문에는 아래 표에서 바꿀 필드만 보낸다. 주기·`status`·`sourceType`·`confirmedAt`은 수정 입력으로 받지 않는다.

| 이름 | 타입 | 필수 | null 보내면 | 범위·설명 | 예시 |
|---|---|---|---|---|---|
| `name` | 문자 | X | 400 | 추가와 같은 범위. 생략하면 유지, `null`로 삭제 불가 | `"월세"` |
| `amount` | 정수 | X | 400 | 원 단위 1,000 이상 100,000,000 이하(양끝 포함). 생략하면 유지, 소수·문자열·`null` 불가 | `720000` |
| `paymentDay` | 정수 또는 `null` | X | 비움 | 1~31 또는 `null`(모름). 생략하면 유지, 비우면 “출금일 확인 필요”. 해당 월에 없는 날은 말일로 계산하며 주말·공휴일 이동은 계산하지 않음 | `26` |
| `paymentAccountId` | UUID 또는 `null` | X | 비움 | 본인 계좌 + `is_selected=true` + 입출금 + 연결 해제 안 됨. `budget_role=savings` 제외. 생략하면 유지, `null`이면 비움. 카드와 동시 지정 불가 | `"27d3dbb3-1ee8-43b7-9134-9e8ff01991d4"` |
| `paymentCardId` | UUID 또는 `null` | X | 비움 | 본인 카드 + `is_selected=true`. 생략하면 유지, `null`이면 비움. 계좌와 동시 지정 불가 | `null` |
| `evidenceTransactionId` | UUID 또는 `null` | X | 비움 | **카드로 낼 때만**. 선택한 카드의 본인 실제 결제 하나. 근거 거래로 저장하고 가맹점을 기억함. 목록의 `evidenceSuggestion`을 확정할 때도 이 칸을 쓴다. 생략하면 유지, `null`이면 비움 | `"c8c60113-7ac4-4cc2-998e-6bbbf5404f10"` |
| `category` | 문자 | X | 400 | `API_RULES.md` 코드표의 10개 + `ETC`. `UNCLASSIFIED` 불가. 생략하면 유지, `null`로 삭제 불가 | `"HOUSING_TELECOM"` |

- 최소 한 칸은 보내야 한다. 빈 객체 `{}`는 `400 invalid`(“바꿀 값을 하나 이상 보내 주세요.”)이다.
- [공통 수정 요청 규칙](../API_RULES.md#수정-요청-patch)에 따라 안 보낸 칸은 그대로 두고, `null`은 비울 수 있는 칸만 비운다. `paymentDay`를 비우면 “출금일 확인 필요”로 표시하고, `paymentAccountId`·`paymentCardId`를 둘 다 비우면 결제 수단은 모름이다. `evidenceTransactionId`도 비울 수 있다.
- `name`·`amount`·`category`는 저장에 필요한 필수 칸이므로 `null`을 보내면 `400 invalid`이다. PATCH에서 보내는 것 자체는 선택이며, 생략하면 기존 값을 유지한다. 빈 글자 `""`는 모든 칸에서 `400 invalid`이다.
- 결제 수단을 바꿀 때는 `paymentAccountId`·`paymentCardId`를 같이 보낸다. 기존 값과 요청을 합친 최종 상태에서 검사하며, 한쪽만 보내 계좌와 카드가 둘 다 남으면 `400 invalid`이다. 서버가 보내지 않은 다른 칸을 알아서 지우지 않는다.
- 선택 조건은 요청에 지정한 결제 수단 ID를 검사할 때 적용한다. 결제 수단 필드를 생략하고 이름·금액만 수정하면, 기존 연결 해제 계좌·카드도 그대로 유지한다.

예: `PATCH /api/budgets/fixed/a7c1d0e2-3b4f-4c68-9a12-8f30d5e1b6c4/`

금액·출금일 함께 바꾸기:

```json
{
  "amount": 720000,
  "paymentDay": 26
}
```

금액만 바꾸기 — 계좌·카드·출금일 등 보내지 않은 칸은 그대로 유지한다.

```json
{
  "amount": 720000
}
```

계좌 비우기 — 결제 수단을 모름으로 바꾸므로 두 ID를 함께 비운다.

```json
{
  "paymentAccountId": null,
  "paymentCardId": null
}
```

계좌 → 카드로 바꾸기 — 기존 계좌를 비우고 선택한 카드 ID를 함께 보낸다.

```json
{
  "paymentAccountId": null,
  "paymentCardId": "6a213d92-887b-4ce1-a395-cd1e6e7482f0"
}
```

목록의 거래 연결 제안에서 [맞아요]를 누르거나 여러 건 중 하나를 고르면 해당 고정지출에 그 거래의 `evidenceSuggestion.candidates[].transactionId`를 보낸다. 아래는 목록 예시의 OTT 항목에 대한 요청이다.

```http
PATCH /api/budgets/fixed/d4e8c728-6103-42d0-a9c7-17e5a694c01f/
```

```json
{
  "evidenceTransactionId": "c8c60113-7ac4-4cc2-998e-6bbbf5404f10"
}
```

이 요청은 거래 연결을 확인하는 것이며 고정지출 후보의 `status`를 확정하는 요청과 구분한다. [아니에요]는 이 PATCH를 포함해 아무 요청도 보내지 않는다.

**언제부터 바뀌나**

- 아래 납부 예정 금액 변경은 해당 고정지출의 `PaymentDue`가 있는 경우에 적용한다. 카드 고정지출에는 별도 납부 예정이 없으므로 이 수정으로 카드 청구서의 금액을 바꾸지 않는다.
- `amount`를 바꾸면 아직 내지 않은 회차(`payment_state=unpaid`) 중 이번 주기 미납분과 앞으로의 회차의 납부 예정 금액(`PaymentDue.confirmed_amount`)만 새 금액으로 바꾼다. 이미 냈거나 일부 낸 회차(`paid`·`partial`)는 그대로 둔다.
- 결제 수단·출금일을 바꿀 때도 같은 범위(이번 주기 미납분과 앞으로의 회차)에만 반영한다. 카드로 바꾸거나 출금일을 비우면(`null`) 그 미납 납부 예정을 취소하고(`canceled`), 출금일을 바꾸면 미납분의 날짜를 새 출금일로 바꾸며, 계좌·모름 항목에 출금일이 새로 생기면 그때 납부 예정을 만든다(만드는 시점의 세부는 C-15).
- 이번 주기 차액에 대한 여윳돈 처리·예산 조정 제안은 예산 쪽에서 한다(`TXN-008`·`BUD-005`). 이 API 응답에는 계산 결과를 넣지 않는다.
- 변경 전 금액은 별도 이력 표에 저장하지 않는다. 지난 회차의 납부 예정(`PaymentDue.confirmed_amount`)과 승인된 예산의 `input_snapshot`에 남는다.
- 승인 전 예산 초안(온보딩 중)은 바뀐 값으로 다시 계산한다. 승인된 예산은 자동으로 바꾸지 않으며 사용자 승인 후 반영한다(`BUD-005`).

**받는 값 (200 OK)**

## 3. 고정지출 중지

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 확정된 고정지출의 수정 팝업에서 [이 고정지출 삭제] 버튼을 누를 때 (실제로는 지우지 않고 중지. 버튼 이름은 [더 이상 안 나가요] 등으로 바꾸는 것을 제안) |
| 어디로 | `DELETE /api/budgets/fixed/<id>/` |
| 로그인 필요 | O · 세션 쿠키, CSRF 필요 |
| 명세 상태 | 확정 (10/21) |
| 개발 상태 | 미구현 |

**보내는 값**

| 이름 | 위치 | 타입 | 필수 | 범위·설명 |
|---|---|---|---|---|
| `id` | 경로 | UUID | O | 중지할 본인 고정지출의 `recurringId` |

본문과 쿼리 파라미터는 보내지 않는다. 중지할 수 있는 것은 **확정(`confirmed`)** 항목이며, 이미 중지된 항목은 아래처럼 `204`로 성공한다. 후보는 중지가 아니라 `6. 후보 무시`([고정지출 아니에요])로 처리하므로, 후보·무시 항목에 `DELETE`를 보내면 `404 not_found`이다.

```http
DELETE /api/budgets/fixed/a7c1d0e2-3b4f-4c68-9a12-8f30d5e1b6c4/
```

**받는 값 (204 No Content)**

- 성공 응답 본문은 없다. `{}`나 성공 메시지 JSON을 반환하는 응답이 아니다. 기존 `apiSend`에서는 반환값이 `null`일 수 있다.
- **고정지출 행을 지우지 않고 `status=stopped`로 변경**한다. `204` 응답에 상태 JSON을 추가하지 않는다.
- 해당 고정지출의 이번 주기 미납분(`payment_state=unpaid`) 납부 예정이 있으면 취소한다. 해당 `PaymentDue`의 `obligation_state`를 `canceled`로 바꾸고 `canceled_at`에 취소 시각을 기록한다. 이미 낸 회차는 보존하고 다음 주기부터 납부 예정에서 제외한다. 카드 고정지출에는 별도 납부 예정이 없으므로 카드 청구서의 납부 예정을 취소하지 않는다.
- 이미 중지된 본인 항목을 다시 중지해도 **`204 No Content`로 성공**한다. 에러로 처리하지 않으며, 같은 일을 두 번 반영하지 않는다([같은 요청을 두 번 보내면](../API_RULES.md#같은-요청을-두-번-보내면)).
- 중지한 항목의 **다시 시작 API는 1차에 없다.** 다시 쓰려면 `1. 고정지출 직접 추가`로 새 항목을 만든다.
- 이미 결제된 거래와 지난 회차의 납부 예정 금액은 보존한다. 승인 전 예산 초안은 바뀐 값으로 다시 계산하고, 승인된 예산은 자동으로 바꾸지 않으며 사용자 승인 후 반영한다(`BUD-005`).
- 앱에서 중지해도 은행 자동이체나 외부 구독이 해지되지 않는다. 화면에 “앱의 고정지출 관리만 중지돼요. 자동이체·구독 해지는 해당 서비스에서 확인해 주세요.”와 같은 안내를 제공한다.
- 성공 후 목록을 다시 조회한다. 목록은 `suggested`·`confirmed`만 반환하므로 `stopped`인 항목은 나오지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 주소의 없는·남의·형식 틀린 ID, 후보·무시 항목 | 404 | `not_found` | “찾을 수 없어요.” 표시 후 목록 새로고침. `fields` 없음 |

그 밖의 로그인·CSRF·서버 오류는 공통 실패 응답을 따른다. 실패 시 화면에서 완료된 것으로 표시하지 않는다.

없는·남의·형식 틀린 주소 ID의 실패 응답 예시 — 세 경우 모두 같으며 `fields`는 없다.

```json
{

    "code": "not_found",
    "message": "찾을 수 없어요."
  }
```

|---|---|---|

- 화면은 `status`로 두 칸을 나눈다. 후보는 “새로 찾았어요” 칸에 [맞아요]·[아니에요]로 표시하고, 확정은 “내 고정지출” 칸에 표시한다. 후보가 없으면 “새로 찾았어요” 칸을 숨긴다.
- “새로 찾았어요” 칸의 고정지출 후보에 대한 [맞아요]는 `5. 후보 확정`, [아니에요]는 `6. 후보 무시` API를 호출한다. 온보딩 [확인하고 다음]에서는 화면에 남은 고정지출 후보 전부를 한 번에 확정 요청으로 보낸다.
- `evidenceSuggestion.count`가 1이면 해당 항목에 “이 결제가 OTT 맞나요? (10/5 구독 서비스 15,000원) [맞아요] [아니에요]”를 표시한다(항목 이름이 OTT인 예시). 2 이상이면 “비슷한 결제가 2건 있어요 [고르기]”를 표시하고, [고르기]를 누르면 `candidates`를 날짜·가맹점·금액으로 보여 주는 작은 선택 창을 띄운다(“이 중에 없어요” 포함). 저장된 근거 거래인 `evidence`와 아직 연결하지 않은 제안을 구분한다.
- [맞아요] 또는 선택 창에서 고른 거래는 해당 고정지출의 `2. 수정`에 `evidenceTransactionId`로 보낸다. [아니에요]·“이 중에 없어요”는 아무 요청도 보내지 않으며 서버는 거절을 저장하지 않는다. 다음 달 새 결제가 오면 다시 묻는다.
- 출금일이 `null`인 카드 고정지출은 날짜 기준이 없어 제안하지 않는다. 화면은 “출금일 확인 필요”로 출금일 입력을 먼저 안내한다.
- `summary.suggestedCount`는 고정지출 후보 수이며 거래 연결 제안 수가 아니다.
- 확정 항목이 없으면 “내 고정지출” 칸에 “등록한 고정지출이 없어요”와 직접 추가 버튼을 표시한다. 후보·확정이 모두 없으면 `items: []`와 합계·후보 수 `0`을 반환한다. 조회 실패를 빈 목록으로 처리하지 않는다.
- `paymentDay`가 `null`이면 “출금일 확인 필요”로 표시한다. 없는 날짜를 임의로 채우지 않는다.
- 해당 월에 `paymentDay`가 없으면 그 달 말일로 본다(2월 31일 → 2/28, 윤년 2/29). 급여일·대출 납부일과 같은 규칙이며 주말·공휴일 이동은 계산하지 않는다(`BUD-004`). 해당 월의 예정일만 보정하며 등록된 매월 출금일 값은 유지한다.
- 계좌 연결이 해제되면 `paymentAccount.status`는 `disconnected`이고, 화면에는 “연결 해제된 계좌 · 다시 고르기”를 보여 준다. 확정된 고정지출은 목록과 고정비에 그대로 남는다. 카드도 응답 객체의 연결 상태를 표시한다.
- 계좌 기록 자체가 삭제되어 `paymentAccount`가 `null`이면 기존 “출금 계좌 확인 필요” 안내를 유지한다. 카드가 지정된 항목은 카드 정보를 표시한다. 두 수단 모두 `null`인 모름 상태도 저장 가능한 상태이며, 이 안내를 등록 실패로 처리하지 않는다.
- 카드 결제 항목은 “카드값에 포함”으로 표시한다. 별도 고정지출 납부 예정이 아닌 카드 청구서에 포함된 금액이라는 뜻이다.
- 카드 결제라도 확정 항목이면 `confirmedMonthlyTotal`에 포함한다. 표시용 월 합계와 실제 납부 예정은 구분한다.
- 계좌·카드 이름과 번호는 서버가 만든 표시 이름을 사용한다. 프론트에서 번호 원문을 조합하거나 누락된 번호를 추측하지 않는다.
- 현재 화면의 자동 감지 안내와 감지 횟수 배지는 예시 데이터다. 응답에 근거가 없는 “최근 3개월 3회 감지” 문구를 모든 항목에 표시하지 않는다.
- 금액 합계는 `confirmedMonthlyTotal`만 넣고, 남은 결제액·예산 차감액은 넣지 않는다. “다음 급여일까지 아직 나갈 금액”은 홈 계산과 함께 정한다. 카드 청구서도 이번 응답에는 넣지 않는다. `confirmedMonthlyTotal`을 예산에서 차감할 금액으로 사용하지 않는다. 카드 고정지출은 별도 납부 예정 없이 카드 청구서에 포함하며, 첫 청구서의 예산 선차감 계산은 이 API에서 하지 않는다.

**실패하면**

| 상황 | 상태 | `code` | 화면 안내 |
|---|---|---|---|
| 로그인하지 않음 | 403 | `not_authenticated` | 로그인 화면으로 이동 |
| 서버 오류(배포 환경) | 500 | `server_error` | 목록을 불러오지 못했음을 안내하고 재시도 제공 |

나머지는 공통 실패 응답을 따른다. 본인 항목이 없다는 이유로 `404`를 반환하지 않는다.

**확인 필요**

없음.
