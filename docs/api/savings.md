> 담당: 김나은 · 명세 상태: 초안 · 개발 상태: 미구현
> 작성일: 2026-10-22 · S-01 ~ S-12 결정 반영 (10/22, S-11 · S-12는 PR #29 리뷰)
> 검증: 임시 PostgreSQL에서 시제품으로 44개 상황 통과 (목록 · 후보 계좌 수정 금지 · 확정 · 무시 · 직접 추가 · 입력 오류 13 · 수정 · 확정 계좌 변경 · 중지 · 고정지출과 분리 · 동시 요청)

## 작성 범위와 근거

| 기능 | 방식 · 주소 | 이번 작성 범위 |
|---|---|---|
| 정기 저축 목록 보기 | `GET /api/budgets/savings/` | 후보 · 확정 함께, 저축 최소 금액 |
| 정기 저축 직접 추가 | `POST /api/budgets/savings/` | 요청 · 응답 · 실패 |
| 정기 저축 수정 | `PATCH /api/budgets/savings/<id>/` | 요청 · 응답 · 실패 |
| 정기 저축 중지 | `DELETE /api/budgets/savings/<id>/` | 요청 · 응답 · 실패 |
| 후보 확정 ([저축이에요]) | `POST /api/budgets/savings/confirm/` | 요청 · 응답 · 실패 |
| 후보 무시 ([아니에요]) | `POST /api/budgets/savings/ignore/` | 요청 · 응답 · 실패 |

- 화면: [SavingsPage.jsx](../../frontend/src/pages/SavingsPage.jsx) (첫 설정 흐름: 고정지출 확인 → **저축 확인** → 예산 방향, 그리고 **마이 > 정기 저축**에서 다시 열기), [SavingPopup.jsx](../../frontend/src/popups/SavingPopup.jsx)(직접 추가 · 수정 · 중지). 지금은 예시 데이터이고 API는 연결되지 않았다.
- 데이터: [finance/models.py](../../backend/finance/models.py)의 `RecurringSaving`(표 `recurring_saving`, 10/22 추가), `BankAccount`(`account_type` · `budget_role`), `FinancialTransaction`(`transaction_type`).
- 요구사항: `TXN-005`(저축 이동 · 실적 분리, 저축 후보), `BUD-003`(저축 최소 금액), `BUD-005`(승인된 예산은 사용자 승인 후 변경).
- 모양은 [fixed.md](fixed.md)(고정지출)와 같다. 다른 점만 아래 "고정지출과 다른 점"에 모았다.

### 10/22 결정

| 번호 | 질문 | 결정 |
|---|---|---|
| S-01 | 저축 후보 · 확정을 어디에 저장하나 | **새 표 `recurring_saving`** (30번째 표). 고정지출 표에 섞지 않는다 — 저축은 고정지출이 아니고(C-01), 섞으면 고정비 합계에 저축이 들어가 두 번 빠질 위험 |
| S-02 | 저축 최소 금액 | **확정된 정기 저축의 금액 합계를 그때그때 계산**한다. 저장하지 않는다. 지킬 돈에서 사용자가 정하는 저축(`financial_profile.savings_floor`)은 이보다 작을 수 없다 |
| S-03 | 직접 추가를 받나 | **받는다.** 다른 은행 적금처럼 감지되지 않는 저축 |
| S-04 | 수정 · 중지 규칙 | **고정지출과 같다.** 안 보낸 칸은 그대로 · `null`은 비우기, 중지는 지우지 않고 `stopped`, 다시 시작은 새로 추가, 이미 중지면 다시 중지해도 204 |
| S-05 | 자동 감지 조건 | 내 계좌끼리 이체 중 **같은 받는 계좌**로, **매달 같은 날 ±3일**, **같은 금액**이 **3달 연속**. 고정지출과 같은 폭(금액만 ±10% 대신 같은 금액) |
| S-06 | [저축이에요] | `confirmed`. 받는 계좌를 앱에 연결해 뒀으면 그 계좌 용도를 **저축**(`budget_role = savings`)으로 표시하고, 근거 이체는 거래 종류 **`saving`** |
| S-07 | [아니에요] | `ignored`(다시 묻지 않음). 근거 이체는 **`own_transfer`**(내 계좌끼리 옮긴 돈 — 소비도 저축도 아님) |
| S-08 | 온보딩 [확인하고 다음] | 고정지출과 달리 **후보마다 다 골라야 넘어간다**(저축은 자동 확정 금지, TXN-005). 화면은 고른 대로 확정 목록 · 무시 목록을 각각 보낸다 |
| S-09 | 직접 추가 때 받는 값 | 이름 · 금액(1,000원 ~ 1억 원) 필수. 이체일 · 보내는 계좌 · 받는 계좌는 선택 |
| S-10 | 이번 달 실제로 저축했는지(실적) | **이 명세 밖.** 이 API는 '매달 하기로 한 저축 목록'만 다룬다. 실적 집계는 거래 · 예산 쪽(TXN-005) |
| S-11 | 후보의 계좌를 고쳐서 확정하면? (PR #29 리뷰) | **후보(`suggested`)는 보내는 · 받는 계좌를 바꿀 수 없다**(400). 후보는 'A → B 이체를 3번 봤다'는 근거로 만든 것이라, 계좌를 바꾸면 근거와 안 맞는 계좌가 저축용으로 표시되고 엉뚱한 이체가 저축으로 처리된다. 계좌가 틀렸으면 [아니에요] 후 직접 추가. 이름 · 금액 · 이체일은 고칠 수 있다. **확정** 항목은 계좌를 바꿀 수 있고, 이미 `saving`으로 처리된 지난 이체는 그대로 두며(실제로 그 계좌에 저축했던 기록) 새 받는 계좌에만 저축용 표시를 붙인다 |
| S-12 | 저축이 바뀌면 예산 초안은? (PR #29 리뷰) | 정기 저축 **추가 · 확정 · 금액 변경 · 중지**로 저축 최소 금액이 바뀌면 **승인 전 예산 초안은 바로 만료**(승인 불가, 다시 만들기). **승인된 이번 달 예산은 그대로**, 다음 달 예산부터 새 최소 금액을 쓴다(BUD-005). 결정기록 D: 초안 만료는 '고정지출 또는 저축 최소 금액이 바뀔 때만' |

### 고정지출과 다른 점

| | 고정지출 (fixed.md) | 정기 저축 (이 명세) |
|---|---|---|
| 카테고리 | 필수 | **없음** (저축은 카테고리가 아님. 보내면 400) |
| 결제 수단 | 계좌 · 카드 · 모름 | 보내는 계좌 · 받는 계좌 (둘 다 선택) |
| 후보 금액 비교 | ±10% | 같은 금액 |
| 온보딩 [확인하고 다음] | 남은 후보를 한 번에 확정 | 후보마다 다 골라야 넘어감 |
| 납부 예정(`PaymentDue`) | 만듦 (계좌 · 출금일 있을 때) | **안 만듦**. 저축은 예산의 저축 몫으로 챙긴다 |
| 근거 거래 고르기 · '이 결제가 맞나요?' | 있음 (카드) | 없음 |
| 확정했을 때 | — | 받는 계좌 용도 = 저축, 근거 이체 = `saving` |

## 공통: 정기 저축 한 건의 응답 형태

목록 · 추가 · 수정 · 확정 · 무시 응답의 한 건은 모두 이 모양이다.

| 이름 | 타입 | 뜻 |
|---|---|---|
| `savingId` | UUID | 정기 저축 ID |
| `name` | 문자 | 이름 (예: "청약", "신한 자유적금"). 후보는 받는 계좌 이름으로 채운다 |
| `amount` | 정수 | 매달 저축액(원), 1,000 ~ 100,000,000 |
| `transferDay` | 정수 또는 `null` | 매월 이체일 1~31. 모르면 `null`. 그 달에 없는 날은 말일 |
| `fromAccount` | 객체 또는 `null` | 보내는 내 입출금 계좌 `{ accountId, displayName, status }` ([계좌 · 카드 표시](../API_RULES.md#계좌--카드-표시)) |
| `toAccount` | 객체 또는 `null` | 받는 저축 계좌. 다른 은행이라 연결 안 했으면 `null` |
| `status` | 문자 | `suggested`(후보) · `confirmed`(확정). 목록에는 이 둘만 나온다 |
| `sourceType` | 문자 | `detected`(자동 발견) · `manual`(직접 추가). 후보를 확정해도 `detected` 유지 |
| `confirmedAt` | 시각 또는 `null` | 사용자가 확정한 시각 |
| `evidenceCount` | 정수 | 근거 이체 수. 화면 "최근 3개월 3회 감지" |
| `lastTransferOn` | 날짜 또는 `null` | 근거 이체 중 가장 최근 날짜 |

```json
{
  "savingId": "6f1d2a3b-4c5d-4e6f-8a9b-0c1d2e3f4a5b",
  "name": "신한 자유적금",
  "amount": 300000,
  "transferDay": 25,
  "fromAccount": { "accountId": "27d3dbb3-1ee8-43b7-9134-9e8ff01991d4", "displayName": "국민 급여통장 · ****5678", "status": "connected" },
  "toAccount": { "accountId": "9c2e7b10-5a4f-4d8e-b3c1-7f6a5e4d3c2b", "displayName": "신한 자유적금 · ****9012", "status": "connected" },
  "status": "suggested",
  "sourceType": "detected",
  "confirmedAt": null,
  "evidenceCount": 3,
  "lastTransferOn": "2026-09-25"
}
```

**보내는 값 공통 규칙**

| 칸 | 규칙 | 오류 문구 (`fields`) |
|---|---|---|
| `name` | 앞뒤 공백 제거 후 1~100자 | "이름은 1~100자로 입력해 주세요." |
| `amount` | 정수 1,000 ~ 100,000,000 | "금액은 1,000원 ~ 1억 원으로 입력해 주세요." |
| `transferDay` | 정수 1~31 또는 `null` | "이체일은 1일부터 31일 사이로 입력해 주세요." |
| `fromAccountId` | 내 계좌 · 관리 대상(`is_selected`) · 입출금(`account_type = demand`) · 연결 해제 아님, 또는 `null` | "선택할 수 없는 계좌예요." |
| `toAccountId` | 내 계좌 · 연결 해제 아님(예적금도 됨, 관리 대상이 아니어도 됨), 또는 `null` | "선택할 수 없는 계좌예요." |
| 두 계좌 | 둘 다 있으면 서로 달라야 함 | `nonFieldErrors`: "보내는 계좌와 받는 계좌가 같아요." |
| 표에 없는 칸 | `status` · `category` 등을 보내면 400 | "이 칸은 보낼 수 없어요." |

- 없는 계좌 · 남의 계좌 · 고를 수 없는 계좌는 모두 같은 문구로 답한다(API_RULES 본문 ID 규칙).
- 빈 글자 `""`는 400이다. 비우려면 `null`로 보낸다.

## 1. 정기 저축 목록 보기

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 저축 확인 화면(온보딩)과 저축 관리 화면을 열 때 |
| 어디로 | `GET /api/budgets/savings/` |
| 로그인 필요 | O · 세션 쿠키 |
| 명세 상태 | 초안 |

**보내는 값**: 없음.

**받는 값 (200 OK)**

| 이름 | 타입 | 뜻 |
|---|---|---|
| `items` | 배열 | 후보(`suggested`)와 확정(`confirmed`). 중지 · 무시는 없다 |
| `summary.minimumMonthly` | 정수 | **저축 최소 금액** = 확정 항목 `amount` 합계(S-02). 후보는 넣지 않는다 |
| `summary.suggestedCount` | 정수 | 후보 수 |

- 정렬: **후보 먼저**(최근에 찾은 순, `created_at` 최신순) → 확정(이체일 빠른 순, 이체일 모름은 맨 아래). 고정지출과 같다.
- 페이지는 나누지 않는다.

```json
{
  "items": [
    { "savingId": "…", "name": "주택청약", "amount": 200000, "transferDay": 10, "status": "suggested", "sourceType": "detected", "…": "…" },
    { "savingId": "…", "name": "신한 자유적금", "amount": 300000, "transferDay": 25, "status": "confirmed", "sourceType": "detected", "…": "…" }
  ],
  "summary": { "minimumMonthly": 300000, "suggestedCount": 1 }
}
```

**화면**

- 온보딩 저축 확인: 후보마다 [저축이에요] / [아니에요]. 아래 "매달 꼭 저축할 돈"은 **화면에서 고른 것 기준으로 미리 보여 주고**, 저장 뒤에는 `summary.minimumMonthly`를 쓴다.
- 후보가 없으면 "매달 반복되는 내 계좌끼리 이체를 찾지 못했어요. 저축 금액은 지킬 돈 설정에서 정할 수 있어요."
- 후보 카드: 받는 계좌 이름(없으면 `name`) · "매월 25일 · 국민 · 5678에서 보냄" · 금액 · "최근 3개월 3회 감지"(`evidenceCount`).
- **[+ 저축 직접 추가]**: 감지되지 않은 저축(다른 은행 적금 등) → `2. 직접 추가` 팝업.
- **마이 > 정기 저축**에서 같은 화면을 열면 확정된 저축 목록과 [수정](→ `3. 수정` · `4. 중지` 팝업)을 보여 준다. 고정지출 화면을 온보딩과 마이에서 같이 쓰는 것과 같다.

**실패하면**: 로그인 안 됨 = 403 `not_authenticated`, 서버 오류 = 500 `server_error` (공통).

## 2. 정기 저축 직접 추가

| 칸 | 내용 |
|---|---|
| 어떤 기능 | [+ 저축 직접 추가] 팝업에서 [추가하기] |
| 어디로 | `POST /api/budgets/savings/` |
| 로그인 필요 | O · 세션 쿠키 + CSRF |
| 요청 번호 | `Idempotency-Key` (팝업을 열 때 만든 번호, 선택) |
| 명세 상태 | 초안 |

**보내는 값**

| 이름 | 타입 | 필수 | 설명 | 예시 |
|---|---|---|---|---|
| `name` | 문자 | O | 1~100자 | `"청약"` |
| `amount` | 정수 | O | 1,000 ~ 100,000,000 | `100000` |
| `transferDay` | 정수 또는 `null` | X | 1~31. 생략하면 `null`(모름) | `10` |
| `fromAccountId` | UUID 또는 `null` | X | 보내는 내 입출금 계좌 | `null` |
| `toAccountId` | UUID 또는 `null` | X | 받는 저축 계좌 | `null` |

```json
{ "name": "청약", "amount": 100000, "transferDay": 10, "fromAccountId": null, "toAccountId": null }
```

**받는 값 (201 Created)**: 공통 한 건 형태. `status = confirmed`, `sourceType = manual`, `confirmedAt` = 지금, `evidenceCount = 0`.

- 받는 계좌를 골랐으면 그 계좌 용도를 저축으로 표시한다(S-06과 같음).
- 저축 최소 금액이 늘어나므로 승인 전 예산 초안은 만료된다(S-12).
- 같은 요청 번호 · 같은 내용으로 다시 보내면 처음 응답을 그대로 준다. 다른 내용이면 `409 idempotency_conflict`.

**실패하면**

| 상황 | 상태 | `code` | 화면 |
|---|---|---|---|
| 칸 오류 (위 공통 규칙) | 400 | `invalid` | 칸 아래 `fields` 문구 |
| 같은 요청 번호 · 다른 내용 | 409 | `idempotency_conflict` | "이미 처리 중인 요청이에요." 후 팝업 다시 열기 |
| 로그인 안 됨 · 서버 오류 | 403 · 500 | `not_authenticated` · `server_error` | 공통 |

## 3. 정기 저축 수정

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 정기 저축 수정 팝업에서 [수정 저장] |
| 어디로 | `PATCH /api/budgets/savings/<id>/` |
| 로그인 필요 | O · 세션 쿠키 + CSRF |
| 명세 상태 | 초안 |

- 수정할 수 있는 것은 목록에 나오는 **후보 · 확정**뿐이다. 중지 · 무시 항목은 `404`.
- 보내는 값은 직접 추가와 같은 칸이며 **바꿀 칸만** 보낸다. 안 보낸 칸은 그대로, `null`은 비우기(`transferDay` · `fromAccountId` · `toAccountId`만). `name` · `amount`에 `null`이면 400 "이름은 / 금액은 비울 수 없어요."
- 빈 객체 `{}`는 400 "바꿀 값을 하나 이상 보내 주세요."
- **후보(`suggested`)는 `fromAccountId` · `toAccountId`를 바꿀 수 없다**(S-11). 지금과 **다른** 값을 보내면 `400 invalid`(지금과 같은 값은 바뀌는 게 없으므로 통과) — `fields.<그 칸>`: "찾은 저축의 계좌는 바꿀 수 없어요. [아니에요]를 누르고 직접 추가해 주세요."
- 확정 항목의 받는 계좌를 바꾸면 새 계좌도 저축 용도로 표시한다. 이미 `saving`으로 처리된 지난 이체는 그대로 둔다. 보내는 계좌 = 받는 계좌가 되면 400(바꾼 뒤 모양으로 검사).
- 금액을 바꾸면 저축 최소 금액(목록 `summary.minimumMonthly`)이 바로 바뀐다. **승인 전 예산 초안은 바로 만료**되고(S-12), **승인된 이번 달 예산은 자동으로 바꾸지 않으며** 다음 달 예산부터 새 금액을 쓴다(BUD-005).

```json
{ "amount": 350000 }
```

**받는 값 (200 OK)**: 공통 한 건 형태.

**실패하면**

| 상황 | 상태 | `code` |
|---|---|---|
| 칸 오류 · 빈 객체 · 필수 칸 `null` · 후보의 계좌 변경(S-11) | 400 | `invalid` |
| 주소의 없는 · 남의 · 형식 틀린 ID, 중지 · 무시 항목 | 404 | `not_found` ("찾을 수 없어요.", `fields` 없음) |

## 4. 정기 저축 중지

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 정기 저축 수정 팝업에서 [더 이상 안 해요] · 연결 해제 확인 창에서 "같이 그만할까요?"에 체크한 저축 (결정기록 3-3 F) |
| 어디로 | `DELETE /api/budgets/savings/<id>/` |
| 로그인 필요 | O · 세션 쿠키 + CSRF |
| 명세 상태 | 초안 |

- 행을 지우지 않고 `status = stopped`로 바꾼다. 목록에서 빠지고 저축 최소 금액에서 빠진다.
- 중지할 수 있는 것은 **확정** 항목. 이미 중지면 다시 보내도 `204`(이미 그 상태). 후보는 중지가 아니라 [아니에요](6번)로 처리하므로 후보 · 무시 항목은 `404`.
- 다시 시작하는 API는 1차에 없다. 다시 하면 직접 추가로 새로 만든다.
- 연결 해제 때 체크하지 않은 저축은 그대로 남고, 보내는 · 받는 계좌가 `disconnected`로 보여 "연결 해제됨 · 다시 고르기"를 표시한다(F). 고정지출(fixed.md)과 같다.
- 받는 계좌의 저축 용도 표시는 그대로 둔다(계좌 용도는 계좌 관리에서 바꾼다).
- 저축 최소 금액이 줄어드므로 승인 전 예산 초안은 만료되고, 승인된 이번 달 예산은 그대로 둔다(S-12).

**받는 값 (204 No Content)**: 본문 없음.

**실패하면**: 주소 ID 오류 · 후보 · 무시 항목 → `404 not_found`.

## 5. 후보 확정 ([저축이에요])

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 저축 확인 화면 [확인하고 다음]에서 [저축이에요]를 고른 후보들 |
| 어디로 | `POST /api/budgets/savings/confirm/` |
| 로그인 필요 | O · 세션 쿠키 + CSRF |
| 요청 번호 | `Idempotency-Key` (버튼을 누를 때 만든 번호, 선택) |
| 명세 상태 | 초안 |

**보내는 값**

| 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `savingIds` | UUID 배열 | O | 1개 이상. 내 후보(`suggested`) 또는 이미 확정(`confirmed`)인 것 |

```json
{ "savingIds": ["6f1d2a3b-4c5d-4e6f-8a9b-0c1d2e3f4a5b"] }
```

**처리 (S-06)**

- `suggested` → `confirmed`, `confirmedAt` 기록. `sourceType`은 `detected` 그대로.
- 받는 계좌가 있으면 그 계좌 `budget_role = savings`(저축 용도). 이 계좌는 고정지출 결제 계좌 고르기에서 빠진다(fixed.md).
- 근거 이체들의 거래 종류 `transaction_type = saving` → 소비로 세지 않는다.
- 이미 `confirmed`인 것은 그대로 두고 성공으로 답한다.
- 새로 확정된 것이 있으면 저축 최소 금액이 늘어나므로 승인 전 예산 초안은 만료된다(S-12).
- 하나라도 고를 수 없는 ID(없음 · 남의 것 · 무시 · 중지)가 있으면 **전부 저장하지 않고** 400.

**받는 값 (200 OK)**: `{ "items": [한 건 형태, …] }` — 보낸 순서가 아니라 처리된 항목.

**실패하면**

| 상황 | 상태 | `code` | `fields` |
|---|---|---|---|
| 빈 배열 · 형식 틀린 ID · 고를 수 없는 ID | 400 | `invalid` | `savingIds`: "선택할 수 없는 항목이에요." |
| 같은 요청 번호 · 다른 내용 | 409 | `idempotency_conflict` | 없음 |

## 6. 후보 무시 ([아니에요])

| 칸 | 내용 |
|---|---|
| 어떤 기능 | 저축 확인 화면 [확인하고 다음]에서 [아니에요]를 고른 후보들 |
| 어디로 | `POST /api/budgets/savings/ignore/` |
| 로그인 필요 | O · 세션 쿠키 + CSRF |
| 요청 번호 | `Idempotency-Key` (버튼을 누를 때 만든 번호, 선택) |
| 명세 상태 | 초안 |

- 보내는 값 · 받는 값 · 실패는 5번과 같다(`savingIds`).
- **처리 (S-07)**: `suggested` → `ignored`. 같은 후보를 다시 묻지 않는다. 근거 이체는 `transaction_type = own_transfer`(내 계좌끼리 옮긴 돈 — 소비도 저축도 아님). 이미 `ignored`면 그대로 성공. 확정 · 중지 항목은 400.

### 온보딩 [확인하고 다음] 흐름 (S-08)

1. 후보마다 [저축이에요] / [아니에요]를 **모두** 골라야 버튼이 동작한다. 하나라도 안 골랐으면 "찾은 이체마다 저축인지 골라 주세요."
2. [저축이에요] 고른 것이 있으면 `5. 후보 확정`, [아니에요] 고른 것이 있으면 `6. 후보 무시`를 보낸다. 두 요청은 각자 요청 번호를 쓴다.
3. 둘 다 성공하면 다음 화면(예산 방향)으로. 하나가 실패하면 그 안내를 보여 주고 머문다(성공한 쪽은 이미 저장돼 있으므로 다시 눌러도 '이미 그 상태'로 성공).
4. 다음 화면은 `summary.minimumMonthly`(저축 최소 금액)를 쓴다.
