# 소비 분석 에이전트 1차 마무리

기준일: 2026-11-03 · 더미 DB 기준 · 상태: 1차 마무리, 후속 수정 범위는 별도 결정

## 역할과 수정 내용

소비 분석 에이전트는 **소비 변화와 그 근거를 확인해 예산 판단을 돕는 역할**을 맡는다. 예산 변경안 제안·승인·적용은 예산 조정 에이전트의 역할이다. 예산을 직접 바꾸지 않는 것은 기능 부족이 아니라 역할 분리다.

- **기본 질문·대화 처리:** 소비/예산 대상과 총액/전반 분석을 구분하고, 비교·날짜·직전 맥락 지침을 정리했다. 예산 기간에 동의할 때 이전 기간 정보(`period_said` 포함)를 함께 초기화했다. “거기서 제일 많이 나간 건?”은 가장 큰 결제 1건으로 보는 제품 결정을 반영했다.
- **조회 범위와 근거:** 기간·주말·시간대 등 조건을 조회와 설명에 유지하도록 보완했다. 자료 없음과 0원을 구분하고, 식별할 수 없는 품목을 카테고리 전체로 대신 판단하지 않도록 했다.
- **B 분석:** 가격 부담은 건당 평균, 구매 빈도는 결제 건수로 연결했다. 질문 대상의 근거가 부족하면 추가 조회하고, 이미 충분하면 생략한다. 구체적인 가설 없이 범위의 총액만 반복한 해석은 계획 단계에서 다시 확인할 수 있게 했다.
- **답변 연결:** 일반 증가 설명에 전체 증가액을 필수로 포함하고, 일부 항목의 증가가 전체보다 큰 이유와 분류 기준 전환을 설명하도록 했다. 근거 상태에 맞는 다음 확인 사항을 붙이고, 이미 답한 지표를 다시 확인하라고 반복하지 않도록 했다.
- **정확성 유지:** 금액·차이·평균 등 계산은 서버가 담당한다. B의 답변 LLM은 검증 가능한 서버 문장 ID를 선택하며, 검사 실패 시 기존 설명으로 대체한다. 관측된 결제 변화만으로 실제 원인·상품 가격·약속 횟수를 단정하지 않는다.

실제 LLM 호출은 기본 기능 최종 검증 **371/400회**, 이후 B 보완 검증 **94/100회**를 사용했다. 두 실행 모두 호출 오류·재시도는 0회였다. 이전 모든 작업의 누적 호출 수를 뜻하지 않는다.

기본 해석 지시문 본문은 정리 과정에서 **86→82줄, 3,094→3,055토큰**으로 줄었다. 이후 B 보완에서는 본문을 유지하고, 공통 가설 지침을 **9→11줄, 340→428토큰**으로 보완했다. 이 지침은 해석 요청에도 첨부되므로 전체 입력이 불변인 것은 아니다. 토큰은 동일한 `o200k_base` 기준이다.

실제 답변에서 확인한 변화:

- “밥값이 올라서야?” → 총액·시간대 대신 **건당 평균 12,000→15,000원**, 상품 가격 상승 여부는 판단 불가라고 답했다.
- “밤에 많이 먹어서?” → 근거가 부족한 데이터에서는 밤을 추가 조회하고, 밤 근거가 이미 있는 데이터에서는 조회를 생략했다.
- “쇼핑 한 번에 쓰는 돈이 비싸진 거야?” → **건당 평균 80,000→150,000원**으로 식비 외 범위도 확인했다.

검증 중 첫 전체 자동 테스트에서 가짜 응답기의 필수 근거 선택 문제와 변경된 문장·검사 순서에 관한 기대 차이로 3건이 실패했다. 대역과 자동 테스트를 정리한 뒤 전체를 다시 실행해 새 실패 없이 마쳤다. 실제 LLM 평가의 기존 15개 기대값은 변경하지 않았다.

## 남은 한계

1. **기본 기능의 잔여 실패:** 마지막 전체 검증에서 `h10`(이전 결과 재표시), `n10`(남은 예산의 맥락), `b10`(스타벅스), `b17`(가장 많이 쓴 대상의 설명), `c18`(미지원 예산 분할), `p05`(미지원 기간 처리)가 최종 결정 기준에 불일치했다. 질문 목록의 `R-1`·`R-4`도 배달 조회 대신 카테고리를 되물었다. 이후 B 보완에서 이 전체 목록을 다시 돌리지 않았으므로 해결됐다고 보지 않는다.
2. **B 채점 1건 불일치:** `e13` “저녁 약속이 많아서?”의 기존 기대는 금액 비교지만, 현재는 **저녁 결제 14→10건**을 답하고 실제 약속 횟수는 알 수 없다고 구분한다. 빈도 의미에 더 맞는 답이라는 검토 의견이 있으나, 기대값 변경 없이 실패로 남겼다.
3. **계획 LLM의 한계:** 배민 질문(`e07`)의 무관한 시간대 조회는 서버가 배달 조회로 교정했고, 신규 개업 질문(`e10`)의 무관한 가게 조회는 차단했다. 최종 경로의 통과 점수가 계획 LLM 자체의 완전성을 뜻하지 않는다.
4. **데이터·표현의 한계:** 더미 데이터의 제한된 질문을 한 번씩 실행한 결과다. 실제 사용자·실제 DB에서의 품질은 별도 확인이 필요하다. 커피 품목·개업 여부 등은 현재 내역으로 식별할 수 없고, “방문 유형·상쇄” 같은 표현은 더 쉽게 다듬을 여지가 있다.
5. **분석 범위:** B는 제한된 추가 조회를 수행하는 흐름이다. 다음 확인 안내가 자동으로 후속 분석을 반복 실행하는 것은 아니다. 예산 변경은 별도 에이전트가 담당한다.

현재 상태를 소비 분석의 **1차 마무리 기준점**으로 둔다. 이후에는 실제 사용에서 확인한 실패 사례를 바탕으로 수정 범위를 별도로 정한다. 이 문서 작성에서는 추가 코드 수정·테스트·LLM 호출·커밋을 하지 않았다.
