# 거래 분류 에이전트 메모

> 담당: 권세진 · 시작 2026-10-29 · 통합 검수 때 이 파일이 검수 목록이 된다 (에이전트 개발 당부 사항 3번)

흐름: 결제대행 접두어 떼기 → 1 다품목 → 2 사용자 기억 → 3 규칙·사전 → 4 SVM → 5 검색+Jev → 6 확인 필요 (10/30 1~6단계 모두 구현).
`transaction_type = spending` 거래만 분류한다. 실행 위치는 거래 저장 뒤 처리의 2단계 `classify_spending`이다.

## 쓰는 API·함수

| 무엇 | 어디 | 용도 |
|---|---|---|
| `classify_spending(user, txs)` | `backend/finance/pipeline.py` | 에이전트 입구 (거래 저장 뒤 처리 2단계) → `classifier.classify()` 호출 |
| `classify()` · `predict()` · `rule_category()` · `judge()` · `search_store()` · `ask_jev()` | `backend/finance/classifier.py` | 분류 에이전트 본체. 모델·Jev 클라이언트는 처음 쓸 때 한 번만 만듦 |
| 카드 승인내역 동기화 `sync_card()` | `backend/finance/sync_cards.py` | 카드 거래를 `spending`·확인 필요로 저장 → 파이프라인 호출. 지금 분류가 실제로 도는 경로 |

| TypeSafe Jev `Choice` | 외부 API (`TYPESAFE_API_KEY` · `JEV_MODEL`), `typesafe-sdk` (requirements에 있음) | 5단계 판단. 선택지 10개 + 기타 + 판단 보류 |
| 거래 분류 수정 `PATCH /api/finance/transactions/<id>/` | 기존 API (혜리) | 사용자 확정 → 다음 분류의 기억이 됨. 고치지 않고 그대로 씀 |
| 거래 목록 `GET /api/finance/transactions/?category=UNCLASSIFIED` | 기존 API (혜리) | '확인 필요' 표시. 고치지 않고 그대로 씀 |

## 임시 결정

**10/30 5단계 구현 내용**
- 순서: 상호(법인 표기만 뺌)로 네이버 검색 → 0건이면 카카오 → 끝 칸 업종 (카카오는 끝 칸이 상호에 들어 있으면 한 칸 앞)
- 검색 업종이 편의점·슈퍼마켓·대형마트·백화점·종합쇼핑몰·○○마트면 Jev 없이 '확인 필요'(다품목)
- 검색 업종이 소프트웨어·애플리케이션·금융·은행·증권·기업·회사·사무소·협회면 근거로 넘기지 않음
- Jev 선택지 12개, 설명은 분류 기준 2장. `confidence` ≥ 0.9(임시)이고 판단 보류가 아니면 자동 분류(출처 `llm`). 아니면 '확인 필요' + 판단 보류를 뺀 확률 상위 3개 후보
- 판단 근거는 거래의 `field_states["classifier"]`에 남김: 검색 출처·업종·Jev 모델·답·confidence·확률·걸린 시간(ms)·오류 이름

- `TYPESAFE_API_KEY`·`JEV_MODEL`이 없으면 5단계를 건너뛰고 SVM 후보로 '확인 필요' (팀원 PC·테스트)

- LLM 장애·검색 실패면 '확인 필요'로 끝냄 (파이프라인 재시도는 그대로)
- 개발·테스트 모델은 저렴한 OpenAI 모델 (이름 미정)
- 4단계(근거 → 판단)는 Jev `Choice`가 함 (10/26 「소비카테고리_분류_워크플로우」 설계안을 따름. 범용 LLM은 필요할 때만). 확률에 임계값을 걸어 확정, 2·3등은 '확인 필요' 후보. Jev 임계값은 실거래 표본으로 정함
- 검색 업종은 **맨 끝 칸**(가장 세부)을 기준으로 봄. 큰 분류는 회사마다 달라서 믿지 않음 (10/29 테스트: 새봄동물병원 → 카카오 `가정,생활 > 반려동물 > 동물병원`, 네이버 `건강,의료>동물병원`, 팀 기준 MEDICAL_HEALTH. Jev에 카카오 전체 경로를 넣으니 MEDICAL_HEALTH 1.0 → 0.97, 줄어든 0.03은 HOUSEHOLD로 감 = 큰 분류가 판단을 흔듦)
  - 단, 프랜차이즈는 카카오 끝 칸이 업종이 아니라 브랜드명 (스타벅스 → `스타벅스`, GS25 → `GS25`). 네이버는 `카페`·`편의점`으로 줌 → **검색은 네이버를 먼저**, 0건이면 카카오 (카카오는 끝 칸이 상호에 들어 있으면 한 칸 앞을 씀)
- 검색 전에 2단계 규칙으로 거를 것 (10/29 9개 이름 테스트)
  - 결제대행사 접두어(`NICE*`, `KCP*` 등): 검색 0건 → 접두어를 떼고 뒤 이름으로 분류
  - 편의점·마트·종합몰(GS25, 쿠팡 등): Jev는 팀 정책을 몰라 FOOD 0.71 · HOUSEHOLD 0.41로 답함 → Jev에 보내지 않고 규칙으로 '확인 필요'
  - 법인명((주)우아한형제들, 비바리퍼블리카): 검색이 본사(업종 `애플리케이션개발`·`금융서비스`)를 찾아 Jev가 **틀린 답을 0.81까지 확신** → 법인명→서비스 사전(배민=FOOD, 토스=이체 등)으로 처리하고, 업종이 소프트웨어·금융 같은 "가게가 아닌" 결과는 근거로 넘기지 않음
- 실거래 가맹점명 49건 SVM 결과 (10/29, 이름 목록은 커밋하지 않음)
  - 소비가 아닌 이름 6건(이자·ATM입금·캐시백·페이 충전·임대료)이 섞여 있음 → `classify_spending`은 1단계 `link_basics`가 `spending`으로 정한 거래만 받아야 함 (혜리 님 단계에 의존)
  - `비식별거래처_XXXX` 10건 중 6건이 FOOD 0.85 이상 → **뜻 없는 이름도 SVM은 FOOD로 확신함**. 상호처럼 안 생긴 이름은 SVM 확정 전에 규칙으로 거를 것
  - 실제 소비 이름 33건 중 SVM 0.85 이상은 15건(약 45%). 상가정보 검증의 68%보다 낮음 → 4단계 호출이 예상보다 많음
  - SVM이 틀린 유형: 교통(티머니·고속버스·택시 `이동의즐거움_택시`) → FOOD, 구독(애플뮤직) → HOUSEHOLD, 법인명((주)아성다이소) → FOOD. 2단계 규칙 후보: 교통 키워드, 구독 사전, 법인명 사전
  - 편의점(이마트24·세븐일레븐)·마트는 SVM 0.64~0.75 FOOD → 규칙으로 '확인 필요'
  - 카드사 글자 수 제한으로 잘린 이름이 있음(…병원외래, …(주)모바일도곡) → 검색으로 보완
- 검색이 효과 있던 경우: 잘린 이름 `새봄동물` → 검색이 `새봄동물병원`을 찾아 Jev 0.33 → 1.00. 이름만으로 답이 나오는 거래(행복약국·우리식당)는 SVM에서 이미 0.98 이상이라 4단계까지 안 옴
- Jev `Choice`의 카테고리 설명에 팀 정책 예외를 적음 (예: 의료·건강에 "동물병원 포함"). 출처는 `scripts/spending_classifier/common.py`의 `SUFFIXES`
- Jev 답에는 `confidence`와 라벨별 `probabilities`가 따로 있고 값이 다름 (NICE*쿠팡: confidence 0.51, HOUSEHOLD 확률 0.56). 임계값을 어느 값에 걸지 잘 모르겠음 → 표본 테스트에서 둘 다 기록
- 같은 입력도 호출마다 Jev 값이 달라짐 (NICE*쿠팡 이름만: 5번 셀 0.41 → 4번 셀 0.51). 임계값 근처 거래는 결과가 바뀔 수 있음 → 임계값은 여유를 두고 정함
- Jev는 이유 문장을 주지 않음 → '확인 필요' 이유는 템플릿으로 할지 OpenAI로 쓸지 잘 모르겠음
- SDK는 기본 모델을 `TYPESAFE_DEFAULT_MODEL`에서 읽는데 우리 `.env`는 `JEV_MODEL` → 호출할 때 `model=`로 직접 넘김
- 은행 출금 거래는 상호명 대신 적요만 있을 수 있음 → 적요를 상호명처럼 넣을지 잘 모르겠음
