# 청년 정책 추천 에이전트 메모

> 담당: 권세진 · 시작 2026-11-03 · 통합 검수 때 이 파일이 검수 목록이 된다 (에이전트 개발 당부 사항 3번)
> 다른 PC에서 이어서 작업할 때도 이 파일부터 읽는다.

통합 챗봇에서 사용자 조건과 고민을 받아 청년 정책 3개를 추천한다. RAG 구조다.

```
① 미리: 정책 정리 → 임베딩 → pgvector 저장 (sync_policies)
② 질문마다: 지역 · 마감 거르기 → 벡터 + 텍스트 검색 → 조건 검사 → 정렬 → 3개
③ 답변: LLM 은 해석과 추천 이유만. 정책명 · 기간 · 금액 · 링크는 DB 값
```

## 진행 상태

| 단계 | 할 일 | 상태 |
|---|---|---|
| 1 | 데이터 넣기 (정리, 적재, 임베딩) | **완료** |
| 2 | 검색 만들기 (`search.py`, 확인 명령 `policy_search`) | 구현 완료, 결과 확인 대기 |
| 3 | 정답 문제 만들기 (질문 20개 + 정답 정책) | |
| 4 | 자연어 잘 찾기 (질문 다듬기, 필요별 검색, 키워드 추출) | |
| 5 | 조건 거르기 (`eligibility.py`) | |
| 6 | 답변과 버튼 대화 (`agent.py`, LangChain 체인, `PolicyProfile`) | |
| 7 | 챗봇 연결 (`chat/engine.py`, `router_core`) | |

단계마다 결과를 확인하고 다음 단계로 간다.

## 다른 PC에서 이어서 하기

1. 코드 받기: PR 이 병합 전이면 `git fetch origin` 후 `git switch feat/policy-agent`, 병합됐으면 main 에서 새 브랜치. 2단계까지 모두 `feat/policy-agent` (PR 97, 작업 이어가기용 · 아직 병합하지 않음)
2. `pip install -r requirements.txt`
3. `.env` 준비: `OPENAI_API_KEY`, `EMBEDDING_MODEL` 포함 (`docs/ENV_SETUP.md`)
4. DB 는 pgvector 가 있어야 한다 (`pgvector/pgvector:pg17`, `docs/ENV_SETUP.md` 3번)
5. `cd backend` 후 `python manage.py migrate`
6. 정책 파일 `youth_policies_20261029.json` 을 저장소 밖에 둔다 (팀 공유 파일, 커밋하지 않는다). 법정동코드 · API 코드정보 엑셀은 받지 않아도 된다
7. 적재 + 임베딩 (약 40초, OpenAI 임베딩 약 100만 토큰):

```bash
python manage.py sync_policies --file <파일 경로> --data-date 2026-10-29 --live-embed
```

8. 확인: `받음 3664`, `임베딩 완료 3664 · 남음 0`, 테스트는 `python manage.py test policies`

코드표와 지역 표는 저장소에 있다(`policies/codes.py`, `policies/data/regions.json`). 원본 엑셀은 다시 필요 없다.

## 정해진 것

**대상과 범위**
- 추천 대상은 정책 전 분야. 대출 · 대출보증 정책도 포함한다(기획서의 '상환 의무 제외'에서 변경).
- 정책 납입액 · 예산 비교(POL-004)는 후속 개발.
- LangChain 은 `langchain-core` 만 쓴다. LangGraph · `langchain-openai` · `langchain-postgres` 는 쓰지 않는다.

**조건 입력 (별도 화면 없이 채팅 버튼)**
- 온보딩 값은 다시 묻지 않는다. 나이 = 생년월일, 여성 조건 = 성별. 생년월일이 없으면 내 정보로 안내하고 끝낸다.
- 묻는 것: 지역(시도 16개 → 시군구 → 구가 있는 시 13곳은 구, 세종은 시도에서 끝), 특화 대상(여러 개, [다 골랐어요] [해당 없음] [건너뛰기]).
- 취업 상태: 월급 정보가 있으면 묻지 않고 재직자로 본다. "취업 준비 중"처럼 말하면 그 말을 따른다. [조건 바꾸기]에서는 묻는다.
- 묻지 않는 것: 학력, 전공, 혼인, 주거 형태, 연소득. 해당 요건 정책은 '확인 필요'로 표시한다.
- 끝에 "다음에도 이 조건으로 추천할까요?" 를 묻고 동의한 경우만 회원별로 저장한다.
- 저장은 핸들러가 하지 않는다. `reply.save_profile` 을 돌려주면 엔진이 대화 저장과 같은 트랜잭션에서 한다(409 면 저장도 안 됨).

**자격 판단 (코드가 함, 위에서부터 처음 맞는 줄)**
1. 정책이 제한없음 → 충족
2. 정책 칸이 비었거나 사용자 값을 모름 → 확인 필요
3. 사용자 코드가 정책 코드에 있음 → 충족
4. 정책 코드에 '기타'가 있음 → 확인 필요
5. 그 밖 → 불충족 (추천에서 뺌)

- 지역은 코드를 그대로 비교하지 않고 `match` 목록으로 비교한다. 화성시 코드로만 적힌 정책 345건, 천안시 99건이 있다.
- 소득은 탈락 근거로 쓰지 않는다. 금액 단위와 본인/가구 구분을 알 수 없다.

**대화 규칙**
- 버튼은 이름이 문장으로 들어온다. 답할 때 {이름: 동작}을 상태에 저장해 두고 같은 이름이면 그 동작을 실행한다. 정책번호는 서버 상태에서만 나온다.
- 추천 뒤 담당 유지(`replied`). "취소 · 그만 · 됐어"는 `ended`, 정책 상태는 핸들러가 지운다.
- 다른 담당을 다녀오면 [이어서 하기] [새로 추천]. 소비 · 예산 질문은 상태를 바꾸기 전에 `not_mine`.
- 핸들러는 DB 에 쓰지 않는다. 검색 오류는 추천 없음으로 바꾸지 않고 `failed`.
- 모든 추천에 "자격 확정이 아니에요. 공고 원문으로 확인해 주세요."를 붙이고 "신청 가능"이라고 쓰지 않는다.

**검색 (2단계, 11-07)**
- 지역 · 마감을 SQL 로 거른 뒤 벡터 순위와 키워드별 순위를 RRF 로 합친다. 후보 30개를 넘기고 나이 · 자격은 5단계가 본다.
- 후보는 신청 중, 상시, 신청 예정, 기간 모름. 마감(`closed`)과 신청기간이 지난 정책은 뺀다. `Hit.apply_state` 로 구분해 답변에서 표시한다.
- 사업 종료일이 지난 정책은 빼지 않고 `Hit.business_ended` 로 표시한다. 지금 상시 923건 중 6건뿐이지만 올해 안에 끝나는 상시가 310건이라, 빼면 데이터 갱신 전 1월 1일에 한꺼번에 사라진다. 상시 사업은 알아 두었다가 나중에 찾아볼 수도 있다. 답변에서 어떻게 보여 줄지는 6단계에서 정한다.
- 같은 기관의 재등록 정책(2024년 번호 + 2026-09-22 번호)은 검색에서 둘 다 둔다. 추천 3칸이 겹치지 않게 하는 처리는 6단계에서 한다.
- 지역 가산점은 넣지 않는다. `Hit.nationwide` 만 넣어 두고 3단계 측정 뒤 정한다.
- 키워드는 정확한 부분 문자열로 찾는다. 트라이그램은 "면접"과 "면허"도 0.33 으로 잡는다.
- 임베딩 실패는 `EmbedFailed` 로 올린다. `[]` 는 정상 결과(추천 없음)다.
- 모델 · 마이그레이션은 바꾸지 않았다. 사업 종료일은 `raw` 에서 읽는다.

## 임시 결정

- 임베딩 문장에 자격 조건 · 기관 · 지역을 넣지 않음. 결과가 나쁘면 `embed_text()` 를 고치고 다시 임베딩
- 정책 1건 = 벡터 1개 (가장 긴 문장 1,512자)
- 벡터 색인 없음. 지역을 거르면 0.05초 안팎, 2만 건을 넘으면 HNSW 추가
- 소득으로 탈락시키지 않음, 연소득 받지 않음
- '기타' 코드로 탈락시키지 않음
- 나이 제한 플래그 무시, 숫자만 사용. 원문의 "NN~NN세"와 어긋나면 모름
- 원본은 담당자 이름 칸만 빼고 저장
- 파일 적재는 기준일이 2026-10-29 라 API 승인 전까지 최신 아님 안내가 뜬다
- `regions.json` 은 법정동 5자리 표에서 일회용 스크립트로 만듦. 표가 바뀌면 다시 만든다
- RRF 상수 60, 후보 30개. 3단계 측정으로 다시 본다
- 이름 · 키워드 칸 일치는 본문 일치보다 키워드 순위만 높다. 차이가 작아서 벡터 순위 한 칸이면 뒤집힌다. 정답 문제에서 나쁘면 가중치를 준다
- 지역 코드가 200개를 넘으면 전국으로 표시. 실제로는 지역 기관 등록이 섞여 있다 (아래 2단계 결과)

## 2단계에서 확인된 것 (11-07 실측)

- **지역과 마감은 검색 전에 SQL 로 거른다.** 면접수당 벡터로 상위 30건을 뽑으면 동탄구 해당은 1건뿐이었다.
- **키워드가 벡터의 빈틈을 메운다.** "자격증 시험 비용"은 벡터 상위가 보증료 정책뿐이었는데 키워드 `응시료` 를 합치니 응시료 지원이 1위다. "면접 교통비"는 면접수당이 2위까지 오른다. 2단계는 키워드를 명령 인자로 직접 넣고, 추출은 4단계에서 한다.
- **거리만으로는 '맞는 정책 없음'을 못 가른다.** 맞는 정책이 없는 "우주 비행사"의 1위 거리(0.571)가 맞는 정책이 있는 "월세"(0.630)보다 가깝다. 질문마다 거리 범위가 다르다. 3단계 뒤 다른 기준이 필요하다. 키워드도 본문의 우연한 일치를 잡는다("우주" → 창업 사관학교).
- **전국 코드가 곧 전국 정책은 아니다.** 강남구 후보 275건 중 246건이 지역 코드 200개 초과인데, 그중 적어도 38건(약 15%)은 지자체 등록이다. "충청북도 취업박람회", "제4회 은평청년축제"가 다른 지역 결과에 나온다. 3단계에서 영향을 보고 등록 기관을 쓸지 정한다.
- 11-07 기준 후보 1,248건, 동탄구 269건, 강남구 275건, 세종 290건. 지역을 거른 뒤 같은 이름은 5~7종류이고 대부분 재등록이다.
- 검색 시간은 벡터 0.03초 안팎, 질문 임베딩 0.1~0.5초(첫 호출 1.6초).

## 정책 50건 실험에서 배운 것 (11-06)

- 구체적인 고민은 단어가 달라도 찾는다 ("시험 비용" → "응시료").
- 고민이 둘이면 한쪽으로 쏠린다. "면접 교통비랑 정장"은 상위 3개가 전부 정장이었다 → 필요별 검색.
- 막연한 질문은 오답이 많다. "돈 모으고 싶어"를 "청년 저축 자산 형성 통장 지원"으로 바꾸면 상위 4개가 모두 맞았다 → 질문 다듬기.
- 맞는 정책이 없어도 뭔가 내놓는다 → 낮은 점수 기준 필요. 기준은 정답 문제를 만든 뒤 정한다.
