# 청년 정책 추천 에이전트 메모

> 담당: 권세진 · 시작 2026-11-03 · 통합 검수 때 이 파일이 검수 목록이 된다 (에이전트 개발 당부 사항 3번)
> 다른 PC에서 이어서 작업할 때도 이 파일부터 읽는다.

통합 챗봇에서 사용자 조건과 고민을 받아 청년 정책 3개를 추천한다. RAG 구조다.

```
① 미리: 정책 정리 → 임베딩 → pgvector 저장 (sync_policies)
② 질문마다: 지역 · 마감 거르기 → 벡터 + 텍스트 검색 → 조건 검사 → 정렬 → 3개
③ 답변: LLM 은 해석과 추천 이유만. 정책명 · 기간 · 금액 · 링크는 DB 값
```

## 진행 상태

| 단계 | 할 일 | 상태 |
|---|---|---|
| 1 | 데이터 넣기 (정리, 적재, 임베딩) | **완료** |
| 2 | 검색 만들기 (`search.py`, 확인 명령 `policy_search`) | **완료** (11-10 결과 확인) |
| 3 | 정답 문제 만들기 (질문 20개 + 정답 정책) | **1차 채점 완료** (11-10, `policies/eval/`) |
| 4 | 자연어 잘 찾기 (질문 다듬기, 필요별 검색, 키워드 추출) | **1차 완료** (11-10, `reading.py`). 프롬프트 비교(여러 번 돌린 평균)는 남음 |
| 5 | 조건 거르기 (`eligibility.py`) | **1차 완료** (11-10) |
| 6 | 최소 고정 흐름 챗봇: 읽기 → 검색 → 자격 → 답변 + 되묻기 버튼 (`agent.py`, `PolicyProfile`) | **1차 완료** (11-10, 흐름 동작 확인). 추천 품질 개선 남음 |
| 7 | 챗봇 연결과 화면 확인 (`chat/engine.py`, `router_core`) | **최소 연결 완료** (11-10, 화면 확인). 복귀 · 취소 라우터 정리는 김나은과 |
| 8 | 에이전트 층으로 교체 (행동 고르기 · 돌아보기 · 다시 검색) + 고정 흐름과 비교 채점 | **8-1 행동 고르기 · 정책 상세 완료** (11-11, `planner.py`). **8-2 돌아보기(맞는 정책만 남기기) 완료** (11-11, `review.py`). 다시 검색, LLM 이유 문장, 비교 채점은 남음 |

단계마다 결과를 확인하고 다음 단계로 간다.

## 에이전트 방향 (11-10 결정)

- 1~4단계는 RAG 검색 파이프라인이다. 6단계는 코드가 순서를 정하는 고정 흐름 챗봇, 에이전트가 되는 곳은 8단계다.
- **만드는 순서: 고정 흐름 챗봇을 끝까지 만들어 화면에서 확인한 뒤 에이전트로 바꾼다.** 에이전트도 같은 도구(검색 · 자격 · 정책 상세 · 직전 추천)를 쓰고, 바뀌는 건 순서를 누가 정하느냐(코드 → LLM)뿐이다. 고정 흐름은 에이전트의 비교 기준이고, 에이전트의 LLM 호출이 실패하거나 상한에 걸리면 돌아갈 대체 경로다. 라우터 연결 · 버튼 · 상태 저장 문제는 에이전트와 상관없이 나오므로 먼저 푼다.
- **나중에 바꾸기 쉽게 6단계에서 지킬 것**
  1. 도구는 입력 · 출력이 분명한 함수로 나눈다 (`search_needs` · 자격 확인 · 정책 상세 · 직전 추천). 핸들러 안에 한 덩어리로 쓰지 않는다.
  2. "다음에 무엇을 할지" 정하는 코드는 한 함수에만 둔다. 8단계에서 그 함수만 LLM 행동 고르기 반복문으로 바꾼다.
  3. 답변에서 사실과 이유를 나눈다. 정책명 · 금액 · 링크 · 마감은 코드가 DB 값으로 채우고 LLM 은 이유 문장만 쓴다.
  4. 직전 추천 · 대화 중인 버튼 · 조건을 상태에 남긴다 ("그거 얼마 줘?" 같은 질문에 쓴다).
  5. 되묻기(분야 버튼)처럼 에이전트의 핵심 행동은 고정 흐름에서도 규칙으로 먼저 넣어 둔다. 8단계에서 LLM 판단으로 바꾸기만 한다.
- **일정 주의**: 고정 흐름을 오래 다듬으면 에이전트로 바꿀 시간이 모자라 "RAG 챗봇"으로 발표하게 된다. 6단계는 최소 고정 흐름으로 짧게 끝낸다.
- **원칙: 판단은 LLM, 사실은 코드.** 금액 · 마감 정렬 · 자격 판단 · 정책명 · 링크는 코드와 DB 가 하고 LLM 에게 넘기지 않는다 (팀 규칙: 금액 계산은 계산 엔진만, LLM 은 제안만).
- **8단계 에이전트 흐름**
  1. 읽기 — 4단계 `reading`
  2. LLM 이 다음 행동 고르기 — 되묻기 / 검색 / 자격 확인 / 정책 상세 / 직전 추천 / 끝내기
  3. 코드 도구 실행
  4. 돌아보기 — 결과가 안 맞으면 키워드를 바꿔 다시 검색 (최대 1~2번)
  5. 답변 — 이유만 LLM, 사실은 DB 값
- **안전장치**: 한 턴에 도구 호출 최대 4~5번, 정해 둔 도구만, 추천 번호는 도구 결과 안에서만 (코드로 검사).
- **구현**: LangGraph 없이 `langchain-core` + 최대 횟수가 있는 단순한 반복문.
- **에이전트 채점**: 같은 시험지로 고정 흐름과 비교한다. `eval/agent_questions.md` 질문마다 기대하는 첫 행동을 적고 비교한다. 지표는 첫 행동 정확도, 다시 검색으로 정답이 올라온 수, 지어낸 정책명 · 링크 0건, 평균 도구 호출 수.
- **규칙을 풀어 보는 실험**: '맞는 정책 없음' 판단 하나만 LLM 에게 맡겨 본다 (q26 · q27 로 채점).

## 팀원이 챗봇에서 확인하기 (정책 데이터 복원, 11-11)

정책 데이터는 저장소에 없다. 복원하지 않으면 정책 추천이 "찾지 못했어요"로만 나오고, 소비 분석 · 예산은 그대로 동작한다.
원본 JSON 대신 **권세진 PC 에서 적재 · 임베딩까지 끝낸 정책 표 덤프**(`policies_20261029.dump`, 약 28MB)를 팀 공유 드라이브로 받는다.
임베딩 비용이 없고 모두 같은 데이터가 되며, 원본의 담당자 이름 칸이 빠져 있다. 덤프는 `policy` · `policy_sync` 두 표의 데이터만이고, 회원 데이터(`saved_policy` · `policy_profile`)는 없다. 커밋하지 않는다.

1. main 받기 → `pip install -r requirements.txt` → `cd backend` → `python manage.py migrate`
2. 받은 덤프를 로컬 DB 컨테이너에 복원 (Git Bash, 저장소 루트에서. 사용자 · DB 이름은 `.env` 의 `POSTGRES_USER` · `POSTGRES_DB`):

```bash
docker exec -i money-cushion-db pg_restore -U money_cushion -d money_cushion --data-only --no-owner < policies_20261029.dump
```

   이미 정책이 들어 있으면 키가 겹친다는 오류가 난다. 그때는 저장한 정책이 없는지 확인하고 비운 뒤 다시 복원한다:
   `docker exec -i money-cushion-db psql -U money_cushion -d money_cushion -c "TRUNCATE policy, policy_sync;"`
   (저장한 정책이 있으면 `saved_policy` 가 막는다 — 그 PC 는 복원하지 않아도 된다)
3. 확인: `docker exec -i money-cushion-db psql -U money_cushion -d money_cushion -tAc "select count(*), count(embedding) from policy;"` → `3664|3664`
4. 서버를 환경변수 `CHAT_ENGINE=router` · `CHAT_LLM=live` 로 켠다 (`.env` 의 `OPENAI_API_KEY` · `LLM_MODEL` · `EMBEDDING_MODEL` 필요). `CHAT_LLM=fake` 면 LLM 판단(행동 고르기 · 돌아보기) 없이 규칙으로만 동작하고, 질문 임베딩이 가짜라 검색 결과가 엉뚱하다
5. 챗봇에서: [청년 정책을 추천받고 싶어요] → 서울특별시 → 관악구 → 아래 문장들
   - "자격증 시험비가 너무 비싸" → 응시료 지원 1개
   - "그거 신청 링크 알려줘" → 같은 정책의 신청 방법 · 링크
   - "면접 볼 때 정장 빌릴 수 있어?" → 취업날개
   - [1번 저장] → [저장한 정책 보기]
   - "전국청년 무조건생활지원금 신청하고 싶어" → 찾지 못했어요 (지어내지 않음)
   - "이번 달 얼마 썼어?" → 소비 분석으로 넘어감
   - 회원 생년월일이 없으면 "내 정보에서 생년월일을 입력"으로 끝난다 (나이 조건 때문)

덤프를 다시 만들 때 (적재한 PC 에서, 정리 규칙이 바뀌면 먼저 `policy_renormalize --save`):
`docker exec money-cushion-db pg_dump -U money_cushion -d money_cushion --data-only --no-owner -t public.policy -t public.policy_sync -Fc > policies_20261029.dump`

## 다른 PC에서 이어서 하기

1. 코드 받기: PR 97 병합 뒤에는 main 에서 새 브랜치. 병합 전이면 `git fetch origin` 후 `git switch feat/policy-agent`
2. `pip install -r requirements.txt` (11-11부터 `langchain-core` 포함)
3. `.env` 준비: `OPENAI_API_KEY`, `EMBEDDING_MODEL` 포함 (`docs/ENV_SETUP.md`)
4. DB 는 pgvector 가 있어야 한다 (`pgvector/pgvector:pg17`, `docs/ENV_SETUP.md` 3번)
5. `cd backend` 후 `python manage.py migrate`
6. 정책 데이터: 위 "팀원이 챗봇에서 확인하기"의 덤프 복원이 가장 빠르다. 원본에서 적재하려면 정책 파일 `youth_policies_20261029.json` 을 저장소 밖에 둔다 (팀 공유 파일, 커밋하지 않는다). 법정동코드 · API 코드정보 엑셀은 받지 않아도 된다
7. 원본 적재 + 임베딩 (약 40초, OpenAI 임베딩 약 100만 토큰):

```bash
python manage.py sync_policies --file <파일 경로> --data-date 2026-10-29 --live-embed
```

8. 확인: `받음 3664`, `임베딩 완료 3664 · 남음 0`, 테스트는 `python manage.py test policies`
9. **이미 정책을 적재해 둔 PC** 는 코드를 받은 뒤 `python manage.py policy_renormalize --save` 를 한 번 돌린다. 정리 규칙이 바뀌어도 원본이 그대로면 `sync_policies` 가 다시 정리하지 않는다 (11-10 나이 규칙 변경)

코드표와 지역 표는 저장소에 있다(`policies/codes.py`, `policies/data/regions.json`). 원본 엑셀은 다시 필요 없다.

## 쓰는 API·함수

| 무엇 | 어디 | 용도 |
|---|---|---|
| `sync_policies` | `policies/management/commands/` | 파일 적재 + 바뀐 정책 임베딩 |
| `load()` · `embed_changed()` | `policies/sync.py` | 검증 뒤 한 트랜잭션 공개, 임베딩은 트랜잭션 밖 |
| `policy_fields()` · `embed_text()` | `policies/normalize.py` | 원본 → 칸 정리, 임베딩 문장 |
| `embedder()` | `policies/llm.py` | 가짜/실제 임베딩 (`CHAT_LLM`, `--live-embed`) |
| `REGIONS` · `KNOWN_CODES` | `policies/regions.py` | 지역별 `match` 코드 목록 |
| `search()` · `candidates()` | `policies/search.py` | 지역 · 마감 거르기, 벡터 + 키워드 순위 합치기 → `Hit` 목록 |
| `policy_search` | `policies/management/commands/` | 검색 결과 확인 (`--region`, `--keyword`, `--date`, `--limit`, `--live-embed`) |
| `policy_find` | `policies/management/commands/` | 정답 후보 찾기. 검색 순위와 상관없이 단어가 들어간 지역 후보 전체 (`--detail`) |
| `policy_eval` · `load()` · `run()` · `summary()` | 명령 · `policies/evaluate.py` | 정답 문제 채점 (`--check`, `--only`). 질문 파일 `policies/eval/questions.json`, 쓰는 법 `policies/eval/README.md` |
| `find_region()` | `policies/regions.py` | 지역 이름 일부 · 코드 → 코드 (두 확인 명령 · 평가 파일) |
| `read()` · `parse()` · `reader()` · `needs_for()` | `policies/reading.py` | 4단계 질문 읽기: 문장 → 필요(검색 문장 + 키워드) 목록 · 지명 · 막연한지. LLM 1회, `complete(system, user)` 주입 |
| `search_needs()` | `policies/search.py` | 필요마다 검색해 순위를 RRF 로 합친다 (필요 하나면 `search()` 와 같다) |
| `place_regions()` | `policies/regions.py` | 문장 속 지명 → 해당할 수 있는 지역 코드 목록 ("광주" → 전남광주통합특별시, "중구" → 5곳) |
| `policy_search --read` · `policy_eval --auto` | 확인 명령 | 질문 읽기로 검색 · 채점 (실제 LLM) |
| `policy_renormalize` · `renormalize()` | 명령 · `policies/sync.py` | 정리 규칙을 고친 뒤 저장된 원본으로 정리 칸을 다시 만든다 (기본 미리보기, `--save`). 활성 여부 · 임베딩은 그대로 |
| `handle()` · `decide()` | `policies/agent.py` | 6단계 핸들러 (라우터 계약 `handler(request) → dict`). 다음 행동은 `decide()` 한 곳에서만 정한다 |
| `profile_for()` · `find()` · `again()` · `facts()` | `policies/tools.py` | 6 · 8단계 공용 도구: 사용자 조건, 검색 → 자격 → 재등록 겹침 빼기, 더 보기, 답변 한 칸의 사실(DB 값) |
| `policy_chat` | 확인 명령 | 입력을 차례로 보내 대화 확인 (`[버튼]` = 기능 버튼, 버튼은 이름 그대로, 실제 LLM · 임베딩) |
| `save()` · `save_all()` · `unsave()` · `items()` | `policies/saved.py` | 저장한 정책(북마크). 저장 API 와 채팅(엔진)이 같이 쓴다 |
| `GET /api/policies/saved/` · `PUT · DELETE /api/policies/<정책번호>/saved/` | `policies/api.py` | 저장 목록 · 저장 · 취소 (명세 `docs/api/policies.md`) |
| `remembered_region()` · `remember()` | `policies/profiles.py` | 회원별 사는 지역 저장(`policy_profile`). 핸들러는 읽기만, 쓰기는 엔진(`save_profile`) |
| `chain()` | `policies/llm.py` | LangChain 체인 `프롬프트 | LLM | 출력 파서`. 질문 읽기(`StrOutputParser`) · 행동 고르기(`PydanticOutputParser` + 답 모양 `planner.Plan`)가 쓴다 |
| `keep()` · `reviewer()` | `policies/review.py` | 8단계 돌아보기: 검색 · 자격 뒤 앞 10개를 LLM 이 다시 보고 질문과 맞는 것만 남긴다(순서 그대로, 0~10개). 실패하면 거르지 않음 |
| `responses()` | `policies/llm.py` | 체인의 LLM 자리에 넣을 호출기(`ResponsesClient.complete`) 만들기. 가짜 모드 · 키 없음이면 `None` |
| `ask()` · `chooser()` | `policies/planner.py` | 8단계 행동 고르기: 읽은 문장 + 직전 추천 + 방금 본 정책 → 검색 · 되묻기 · 정책 상세 · 다른 담당 · 끝내기 중 하나. LLM 1회, 실패하면 `None` → 규칙 |
| `detail()` | `policies/tools.py` | 8단계 정책 상세: 지원 내용 · 신청 방법 · 제출 서류 · 기간 · 자격 · 그 밖 중 고른 항목을 DB 원문으로 (300자). 원문에 없으면 `None` |
| `tidy()` | `policies/tools.py` | 지원 내용 원문 앞부분 정리 (글머리 기호 → ' · ', 80자에서 낱말 단위로 자르기) |
| `Profile` · `judge()` · `keep()` | `policies/eligibility.py` | 5단계 자격: 정책 하나 → `Verdict`(충족 · 확인 필요 · 불충족 + 조건별 이유, 곧 나이 초과 표시), 검색 결과에서 불충족 빼기 |
| `FinancialProfile` 읽기만 | `users/models.py` | `birth_date`, `gender`, `monthly_take_home_income` |
| `handler(request) → dict` (7단계) | `chat/engine.py` `agents["policy"]` | 라우터 계약: `docs/policy-agent-router-handoff.md` |
| `complete(system, user)` (6단계) | `chat/llm` | 라우터와 같은 LLM 호출기. `ChatOpenAI` 를 따로 만들지 않는다 |

## 정해진 것

**대상과 범위**
- 추천 대상은 정책 전 분야. 대출 · 대출보증 정책도 포함한다(기획서의 '상환 의무 제외'에서 변경).
- 정책 납입액 · 예산 비교(POL-004)는 후속 개발.
- LangChain 은 `langchain-core` 만 쓴다. LangGraph · `langchain-openai` · `langchain-postgres` 는 쓰지 않는다.

**조건 입력 (별도 화면 없이 채팅 버튼)**
- 온보딩 값은 다시 묻지 않는다. 나이 = 생년월일, 여성 조건 = 성별. 생년월일이 없으면 내 정보로 안내하고 끝낸다.
- 묻는 것: 지역(시도 16개 → 시군구 → 구가 있는 시 13곳은 구, 세종은 시도에서 끝), 특화 대상(여러 개, [다 골랐어요] [해당 없음] [건너뛰기]).
- 취업 상태: 월급 정보가 있으면 묻지 않고 재직자로 본다. "취업 준비 중"처럼 말하면 그 말을 따른다. [조건 바꾸기]에서는 묻는다.
- 묻지 않는 것: 학력, 전공, 혼인, 주거 형태, 연소득. 해당 요건 정책은 '확인 필요'로 표시한다.
- 끝에 "다음에도 이 조건으로 추천할까요?" 를 묻고 동의한 경우만 회원별로 저장한다.
- 저장은 핸들러가 하지 않는다. `reply.save_profile` 을 돌려주면 엔진이 대화 저장과 같은 트랜잭션에서 한다(409 면 저장도 안 됨).

**자격 판단 (코드가 함, 위에서부터 처음 맞는 줄)**
1. 정책이 제한없음 → 충족
2. 정책 칸이 비었거나 사용자 값을 모름 → 확인 필요
3. 사용자 코드가 정책 코드에 있음 → 충족
4. 정책 코드에 '기타'가 있음 → 확인 필요
5. 그 밖 → 불충족 (추천에서 뺌)

- 지역은 코드를 그대로 비교하지 않고 `match` 목록으로 비교한다. 화성시 코드로만 적힌 정책 345건, 천안시 99건이 있다.
- 소득은 탈락 근거로 쓰지 않는다. 금액 단위와 본인/가구 구분을 알 수 없다.

**대화 규칙**
- 버튼은 이름이 문장으로 들어온다. 답할 때 {이름: 동작}을 상태에 저장해 두고 같은 이름이면 그 동작을 실행한다. 정책번호는 서버 상태에서만 나온다.
- 추천 뒤 담당 유지(`replied`). "취소 · 그만 · 됐어"는 `ended`, 정책 상태는 핸들러가 지운다.
- 다른 담당을 다녀오면 [이어서 하기] [새로 추천]. 소비 · 예산 질문은 상태를 바꾸기 전에 `not_mine`.
- 핸들러는 DB 에 쓰지 않는다. 검색 오류는 추천 없음으로 바꾸지 않고 `failed`.
- 모든 추천에 "자격 확정이 아니에요. 공고 원문으로 확인해 주세요."를 붙이고 "신청 가능"이라고 쓰지 않는다.
- 찾을 지역 (11-11 멘토 요청으로 변경): **문장 속 지역 > 사는 곳 > 지역 버튼**. 문장을 먼저 읽고, 지명이 시군구 하나로 정해지면 묻지 않고 그 지역으로 찾는다. "서울"처럼 넓으면 그 안의 시군구만, "중구"처럼 여러 곳이면 후보만 버튼으로 묻는다(읽은 결과를 남겨 다시 읽지 않음). 문장 속 지역은 이번 검색에만 쓰고 사는 곳으로 기억하지 않는다(사용자 결정). 사는 곳과 달라도 확인 버튼(예전 `ask_place`)은 없다. 사는 곳을 품는 지명("서울" · 사는 곳 관악구)은 사는 곳으로. 지명이 없으면 사는 곳, 그것도 모르면 지역 버튼

**검색 (2단계, 11-07)**
- 지역 · 마감을 SQL 로 거른 뒤 벡터 순위와 키워드별 순위를 RRF 로 합친다. 후보 30개를 넘기고 나이 · 자격은 5단계가 본다.
- 후보는 신청 중, 상시, 신청 예정, 기간 모름. 마감(`closed`)과 신청기간이 지난 정책은 뺀다. `Hit.apply_state` 로 구분해 답변에서 표시한다.
- 사업 종료일이 지난 정책은 빼지 않고 `Hit.business_ended` 로 표시한다. 지금 상시 923건 중 6건뿐이지만 올해 안에 끝나는 상시가 310건이라, 빼면 데이터 갱신 전 1월 1일에 한꺼번에 사라진다. 상시 사업은 알아 두었다가 나중에 찾아볼 수도 있다. 답변에서 어떻게 보여 줄지는 6단계에서 정한다.
- 같은 기관의 재등록 정책(2024년 번호 + 2026-09-22 번호)은 검색에서 둘 다 둔다. 추천 3칸이 겹치지 않게 하는 처리는 6단계에서 한다.
- 지역 가산점은 넣지 않는다. `Hit.nationwide` 만 넣어 두고 3단계 측정 뒤 정한다.
- 키워드는 정확한 부분 문자열로 찾는다. 트라이그램은 "면접"과 "면허"도 0.33 으로 잡는다.
- 임베딩 실패는 `EmbedFailed` 로 올린다. `[]` 는 정상 결과(추천 없음)다.
- 모델 · 마이그레이션은 바꾸지 않았다. 사업 종료일은 `raw` 에서 읽는다.

**정답 문제 (3단계, 11-10)**
- 질문 20개는 권세진이 직접 쓴다. 종류: 구체 · 막연 · 두고민 · 없음(맞는 정책 없음) · 지역 · 이사(1~2개).
- 권세진이 쓴 질문 40개 중 검색 순위로 채점할 수 있는 20개를 `questions.json` 에, 자격 판단 · 대화 맥락 · 지어내기 거절을 보는 20개를 `agent_questions.md` 에 두었다 (5단계 이후 답변 평가용).
- 질문 문장에는 나이 · 소득 · 지역이 들어 있어도 된다. `region` 은 최종으로 검색할 시군구이고, 문장에 시도만 있거나 지역이 없으면 버튼으로 고른 곳을 가정해 `note` 에 적는다. `이사` 는 사는 곳과 검색 지역이 다르다.
- 광주는 지역 표에서 `전남광주통합특별시`(코드 12)다. 4단계 문장 속 지역 읽기에서 "광주" → 이 지역으로 이어야 한다.
- 질문마다 사람이 뽑은 키워드도 적고 `벡터만` · `키워드` 두 번 채점한다. 4단계 자동 추출은 `키워드` 점수와 비교한다.
- 정답은 묶음 목록. 재등록 번호(같은 이름)는 한 묶음이고 하나만 나와도 찾은 것으로 본다.
- 정답은 검색 결과가 아니라 `policy_find` 로 고른다. 검색 결과에서만 고르면 검색이 놓친 정책은 정답이 될 수 없어 점수가 부풀려진다.
- 기준일은 파일에 고정(2026-11-10). 정답 번호가 그 지역 · 기준일 후보에 없으면 채점 전에 멈춘다.
- 지표: Hit@3(추천 3개라 가장 중요) · Hit@10 · 30위 안 · MRR · 묶음(두고민에서 둘 다 찾는지). 정답 없는 질문은 1위 거리만 따로 본다.
- 채점은 항상 실제 임베딩(`EMBEDDING_MODEL`)을 부른다. 가짜 임베딩으로는 저장된 실제 벡터와 비교할 수 없다.
- 정답 기준: "질문한 사람이 이걸 보면 '내가 찾던 거다'라고 할까?" 자격은 5단계가 거른다. 다른 지역 사업이 전국 코드로 들어온 것(담당 기관으로 판단), 질문한 사람이 될 수 없는 대상 전용(장병 · 전세사기 피해자 · 자립준비청년 · 예술인 등), 운영 · 연구 · 통계 사업은 뺀다.
- 이름만 다른 같은 제도(심리상담 바우처 2건, 청년 미래이음 대출 2건)도 한 묶음. `두고민` 은 주제마다 한 묶음(생활비 정책 전부 / 주거비 정책 전부)이라 `묶음` 점수가 "두 고민을 다 찾았나"가 된다.

## 임시 결정

- 임베딩 문장에 자격 조건 · 기관 · 지역을 넣지 않음. 결과가 나쁘면 `embed_text()` 를 고치고 다시 임베딩
- 정책 1건 = 벡터 1개 (가장 긴 문장 1,512자)
- 벡터 색인 없음. 지역을 거르면 0.05초 안팎, 2만 건을 넘으면 HNSW 추가
- 소득으로 탈락시키지 않음, 연소득 받지 않음
- '기타' 코드로 탈락시키지 않음
- 나이 제한 플래그 무시, 숫자만 사용. 추가 자격 원문의 "NN~NN세"(·"NN세~NN세")와 어긋나면 둘을 모두 감싸는 가장 넓은 범위 (11-10 변경, 전에는 모름). 자녀 나이 범위(상한 15세 미만)는 보지 않는다
- 원본은 담당자 이름 칸만 빼고 저장
- 파일 적재는 기준일이 2026-10-29 라 API 승인 전까지 최신 아님 안내가 뜬다
- `regions.json` 은 법정동 5자리 표에서 일회용 스크립트로 만듦. 표가 바뀌면 다시 만든다
- RRF 상수 60, 후보 30개. 3단계 측정으로 다시 본다
- 이름 · 키워드 칸 일치는 본문 일치보다 키워드 순위만 높다. 차이가 작아서 벡터 순위 한 칸이면 뒤집힌다. 정답 문제에서 나쁘면 가중치를 준다
- 지역 코드가 200개를 넘으면 전국으로 표시. 실제로는 지역 기관 등록이 섞여 있다 (아래 2단계 결과)
- LLM 호출은 LangChain 체인(`llm.chain()`: `ChatPromptTemplate | LLM | 출력 파서`)으로 한다. LLM 자리는 라우터와 같은 `ResponsesClient.complete` 를 `RunnableLambda` 로 감싼다(JSON 모양 강제 · 호출 상한 · 서비스 중단 처리를 그대로 쓰려고). `ChatOpenAI`(langchain-openai)는 쓰지 않는다. 버전 `langchain-core==1.7.0` (11-11)
- 행동 고르기는 직접 쓴 문장에만. 버튼 · 취소 · 지역 고르기 · 저장 목록 문장은 규칙 그대로 (LLM 비용 없음)
- 문장 하나에 LLM 2회 (읽기 + 행동 고르기). 합치면 1회지만 4단계 채점(`policy_eval --auto`)이 읽기 프롬프트를 그대로 쓰므로 나눠 둔다
- 가짜 모드(`CHAT_LLM=fake`)는 행동 고르기 없이 6단계 규칙. 정책 상세는 실제 모드에서만 나온다
- "그거"처럼 가리키기만 하면 방금 상세를 본 정책. LLM 이 번호를 못 정해도 코드가 방금 본 정책을 쓴다. 새로 검색하면 잊는다
- 돌아보기는 검색 결과 앞 10개만 본다(10위 안에 정답 94%). 3개를 억지로 채우지 않는다. 맞는 게 없으면 "찾지 못했어요"
- 돌아보기 기본은 남기기다. 확실히 다른 지원 · 특정 대상 전용(문장에 그 대상이 없을 때) · 이름에 다른 지역이 분명한 것만 뺀다. 처음에 '직접 주는 것만 고르기'로 했더니 정답(저축 → 청약통장)까지 빼서 3위 안 정답이 12 → 9개로 줄었다
- 특정 대상 전용을 문장 기준으로 빼므로, 말하지 않은 신혼부부 · 군인 등은 대상이어도 빠질 수 있다 (조건을 묻지 않기로 한 결정과 맞물림)
- LLM 답 토큰 한도는 행동 고르기 · 돌아보기 모두 1000 (300 은 가끔 답이 잘려 거르지 못했다)
- 직전 추천 묶음은 따로 두지 않는다. 정책 상세가 직전 추천 번호(더 보기 포함)로 정책을 찾는다

## 4단계 질문 읽기 (11-10 1차)

**정한 것**
- LLM 은 한 번만 부른다. 문장 → `needs`(찾는 지원마다 검색 문장 + 키워드 1~4개, 최대 3개) · `place`(지명 그대로) · `vague`. Structured Outputs 스키마 `policy_reading`, 호출기는 라우터와 같은 `ResponsesClient`.
- LLM 은 읽기만 한다. 지명 → 지역 코드는 코드(`place_regions`)가, 사는 곳과 다를 때 확인 버튼은 6단계가 한다. 검색 지역은 계속 버튼으로 고른 곳이다.

## 8-1 행동 고르기 · 정책 상세 (11-11)

- 흐름: 문장 → 읽기(LLM) → **행동 고르기(LLM)** → 코드 도구 → 답. 버튼 · 취소 · 지역은 `decide()` 규칙 그대로이고, `decide()` 가 LLM 이 고른 행동(`choice`)을 받아 `Action` 으로 바꾼다. 실패 · 모양 틀림이면 6단계 규칙.
- 안전장치: 행동은 5개(`search` · `ask_field` · `detail` · `not_mine` · `end`)만. Pydantic 모델 `Plan` 하나로 OpenAI 에 보낼 JSON 스키마도 만들고 받은 답도 검사한다(`PydanticOutputParser`, strict). 번호는 지금까지 보여 준 추천 안에서만, 밖이면 버린다. 정책 상세의 값은 모두 DB 원문이고 비어 있으면 "공고 원문에 없어요. ○○에 확인해 주세요".
- 어느 정책인지 모르면 방금 보인 추천을 버튼으로 묻는다. 추천이 하나도 없으면 분야 버튼. 상세를 본 뒤에도 [N번 저장] 등 추천 버튼은 그대로.
- 실제 LLM 확인(`policy_chat`, 관악구 · "월세 지원 있어?" 뒤): "2번 신청 링크랑 서류 알려줘" → 2번 신청 방법 · 서류(원문에 없음 → 금융위원회 확인 안내), "그거 얼마 줘?" → 같은 정책 지원 내용, "일해도 받을 수 있어?" → 같은 정책 자격 전체(취업 상태 제한없음), "아까 1번은 언제까지 신청해?" → 1번 신청 기간, "다른 거랑 같이 받아도 돼?" → 그 밖(원문에 없음 → 기관 확인), "청년인데 받을 수 있는 돈 없어?" → 분야 버튼, "이번 달 식비 얼마 썼어?" → `not_mine`.
- 남은 것: 돌아보기 · 다시 검색(결과가 안 맞으면 키워드 바꿔 1~2번), 추천 이유 LLM 문장, `agent_questions.md` 에 기대 첫 행동을 적고 고정 흐름과 비교 채점.

## 화면 테스트 뒤 고친 것 (11-10)

권세진이 노트북에서 최신 main + 청년 정책으로 써 보고 낸 의견 세 가지.

1. **추천이 읽기 어렵다** → 정책마다 굵은 제목 + 점 목록(`reply.sections`)으로 보낸다. 엔진이 정책 답변에 sections 가 있으면 `result=True` 로 표시해 채팅 화면의 결과 카드(소비 분석과 같은 틀, 화면 코드 수정 없음)로 그린다. 채팅 화면은 마크다운을 그리지 않는다.
   - 카드 한 칸: 신청(상태 · 기간) · 지원(원문 앞 80자, 글머리 기호 'ㅁ · □ · ㅇ · ○ · ※ · ① · -' 는 ' · ' 로) · 확인할 것 · 곧 나이 초과 · 관련(찾은 키워드) · 링크.
2. **저장한 정책을 어디서 보나** → 채팅의 [저장한 정책 보기] 버튼과 "저장한 정책 보여 줘" · "저장 목록" · "북마크" 문장. 저장 목록도 카드로 (신청 상태 · 마감일 · 저장일 · 링크, 수집에서 빠진 정책 표시). 회원만. 마이페이지 화면은 나중에 정한다.
3. **나갔다 오면 지역을 다시 골라야 한다** → 추천 아래 [다음에도 ○○구로 찾기] 버튼. 누르면 결과의 `save_profile` 을 엔진이 `policy_profile` 에 저장하고, 다음 대화부터 지역을 묻지 않는다 ("저장해 둔 지역(○○구) 기준으로 찾아요." 안내, [지역 바꾸기]로 바꿈). 누르지 않으면 저장하지 않는다. 다른 지역을 '이번만' 볼 때는 버튼을 보이지 않는다.
   - 지역 저장이 기존 동의 목적 안인지(POL-001)는 아직 열린 질문이다 (아래 '필요한 것').

## 7단계 최소 연결 (11-10)

- `chat/engine.py` (김나은 코드, 미리 알림 필요): `agents["policy"] = partial(policy_agent.handle, store=store, user=user)` 로 '준비 중' 대역을 바꿨다. `NOT_READY` 에서 정책 문구를 뺐다.
- 채팅 저장: 정책 결과가 `replied` 이고 `save_policies` 가 있으면 `respond()` 가 대화 저장 트랜잭션 안(상태 rev 확인 뒤)에서 `policies.saved.save_all` 로 저장한다. 409 `conversation_busy` 면 저장하지 않는다. `save_policies` 는 화면 content 에 넣지 않는다.
- 읽기 LLM · 임베딩은 `policies` 쪽 `reader()` · `embedder()` 가 `CHAT_LLM` 을 따른다 (라우터 LLM 의 상한 · 장부와는 아직 따로).
- 가짜 읽기(`CHAT_LLM=fake`)도 "썼 · 지출 · 소비 · 예산 · 얼마 남" 말투는 `mine=false` 로 본다. 가짜 해석으로 띄운 서비스에서 정책 담당에 갇히지 않게.
- 라우터 내부(`router_core`)는 처음에 바꾸지 않았다. 11-11 PR 97 리뷰로 복귀만 고쳤다: 보류된 정책 작업이 있으면 `resume` 으로 이어서 (`_policy_entry`). 취소 처리 정리는 김나은과 맞춘 뒤 한다.
- 테스트: `chat.test_engine` (fixture 설정) 31개 — 정책 버튼 → 지역 질문, 지역 버튼 → 문장 → 추천 → [1번 저장] DB 저장 → 소비 질문은 소비 담당으로, 409 면 저장 안 됨. `chat` 기본 설정 141개 중 실패 1개(`test_portability` 의 Windows `msvcrt`)는 변경 전에도 같다.
- **화면 확인** (11-10): 메인 서비스를 `CHAT_ENGINE=router` · `CHAT_LLM=live` 환경변수로 띄우면 새 엔진이 켜진다 (`.env` · 설정 수정 없음, 환경변수가 `.env` 보다 앞선다). 로컬 확인용 계정 `policy-check@money-cushion.test`(만 27세 · 월급 있음, 로컬 DB 에만)로 채팅 → [청년 정책을 추천받고 싶어요] → 서울특별시 → 관악구 → "월세 지원 있어?" → 추천 3개(1위 2026 청년 월세 지원) → [1번 저장] → `saved_policy` 행 · `GET /api/policies/saved/` 확인.
- 화면 확인에서 찾아 고친 것: 저장 목록 `savedAt` 이 UTC(`Z`)로 나가던 것을 한국 시간(`+09:00`)으로.
- 화면에서 추천 칸이 긴 글(지원 내용 · 확인할 것 · 링크)로 나와 읽기 어렵다 → 정책 카드 화면(2차, `reply.policy_result`) 검토.

## 정책 저장 (북마크, 11-10)

- 추천받은 정책을 저장해 두고 나중에 마이페이지에서 본다. **마이페이지 표시 방식은 아직 정하지 않았다** (저장 목록 API 만 있다).
- 새 표 `saved_policy` (`policies/0002_saved_policy`): 회원 FK CASCADE(탈퇴하면 함께 삭제) · 정책 FK PROTECT · (회원, 정책) UNIQUE. 이유는 `docs/DB_MODELS.md`. 팀 규칙상 마이그레이션은 DB 담당이 만들지만, 이번에는 권세진이 만들고 김나은에게 따로 전달한다 (권세진 결정).
- API (`docs/api/policies.md`): 주소 속 ID 는 정책번호(UUID 아님, `policy` 표의 예외). 저장 `PUT` 은 이미 저장돼 있어도 200, 취소 `DELETE` 는 저장돼 있지 않아도 204 → 요청 번호 없이도 두 번 눌러 생기는 문제가 없다. 없는 · 비활성 정책 저장은 404.
- 저장 목록은 지금 정책 값을 읽는다 (저장 당시 복사본 없음). 마감 · 수집 종료도 지우지 않고 `applyState` · `active` 로 보여 준다.
- 채팅: 추천 뒤 버튼에 [N번 저장] (번호는 화면 번호, 더 보기면 4 · 5번 …). 버튼 값은 `save:정책번호` 로 서버 상태에만 있다. 누르면 핸들러는 **DB 에 쓰지 않고** 결과에 `save_policies: [정책번호]` 를 넣고 "‘…’ 정책을 저장했어요."로 답한다. 실제 저장은 엔진이 대화 저장과 같은 트랜잭션에서 `saved.save_all` 로 한다 (7단계 최소 연결에서 연결함).
- 같은 대화에서 저장한 정책은 상태 `saved` 에 남겨 다시 찾아도 저장 버튼을 빼고 보인다. `saved` 칸이 없는 예전 상태도 읽는다.

## 6단계 최소 고정 흐름 (11-10 1차)

**정한 것**
- 흐름: 생년월일 확인 → 사는 지역 버튼(시도 → 시군구 → 구) → 문장 읽기(LLM 1회) → 다른 지역이면 확인 버튼 → 막연하면 분야 버튼 → 검색 · 자격 → 추천 3개 + [다른 정책 더 보기] [다른 분야 찾기] [지역 바꾸기].
- 다음 행동은 `decide(state, text, read)` 한 곳에서 코드 규칙으로 정한다. 부작용이 없고, `handle()` 의 반복문(최대 4번)이 고른 행동을 실행한다. 8단계는 `decide()` 만 LLM 으로 바꾼다.
- 도구는 `tools.py` (사용자 조건 · 찾기 · 더 보기 · 사실). 사실(정책명 · 기간 · 지원 내용 · 확인할 것 · 링크)은 DB 값 · 코드 계산이고, 1차 추천 이유는 찾은 키워드("찾은 말: 월세")로 코드가 쓴다. LLM 이유 문장은 다음 단계.
- 지원 내용은 DB 문장 앞 90자를 자르기만 한다. 링크는 신청 주소 → 참고 주소 순, 없으면 "정보 없음"(지어내지 않는다).
- 같은 이름 정책(재등록)은 앞의 것 하나만 추천한다. 검색 순서는 그대로 두고 자격 불충족만 뺀다.
- 버튼은 질문할 때 {이름: 값}을 상태에 남기고, 버튼 대신 지명을 쓰면("화성 동탄") `place_regions` 로 고른다. 엉뚱한 답이면 버튼을 다시 보인다.
- 다른 지역 확인에서 "그 지역 기준"을 고르면 그 지역은 이번 검색에만 쓰고 사는 곳은 그대로 둔다. 이미 읽은 필요를 상태에 남겨 다시 읽지 않는다.
- `not_mine`: 4단계 읽기에 `mine` 칸을 더했다 (지출 · 예산 질문이면 false, "카드값이 밀렸어" 같은 고민은 true). not_mine · failed 는 상태를 바꾸지 않는다.
- 추천 없음은 `replied` + 다른 분야 · 지역 버튼. 그만 · 취소 · `cancel` 모드는 `ended` 로 끝내고 정책 상태를 지운다.
- 취업 상태: "취업 준비 · 취준 · 구직 중 · 무직 …" 이 문장에 있으면 미취업자, 아니면 월급 정보가 있으면 재직자. 특화 대상은 아직 묻지 않는다(모름 → 확인 필요).
- 1차에서 미룬 것: `PolicyProfile` 저장("다음에도 이 조건으로?"), 특화 대상 버튼, 직전 추천 후속 질문("그거 얼마 줘?" — 상태 `last` 에 번호만 남겨 둠), LLM 이유 문장.

**확인한 것** (`policy_chat`, 관악구 · 만 27세, 실제 LLM · 임베딩)
- 지역 버튼 → 분야 버튼 → 문장 → 더 보기 → 다른 지역 확인(부산 → 부산진구) → `not_mine`("배달비 얼마 썼어?") → 막연 → 분야 버튼 → 그만까지 끝까지 흐른다.
- 한 턴 약 3초: 읽기 LLM 2.2~2.7초 + 검색 · 자격 0.6~0.7초. 8단계에서 LLM 호출을 더하면 한 번에 2~3초씩 늘어난다.
- **추천 품질 문제** (다음 손볼 것)
  1. 대상이 맞지 않는 정책이 위에 온다: "취업 준비 생활비" 1위가 청년장병 취·창업 지원, 부산 월세 1위가 전세피해 임차인 전용. 특화 대상을 묻지 않아 군인 전용도 '확인 필요'로 남는다 → 특화 대상 버튼(메모의 조건 입력에 이미 있음).
  2. 다른 지역 사업이 전국 코드로 섞인다: 관악구 결과에 "청년단기주거공간 운영(금강장)" · "청춘어람 운영" (다른 군 사업) → 등록 기관으로 거를지 정해야 한다 (2 · 3단계에서 본 문제).
  3. 운영 · 연구 사업이 추천된다: "청년자산형성 5종 연계 강화"(연구용역)가 저축 1위.
  4. 지원 내용이 원문 기호("ㅇ", "□", "①") 그대로라 읽기 어렵다.

## 5단계 자격 거르기 (11-10 1차)

**정한 것**
- 메모의 규칙 다섯 줄을 조건마다 적용하고, 정책 결과는 가장 나쁜 조건을 따른다 (불충족 > 확인 필요 > 충족). LLM 은 쓰지 않는다.
- 보는 조건: 나이 · 취업 상태 · 특화 대상 · 학력 · 전공 · 혼인 · 소득. 지역은 검색이 이미 `match` 로 걸러 다시 보지 않는다.
- `Profile` 은 생년월일 · 성별(`male` · `female`, 온보딩 값 그대로) · 취업 상태 코드 · 특화 대상 코드. 특화 대상 `None` = 모름(건너뛰기), 빈 집합 = 해당 없음. 무엇을 넣을지는 6단계가 정한다 (월급 정보 → 재직자 등).
- 성별은 특화 대상 '여성'으로 쓴다. 특화 대상을 건너뛰었어도 정책이 '여성'만 요구하면 성별로 판단한다.
- 나이 상한까지 90일 안이면 `soon_over` 로 표시한다 ("다음 달이면 만 35세", 에이전트 질문 3-11).
- **나이 칸에 자녀 나이가 적힌 정책이 11건**(부모급여 만 ~1세, 가정양육수당 2~6세, 아이돌봄 ~12세 등). 상한이 만 15세 미만이면 자녀 나이로 보고 확인 필요로 둔다 — 그대로 비교하면 육아 정책이 모두 탈락한다. 상한 99 · 999, 하한 1 같은 값은 사실상 제한 없음이라 그대로 비교해도 된다.
- **나이 정리 규칙을 고쳤다 (1단계 규칙 변경).** 국민취업지원제도(원본 15~69세)가 나이 모름이었다. 원문의 "15세~69세"는 읽지 못하고 세부 조건 "15~34세 청년은 재산 5억 이하"만 읽어 어긋난다고 본 탓이다. 고친 뒤 원문과 어긋나면 비우지 않고 둘을 감싸는 가장 넓은 범위를 쓴다 — 세부 조건별 범위를 여러 개 적은 정책이 많고("18~34세 … 35~39세도 참여 가능"), 넓게 잡으면 받을 수 있는 사람을 잘못 떨어뜨리지 않는다. 전체 12건이 바뀌었다 (모름 → 숫자 8건: 국민취업지원제도 15~69, 청년도전지원사업 18~39 등 / 범위가 넓어짐 4건). `policy_renormalize --save` 로 적용했다.
- 나이 칸이 비어 있는 정책은 관악구 후보 중 141건이다. 136건은 원본 숫자가 0 · 0 이고 본문에도 "OO세"가 없다 (133건은 원본 '나이 제한 있음' 표시가 Y). 본문에 "OO세"가 있는 5건(K-패스, 심리상담 바우처 등)은 모두 신청 나이가 아니었다 (청년 우대율 · 보호자 동의 · 자녀 나이 · 법 설명 · 조사 대상). 본문 숫자를 그대로 나이 칸에 넣으면 틀린 조건이 생긴다.
- 검색 30개 안에서 불충족을 빼고 빈자리는 채우지 않는다. 3개가 안 남으면 어떻게 할지는 6단계에서 정한다.

**확인한 것**
- 시험지에 `profile` 칸을 더했다. 문장에 드러난 나이 · 취업 상태만 적고 지어내지 않았다 (11문제).

## 정책 50건 실험에서 배운 것 (11-06)

- 구체적인 고민은 단어가 달라도 찾는다 ("시험 비용" → "응시료").
- 고민이 둘이면 한쪽으로 쏠린다. "면접 교통비랑 정장"은 상위 3개가 전부 정장이었다 → 필요별 검색.
- 막연한 질문은 오답이 많다. "돈 모으고 싶어"를 "청년 저축 자산 형성 통장 지원"으로 바꾸면 상위 4개가 모두 맞았다 → 질문 다듬기.
- 맞는 정책이 없어도 뭔가 내놓는다 → 낮은 점수 기준 필요. 기준은 정답 문제를 만든 뒤 정한다.
