# 머니쿠션 페르소나 기반 알파 테스트 데이터 설계서

일반적인 소비를 하는 28세 자취 직장인 한 명의 생활·자금·거래 기준이다. 데이터 생성 담당자는 이 문서의 고정 금액과 날짜로 원장을 만들고, 검증 담당자는 6장의 정답과 비교한다. 인물·금융상품·거래는 가상이며, 가맹점 상호·업종은 지역 상가 스냅샷을 사용한다. 금액은 시장 평균이나 ML 예측값이 아니다.

알파 날짜는 2026년 11월 5일이다. 서버는 실제 오늘 날짜를 사용하며 고정 시계를 쓰지 않는다. 1~7절의 금액·건수·잔액은 10월 회귀 정답이다. 7~10월 전체와 11/1~11/5 정답은 9절에서 구분한다. 급여일은 매월 1일로 유지한다.

### 카드대금과 잔액 검증 조건

10월 14일 A에서 나가는 140,000원은 9월 사용분이다. 9월 청구서 1장과 상세 항목 3개(영상 12,000·음악 8,000·숙박 120,000)를 선행 자료로 넣는다. 구매일은 각각 9월 8·12·24일이다. 10월 소비에 다시 더하지 않는다.

10월 신용카드 승인 3건은 11월 청구서의 항목으로 이어진다. 가상 이용기간은 매월 1일~말일, 납부일은 다음 달 14일이다. 할부·이자·수수료·환율은 없다. 첫 카드 연결일은 6월 1일로 두어 최초 연결 선차감과 섞지 않는다.

월말 입출금 합계는 2,480,000원이다. 기존 입출금 2,200,000 + 급여 3,000,000 − 소비 관련 실제 출금 1,820,000 − 적금 900,000 = 2,480,000. 이 사례는 전월 카드대금과 당월 신용 사용액이 우연히 모두 140,000원이므로 소비 합계와 현금 출금 합계가 같다.

쿠션은 A 잔액 중 기존 1,000,000 + 이번 달 보호 배정 150,000 = 1,150,000원으로 가정한다. 다른 계좌 잔액처럼 합산하지 않는다. 목표는 월급의 3배인 9,000,000원, 이번 달 사용은 0원이다.

### 분류와 집계 원칙

오프라인 가맹점은 merchants.csv의 실제 원문 상호·지점·업종을 사용한다. 실제 구매 기록은 아니다. 식료품은 단일 업종 반찬·식료품 소매점으로 만들고, 다품목 슈퍼마켓과 구별한다. 배달 거래에는 분식 가맹점명도 보존한다. 편의점 2건은 품목을 추측하지 않고 UNCLASSIFIED로 유지한다.

서점은 교육, 볼링은 문화·여가, 빨래방은 기타다. 구독은 문화·여가 + 고정 표시이며 별도의 구독 카테고리를 만들지 않는다. 기타·미분류는 10개 ML 정답에 넣지 않는다.

체크카드 66건에는 같은 금액·시각의 B 출금 66건을 추가하고 SAME_PURCHASE로 연결한다. 원장에는 둘 다 남기되 카드 승인만 소비에 집계한다. 교통비 60,000원은 30일 합산 청구 1건이며 승차 내역을 추가 소비로 만들지 않는다.

## 6 이 데이터로 나와야 하는 정답

기준 기간은 2026-10-01 00:00 이상, 2026-11-01 00:00 미만 KST다. 승인 취소·환불은 기본 세트에 없으므로 전부 canceled_amount=0, is_canceled=false다. 계좌 출금 중복을 제거한 순소비를 집계한다.

### 현재 코드와 비교할 때 주의할 차이

생활비 범위는 사용자가 확인한 11/3 budgets/scope.py의 living_spent 기준으로 주거·통신·여행을 제외하며, 10월 정답은 930,000원이다. 첨부한 scope를 현재 폴더에 추가하고 함수 결과를 직접 대조했다. 최신 main의 화면·분석 호출부 연결을 유지한다. 기존 spending_summary(living_only=True)의 1,050,000원과 혼용하지 않는다.

현재 거래 응답의 funding은 fixed/living 두 값만 표시한다. 숙박에 spending_allocation.funding_bucket=free를 저장해도 transaction_item 응답은 living으로 보인다. 예산 밖 소비를 어떤 화면에서 별도 집계할지는 결정이 필요하다. 홈의 승인 예산과 예산 밖 지출 표시는 최신 main의 구현을 유지한다.

### 합계가 맞는지 확인하는 등식

3,000,000 = 770,000 고정 + 900,000 저축 + 150,000 쿠션 + 1,050,000 생활비 + 130,000 여윳돈

3,000,000 − 1,820,000 소비 − 900,000 저축 = 280,000<br>
280,000 = 남은 생활비 120,000 + 남은 여윳돈 10,000 + 쿠션 배정 150,000

10월은 챗봇의 “지난달” 정답으로 사용한다. 홈은 실제 오늘에 해당하는 11월 주기를 사용한다. 11월 5일 이전에 실행하면 그날까지의 거래만 적재·집계하며 11/5의 전체 기대값을 그대로 쓰지 않는다.

10월 원장 예상 건수는 147행이다. 중복 제거 후 소비 73건 + 체크 계좌 중복 66행 + 소비 외 자금 이동 8행이다. 9월 구매를 설명하는 청구 상세 항목은 별도 테이블에 두며 이 건수에는 포함하지 않는다.

## 8 결정이 필요한 것과 질문

- 급여일 1일을 유지하며 서버 시계는 바꾸지 않는다. 더미 서버의 CHAT_TODAY는 today로 설정해 실제 날짜를 사용한다.
- 숙박 120,000원의 여윳돈 차감 결정은 아직 비어 있다. 기존 차감 가정의 숫자를 별도 표시하며 서비스 정책 확정으로 취급하지 않는다.
- 계정은 승인 계정 alpha.home@example.test와 온보딩 계정 alpha.onboarding@example.test의 두 개다. 실제 사용자·은행 인증은 없다.
- 새 시드는 기존 A/B/C와 분리해 현재 날짜 이하의 합성 전표만 적재한다. 11/5에 다시 실행하면 11/5까지 보충되며, 두 계정의 비밀번호·시연 변경은 초기화된다.
- 거래 CSV의 정답은 승인 계정 기준이다. 온보딩 계정은 고정지출 설정 전이므로 생활비 재원 표시가 동일하다고 가정하지 않는다.
- 현재 Docker 엔진 접속이 되지 않아 PostgreSQL 통합 테스트·실제 적재는 미실시다. 필드·FK·합계·날짜·CSV를 검증하고, 온보딩 API와 관련 회귀는 임시 SQLite에서 보조 검증했다. PostgreSQL 제약·잠금 검증을 대체하지 않는다.
- 최신 main의 홈 승인 예산 표시·주거/여행 제외 계산·예금계좌 수집 대상 제외 변경을 유지한다. PostgreSQL 재실행은 현재 접속 문제로 확인하지 못했고, SQLite API 보조 검증과 구분한다.

### 시드와 계정 사용

풀 받은 `backend/spending_fixture/seed.py`에 `--alpha`를 연결했다. 구현은 `local_workspace/scripts/alpha_test/seed.py`에 두어 기존 3인 시드와 분리했다. 첨부한 scope의 생활비 계산은 `backend/budgets/scope.py`에 추가하고 10월 930,000원을 검증했다. 기본 시드는 그대로이며 알파는 전용 두 UUID·이메일만 재생성한다.

시드는 `alpha.home@example.test` 승인 계정과 `alpha.onboarding@example.test` 온보딩 계정 2개를 생성한다. 승인 계정에는 11/1~12/1 주기, 월급 3,000,000원, 생활비 1,050,000원, 고정 770,000원, 저축 900,000원, 쿠션 150,000원, 미배정 130,000원의 테스트 승인 스냅샷을 넣는다. 온보딩 계정은 계좌·카드·거래만 넣고 승인 예산은 넣지 않는다. **시드 연결과 DB 없는 계획 검증을 완료했으며 실제 적재는 아직 하지 않았다.** 온보딩 계정에는 금융 자료와 합성 조회 동의·이력만 있고 프로필·예산·고정지출 설정은 없다.

실행 방법은 backend/spending_fixture/README.md의 알파 절을 따른다. 저장소 루트에서 생성기를 실행한 다음 backend 폴더에서 `../.venv/Scripts/python.exe -m spending_fixture.seed --alpha`로 dry-run, `--alpha --apply`로 적재한다. 그 뒤 FIXTURE_LOGIN_PASSWORD 환경변수를 설정하고 `../.venv/Scripts/python.exe -m spending_fixture.set_login --alpha`로 두 계정의 비밀번호를 정한다. 재적재하면 비밀번호와 시연 변경이 초기화된다.

더미 서버는 PowerShell에서 `$env:CHAT_TODAY = "today"`를 설정한 뒤 기존 service_settings로 실행한다. 기본 3인 시드의 10/29 날짜는 바꾸지 않았다. 알파 시드는 현재 KST 날짜 이하의 합성 전표를 넣고 미래 날짜는 제외한다. 당일 전표는 생활 패턴용 가상 시각과 무관하게 포함한다. 11/5에 재실행하면 11/5 월중 정답 전체가 된다.

최신 main의 홈 승인 예산 표시와 생활비 범위 연결을 유지한다. 적금 C는 deposit으로 보존하며 main의 소비 수집 판정에서 제외된다. 청구서는 카드사 단위 scope_type=issuer, card_id=null이며, card_bill_list 성공 이력은 최초 연결일 6/1부터 적재일(최대 11/5)까지 둔다. 승인 내역 수집 이력과 별개의 합성 근거이며 실제 금융 조회가 아니다. 이 PC에서는 PostgreSQL 접속이 되지 않아 재실행하지 못했으며 SQLite 보조 API 회귀 검증을 구분해서 기록한다. local_workspace는 기본적으로 Git 제외 대상이지만, 이번 알파 기능의 필수 코드·합성 자료·정답·설계서·테스트만 명시적으로 추적해 저장소에 포함한다. 원자료·모델·개인 환경은 포함하지 않는다.

금융 연결 단계 생략은 service_settings의 지정 온보딩 UUID·이메일과 관리 계좌 A/B·카드 D/E·거래를 서버가 확인한 경우에만 적용한다. 프로필 응답의 onboardingNextStep=salary를 받아 월급 설정으로 이동한다. 일반 계정은 connect이다. 지정된 두 알파 계정(UUID·이메일 일치)에만 GET /api/finance/connect/accounts/와 GET /api/finance/connect/cards/의 저장 자료 조회를 허용한다. 인증·조회 동의·자산 및 연결 소유자 검사를 유지하고 해제된 연결은 제외한다. 계좌 목록에는 관리 대상 입출금 A/B와 받는 저축 계좌인 미선택 적금 C도 포함한다. 일반 계정은 기존 503, 미인증 조회는 403이고 일반 서비스 API는 그대로다. 금융 동의·계좌/카드 선택 변경·연결·동기화는 계속 503으로 차단한다.

연결 생략은 자동 감지를 구현한 것이 아니다. detect_candidates()는 여전히 미구현이고 온보딩 계정의 후보·확정 고정지출·저축은 비어 있다. 이 PR의 온보딩은 고정지출 6개 합계 77만원과 적금 90만원을 직접 등록하고 지킬 돈을 저장하는 경로로 테스트한다. 승인 계정에 미리 넣은 confirmed/manual 설정은 합성 시드이며 실제 감지 결과가 아니다.

숙박의 여윳돈 차감은 사용자의 결정란이 비어 있어 기존 설계의 차감 가정으로만 계산했다. `free_remaining_if_deducted`와 `travel_free_deduction_assumed`는 그 가정의 숫자다. 소비·생활비·잔액 정답은 이 가정과 독립적이다.
