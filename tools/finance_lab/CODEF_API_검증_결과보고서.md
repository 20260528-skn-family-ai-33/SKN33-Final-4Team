## 1. 핵심 결과

**머니쿠션에 필요한 계좌·카드·대출 관련 6개 API를 CODEF 샌드박스에 실제 호출하여 모두 HTTP 200 및 업무 성공 코드 `CF-00000`을 확인했다.** 요청 전송, 인증 토큰 사용, 응답 디코딩, 상품별 데이터 구조와 화면 표시를 검증했다.

기본 계좌 조회, 입출금 내역, 카드 승인·청구, 대출 기본정보를 서비스에 활용할 수 있는 구조를 확인했다. 다만 샌드박스는 고정 테스트 응답을 반환하므로 실제 금융기관 인증, 사용자별 거래의 완전성, 모든 기관의 필드 제공 여부까지 검증한 결과는 아니다. [공식 SDK 안내](https://github.com/codef-io/easycodefpy)

**데모 신청, 개인 금융기관 로그인, 실데이터 조회, 정식 API 호출은 수행하지 않았다.** 이번 보고서 작성 과정에서도 추가 외부 금융 API 호출 없이 기존 검증 결과와 공식 명세 확인 내용을 정리했다.

## 2. 목적과 검증 범위

수정된 MVP 프로토타입을 기준으로, 서비스 개발에 앞서 필요한 금융 API의 연결 가능성과 반환 정보를 확인하는 것이 목적이다. 원본 프로토타입 HTML은 수정하지 않았으며 별도의 로컬 테스트 화면을 구성했다.

| 구분 | 역할 | 검증 범위 |
| --- | --- | --- |
| CODEF 샌드박스 | 실제 CODEF 서버와 통신 | 토큰, 6개 상품 요청·응답, 구조 확인, 원본 표시 |
| 로컬 모의 데이터 | 자체 합성 JSON 사용 | 기관 연결 UI, 다중 계좌·카드 선택, 부분 실패, 모의 추가 인증, 빈값 |
| 실제 데모·정식 환경 | 사용자 금융정보 조회 | 이번 검증에서 제외 |

로컬 모의 연결의 성공은 실제 은행 인증의 성공을 의미하지 않는다. CODEF 샌드박스 결과와 로컬 합성 데이터는 화면과 응답 출처에서 구분한다.

## 3. API별 실호출 결과

아래 건수는 이번에 받은 샌드박스 응답 기준이다. 화면 표시를 위해 임의로 줄인 건수가 아니며, 실제 사용자 거래량을 나타내지 않는다.

| API | 경로 | HTTP / 업무 코드 | 반환 결과 |
| --- | --- | --- | --- |
| 보유계좌 | `/v1/kr/bank/p/account/account-list` | 200 / CF-00000 | 계좌 3개, 대출 계좌 1개 |
| 수시입출 거래내역 | `/v1/kr/bank/p/account/transaction-list` | 200 / CF-00000 | 거래 6건, 잔액·출금가능액 |
| 보유카드 | `/v1/kr/card/p/account/card-list` | 200 / CF-00000 | 카드 3개 |
| 카드 승인내역 | `/v1/kr/card/p/account/approval-list` | 200 / CF-00000 | 1건, 주요 값 마스킹 |
| 카드 청구내역 | `/v1/kr/card/p/account/billing-list` | 200 / CF-00000 | 청구 상세 3건, 청구 요약·할부 관련 필드 |
| 대출 거래내역 | `/v1/kr/bank/p/loan/transaction-list` | 200 / CF-00000 | 거래 1건, 대출 원금·잔액·약정이율·만기·납부일자 |

은행 기관코드는 `0004`, 카드사 기관코드는 `0309`를 사용했다. 모든 금융기관을 대상으로 검증한 것은 아니다. 계좌·대출 번호는 샌드박스 목록 응답의 공개 샘플, Connected ID는 공식 예제의 샌드박스용 고정값을 사용했다. 개인 인증정보는 입력하지 않았다.

거래 조회 요청 기간은 `20190601`~`20190630`, 청구월은 `201906`을 사용했다. 고정 샘플에는 요청 범위와 다른 기간·날짜가 포함되어 있으므로 기간 필터가 정상 작동한다고 판정하지 않았다.

공식 상품 문서: [보유계좌](https://developer.codef.io/products/bank/common/p/account), [수시입출 거래](https://developer.codef.io/products/bank/common/p/transaction), [보유카드](https://developer.codef.io/products/card/common/p/account), [카드 승인](https://developer.codef.io/products/card/common/p/approval), [카드 청구](https://developer.codef.io/products/card/common/p/billing), [대출 거래](https://developer.codef.io/products/bank/common/p/loan).

## 4. 주요 데이터와 서비스 활용 가능성

### 4.1 계좌

계좌명·번호·잔액·통화, 거래일·입금·출금·거래 후 잔액 등의 구조를 확인했다. 계좌 거래 샘플에는 급여 여부를 판정할 수 없는 입금, 정기 출금, 이자 등 서로 다른 내역이 포함된다. 단순 입금을 급여로 자동 확정해서는 안 된다.

기본 자산 조회와 거래 원장 구축에 활용할 수 있다. 다만 급여 판별, 소비 분류, 반복 지출 탐지, 안전 소비액 산정은 우리 서비스에서 별도로 구현해야 한다. 잔액을 곧바로 안전 소비액으로 표시하지 않는다.

### 4.2 카드

승인 응답에서 사용일·가맹점·이용금액·취소 구분·취소금액·할부개월 필드를 확인했다. 이번 샌드박스 승인 샘플은 주요 값이 마스킹되어 실제 소비 분석이나 취소금액 계산을 검증할 수 없었다.

청구 응답에서는 총청구액, 결제 예정일, 결제계좌와 상세 내역을 확인했다. 이번 샘플의 총청구액은 `298253`, 할부 금액은 `0`이며 상세 내역은 3건이다. 이 값들은 과거 고정 테스트 샘플이다. 청구 상세 3건의 합계를 총청구액과 동일한 전체 원장으로 취급하지 않는다.

할부 정보는 별도 임의 API를 추가하지 않고 청구 응답의 할부 금액·개월·회차 필드로 확인했다. 이번 샘플에는 양수 할부 사례가 없어 실제 할부 회차별 계산은 미검증이다. 총청구액에 할부 금액을 다시 더하지 않는다.

### 4.3 대출

원금·잔액·약정이율·만기·납부일자와 거래내역 구조를 확인했다. 샘플에는 원금·잔액 `120000000`, 약정이율 `1.44`, 만기 `20210628` 등이 포함되어 있다. 현재 유효한 실제 대출 조건이 아니다.

반환된 거래 1건의 유형은 **일반신규**이다. 이를 대출 상환 내역으로 표시하지 않는다. `resDatePayment`는 공식 명칭인 **납부일자**로 표시하며 다음 이자 납입일로 단정하지 않는다. [대출 거래 명세](https://developer.codef.io/products/bank/common/p/loan)

**다음 회차 상환 예정액·전체 상환 일정은 이번 응답으로 확보를 확인하지 못했다.** 대출 잔액이나 과거 거래만으로 월 상환 예정액을 임의 산출하지 않으며, 추가 제공 수단이 없으면 사용자 입력·확인으로 보완할 필요가 있다.

## 5. 마스킹·누락값 판단

마스킹, 미제공, 숫자 0은 의미가 다르다. 테스트 화면은 `****`를 마스킹, 빈 문자열·null·필드 부재를 미제공, `0`을 실제 반환된 0으로 구분한다.

| 항목 | 이번 샌드박스 관찰 | 실제 데모에 대한 판단 |
| --- | --- | --- |
| 카드번호 | 일부 가림 또는 마스킹 형식 | 승인 명세에도 `1234********5678` 형식이 명시되어 있어 실제 조회에서도 마스킹을 고려해야 함 |
| 카드 사용일·금액·가맹점 | 승인 샘플의 주요 값이 가려짐 | 공식적으로 제공되는 필드이며, 샌드박스 마스킹이 실데이터에도 동일하게 적용된다고 단정할 수 없음 |
| 청구 상세 결제금액 | 일부 빈값, 결제원금은 존재 | 기관·거래별 필드 제공 차이를 확인해야 함; 빈 결제금액을 0으로 대체하지 않음 |
| 출금 예정일 | 샘플에 미제공 | 결제 예정일과 구분하고 제공 여부를 데모에서 확인 |
| 대출 금리·만기 | 이번 샘플에 값 존재 | 전반적인 누락을 판단할 근거는 없지만 모든 기관 제공을 보장하지 않음 |
| 대출 월 상환 예정액 | 확보 미확인 | 별도 확인 또는 사용자 보완 입력을 준비 |

**현재 표본만으로 실제 서비스의 누락률이나 마스킹 비율을 산정할 수 없다.** 공식 출력 명세의 필수 표시만으로 모든 기관·거래에서 항상 값이 존재한다고 가정해서도 안 된다. 예를 들어 카드 청구 명세의 이용금액에는 특정 카드사의 빈값 예외가 명시되어 있다. [승인 출력 명세](https://developer.codef.io/products/card/common/p/approval), [청구 출력 명세](https://developer.codef.io/products/card/common/p/billing)

카드번호가 마스킹되어도 날짜·금액·가맹점이 제공되면 소비 분석은 가능한 방향이다. 다만 카드 식별을 마스킹된 번호 하나에만 의존하지 않고 사용자·기관·카드명 및 상품에서 요구하는 중복 구분 정보를 함께 검토해야 한다.

## 6. 구축한 검증 환경

로컬 주소는 [http://127.0.0.1:8765/](http://127.0.0.1:8765/)이며, 서버가 실행 중인 PC에서 접근한다. 배포된 서비스 주소가 아니다.

- **전체 API 새로 검증**: 6개 상품을 순차 호출한다.
- **이 API 새로 검증**: 해당 상품만 다시 호출하고 다른 상품의 결과를 유지한다.
- **요청·데이터·원본 응답 확인**: 요청 주소와 고정 JSON, 주요 필드·내역 표, 성공 원본 JSON을 확인한다.
- **결과 표시**: HTTP 상태, CODEF 업무 코드, 건수, 소요 시간, 검증 시각을 구분한다.
- **오류 구분**: 미검증, 정상 빈 결과, HTTP 오류, 업무 오류, 추가 인증 필요, 통신 실패, 구조 불일치를 구분한다.

화면의 새로 검증은 캐시를 건너뛰고 CODEF 샌드박스에 실제 요청한다. 내부 API에서 `refresh: false`를 사용하면 성공 응답을 상품별 60초간 재사용한다. 실패한 조회를 합성 성공 데이터로 대체하지 않는다. 검증 시각은 금융 데이터의 기준일이 아니다.

기본 구조:

```text
브라우저 검증 화면
  ├─ 로컬 모의 API → 자체 합성 JSON
  └─ 샌드박스 검증 API → CODEF OAuth → CODEF 샌드박스 6개 상품
```

공개 샌드박스 설정은 Git 제외 로컬 파일에 저장하고 토큰은 메모리에 보관한다. 개인·데모·정식 인증값, 임의 외부 URL, 리디렉션을 허용하지 않는다. 현재 코드는 데모 키와 주소만 바꾸면 바로 전환되는 구조가 아니다. [실행 및 구조 문서](README.md)

## 7. 검증 결과와 한계

| 검증 항목 | 결과 |
| --- | --- |
| 공개 샌드박스 토큰 발급 | HTTP 200 |
| 6개 상품 실호출 | 모두 HTTP 200 / CF-00000 |
| 브라우저 전체 검증 | 정상 6 / 실패·확인 필요 0 |
| 계좌 거래 상세 펼치기 | 요청값 및 실제 반환 6건 표시 확인 |
| 개별 재검증 | 계좌 거래 재호출, 다른 API 결과 유지 확인 |
| 자동 테스트 | 36개 통과: 모의 14개, 샌드박스 기본 12개, 상품별 검증 10개 |
| 의존성·JavaScript·공백 검사 | pip check, node --check, git diff --check 통과 |
| 비밀값 검사 | 인증값 소스 포함 0건, 로컬 설정 Git 제외 및 권한 0600 확인 |
| 원본 프로토타입 | SHA-256 대조 결과 변경 없음 |

자동 테스트는 대체 HTTP 전송 계층 등을 사용하며 외부 금융 API를 호출하지 않는다. 실호출과 브라우저 검증은 위 자동 테스트와 별도로 수행했다. 테스트 클라이언트에서 httpx 지원 방식의 향후 변경 경고가 발생했지만 현재 테스트 실패는 없다.

이번 결과로 검증되지 않은 사항은 다음과 같다.

- 실제 사용자 인증·계정 등록·Connected ID 발급 및 기관별 추가 인증.
- 모든 은행·카드사의 지원 여부, 필드 제공 범위 및 응답 일관성.
- 조회 기간 필터, 대량 거래, 구간 분할 조회와 재조회 시 누락·중복 처리.
- 실제 취소·부분취소, 양수 할부의 회차·잔액 계산.
- 실제 대출 상환 내역, 다음 회차 납부액 및 상환 일정.
- 제품 프런트엔드·DB·사용자별 접근 권한과의 통합.
- 운영 환경의 성능·호출량·비용·장애 대응.

샌드박스 응답 속도나 작은 샘플 건수로 실서비스 성능을 추정하지 않았다. 데모 무료기간 시작 조건과 호출 한도 역시 이번 검증의 대상이 아니므로 확정 정보로 기록하지 않는다.

## 8. 머니쿠션 적용 판단

| 서비스 기능 | 판단 | 구현 시 보완점 |
| --- | --- | --- |
| 자산 목록·계좌 잔액 | 기본 연동 구조 확보 | 선택 계좌 매칭, 적금·마이너스통장 등 유형 구분 |
| 입출금·카드 소비 분석 | 데이터 처리 구조 확보 | 실제 가맹점·금액 검증, 거래 분류·중복 제거 |
| 카드 결제 예정 지출 | 청구 관련 필드 확인 | 청구서 미발행, 기관별 누락, 카드사 범위와 카드별 범위 구분 |
| 대출 보유 현황 | 기본정보 조회 구조 확인 | 누락값 표시 및 사용자 보완 |
| 대출 월 상환 예산 | 현재 응답만으로 자동화 보장 불가 | 예정액의 추가 확보 또는 사용자 확인 |
| 안전 소비액·추천 예산 | CODEF 단독 제공 대상 아님 | 급여일·고정비·저축·쿠션 등과 자체 계산 엔진 결합 |

계좌 중심 MVP를 진행할 근거는 확보했다. 카드·대출은 필드별 제공 여부와 누락 시 처리 방식을 정한 뒤 통합해야 한다. 특히 카드 사용내역과 계좌의 카드대금 출금을 소비로 두 번 계산하지 않는 규칙이 필요하다.

## 9. 데모 연결 전 준비 및 이후 검증

아래는 후속 제안이며 이번 작업에서 실행하거나 데모 신청을 승인한 내용이 아니다.

1. **데모 전 준비**: 원본 응답을 사용자·기관·계좌·카드와 연결하는 내부 모델, 저장·재조회·중복 제거, 미제공·마스킹·0 구분, 예산 반영 규칙을 구현한다.
2. **인증 흐름 준비**: 실제 기관 인증 수단, 계정 등록·Connected ID, 추가 인증·만료·재연결과 서버 측 인증정보 관리를 설계한다. [공식 SDK 계정 관리 안내](https://github.com/codef-io/easycodefpy)
3. **사용자가 지정한 시점에 데모 검증**: 별도 승인 후 대상 은행·카드사와 본인 금융정보로 실제 인증·선택 자산 매칭·거래 기간·금액·청구액·상환 내역을 확인한다.
4. **제품 통합 판정**: 실제 조회 화면과의 대조, 누락·중복 확인, 금액 합산·예산 반영 검증을 통과한 범위부터 적용한다.

소비 분석이나 예산 계산을 위한 많은 거래가 필요하면 별도의 합성 데이터를 사용한다. 이 데이터는 로직 테스트용이며 실제 CODEF 연결 검증의 근거로 대체하지 않는다.

## 10. 실행 방법과 참고 자료

현재 준비된 PC에서 저장소 루트 기준:

```sh
.venv-finance/bin/python -m tools.finance_lab
```

자동 테스트:

```sh
.venv-finance/bin/python -m unittest discover -s tools/finance_lab/tests -v
```

최초 설치, 샌드박스 설정, 경로와 요청 형식은 [실행 안내](README.md)를 따른다. 실제 샌드박스 요청과 보안 제한은 [sandbox.py](sandbox.py), 상품별 표시·자료 구조 검증은 [verification.py](verification.py), HTTP 경로는 [app.py](app.py)에 있다.

검증 근거는 2026-10-15의 실제 샌드박스 응답·브라우저 확인·자동 테스트 결과 및 위 공식 상품 명세이다. SDK 연결 규칙은 [검증에 사용한 고정 버전](https://github.com/codef-io/easycodefpy/tree/23e4e5c9f6c225eddf604c96621a31375b3bc2bc)을 참고했다. 본 문서에는 개인 인증값·토큰·실제 사용자 금융정보를 포함하지 않았다.
